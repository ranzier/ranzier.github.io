2. goodskill-order-provider (订单服务提供者)

分为两个模块：

2.1 goodskill-order-api

OrderService接口及其实现类：

  • OrderService接口
  • OrderServiceFallback实现类

基于 Spring Cloud OpenFeign 实现的 订单微服务 (goodskill-order) 远程调用接口，并提供了 熔断降级处理。
它的作用是让其他微服务（比如 goodskill-seckill-provider）可以通过 FeignClient 远程调用订单服务，并在服务不可用时提供降级策略。

OrderService接口

  • 指定调用的微服务名称：goodskill-order
  • 设置熔断降级实现类：OrderServiceFallback
  • 这意味着当 goodskill-order 服务 不可用 时，调用 OrderServiceFallback 里的方法返回默认值，而不是让请求直接失败。

接口中：定义远程调用的 API

  • 调用 goodskill-order 服务的 /deleteRecord 接口，删除秒杀订单
  • 调用 goodskill-order 服务的 /saveRecord 接口，保存订单记录。
  • 调用 goodskill-order 服务的 /count 接口，查询某个 seckillId 的 订单数量。

OrderServiceFallback（熔断降级实现类）

降级策略：

  • 当 deleteRecord() 调用失败时，返回 false，表示删除失败。
  • count() 方法在降级时 抛出异常，表示此接口不提供备用方案。

2.2 goodskill-order-service

2.2.1 OrderApplication启动类

订单微服务（goodskill-order-provider）的启动类 OrderApplication，使用的是 Spring Boot + MongoDB + 消息驱动模型（类似 Stream 消费）。

  • 实现：监听名为 seckillMongoSave 的消息队列（或通道），接收秒杀请求信息 SeckillMockSaveVo，然后封装为 OrderDTO 对象并存入 MongoDB。
  • 启动订单服务（基于 Spring Boot）
  • 启用 MongoDB 的仓库支持
  • 监听名为 seckillMongoSave 的消息通道
  • 每当有用户秒杀请求（如压测模拟数据）通过消息中间件发来时：
    • 接收消息
    • 构建订单对象 OrderDTO
    • 调用 OrderServiceImpl 将其保存至 MongoDB

3. goodskill-seckill-provider (秒杀服务提供者)

3.1 goodskill-api

3.1.1 DTO和VO

DTO数据传输对象：

  • ExposerDTO: 暴露秒杀地址 的数据传输对象（DTO），它的作用是在秒杀接口开放时，向前端返回当前秒杀的状态和必要参数（如 MD5 加密串）
  • GoodsDTO: 商品信息的 数据传输对象（DTO）,用于封装秒杀商品或普通商品的基本信息，便于服务之间传输或展示在前端页面
  • SeckillExecutionDTO: 用于表示 秒杀执行结果 的数据传输对象（DTO），主要是用来封装一个用户参与秒杀后的结果详情，比如成功/失败状态、相关描述、下单数据、以及二维码路径等
  • SeckillInfoDTO: 封装秒杀活动基本信息的一个数据传输对象（DTO）,用于传递秒杀活动的详细信息，包括时间、商品、库存和价格等
  • SeckillMockCanalResponseDTO: 用于表示秒杀活动状态变更响应结果的一个数据传输对象（DTO）,常用于消息传递、活动更新反馈
  • SeckillMockRequestDTO: 用于模拟秒杀请求的请求数据传输对象（DTO）,主要用于秒杀接口的压测或定时任务模拟用户请求行为
  • SeckillMockResponseDTO: 用于返回秒杀模拟任务执行结果的响应数据传输对象（DTO）,包含秒杀活动 ID、执行备注、状态以及任务 ID
  • SeckillResponseDTO: 用于封装 秒杀操作返回的二进制数据（byte[]），通常用于返回一些 结构化或文件类的数据内容，而不是简单的 JSON 文本
  • SuccessKilledDTO: 用于封装秒杀成功记录的 数据传输对象（DTO），它记录了某个用户在参与某次秒杀活动时的详细信息与状态

VO：

  • GoodsVO: 用于表示 商品信息的值对象,用于传输与商品相关的信息，如商品ID、价格、描述等
  • SeckillVO: 用于表示 秒杀活动相关的数据。VO 类主要用于数据传输，通常用于前后端数据交互或传递业务数据

3.1.2 Service接口

  • GoodsEsService
  • GoodsService
  • SeckillService

GoodsEsService

GoodsEsService是一个 Feign 客户端接口，它用于和 goodskill-seckill 微服务进行通信,为 goodskill-seckill 服务提供了保存商品、批量保存商品、删除商品以及商品名称搜索的功能

GoodsEsService 接口定义了与 goodskill-seckill 微服务进行商品信息交互的操作。包括以下功能：

  1. 保存商品信息：通过 save 方法，将单个商品信息保存到 goodskill-seckill 服务。
  2. 批量保存商品信息：通过 saveBatch 方法，将多个商品信息批量保存到 goodskill-seckill 服务。
  3. 删除商品信息：通过 delete 方法，根据传入的 GoodsDTO 对象删除商品信息。
  4. 根据商品名称进行分页查询：通过 searchWithNameByPage 方法，根据传入的关键词查询商品信息，并分页返回结果。

GoodsService

用于处理商品相关业务逻辑的接口，提供了多个方法来管理商品信息

GoodsService 接口主要负责商品的管理操作，包括：

  • 上传商品照片：通过 uploadGoodsPhoto 方法上传商品照片，并将照片关联到商品。
  • 添加商品：通过 addGoods 方法向系统中添加新的商品信息。
  • 查询商品列表：通过 findMany 方法查询多个商品信息，通常用于获取商品的集合。
  • 根据商品ID查询商品信息：通过 findById 方法查询指定商品的详细信息。

SeckillService

用于处理秒杀相关操作的服务接口，提供了多个与秒杀活动相关的功能。该接口通过 Feign Client 与名为 goodskill-seckill 的微服务进行通信

SeckillService 接口是用于管理秒杀活动的一个服务接口，涵盖了秒杀活动的以下几个方面：

  • 秒杀活动管理：包括查询、添加、更新、删除秒杀活动。
  • 秒杀商品管理：准备秒杀商品数量、减少商品库存等。
  • 秒杀操作：执行秒杀、获取成功秒杀记录、获取二维码等。
  • 秒杀统计：获取秒杀活动的成功秒杀记录数等。

3.2 goodskill-service

3.2.1 common包

  • CommonConstant 类： 是一个常量类，它的作用是统一管理项目中使用的 公共常量，主要用于消息队列（如 Spring Cloud Stream）中绑定通道（binding name）的定义
  • GoodsKillStrategyEnum 是一个 枚举类，用于表示秒杀系统中可选的多种策略实现方案，方便系统在运行时根据配置或参数选择不同的秒杀处理策略。秒杀策略枚举，通过枚举避免暴露具体方法
  • ResponseInfo 是一个 响应状态枚举类（Enum），用于统一定义后端接口的响应状态码和对应的信息，例如成功、失败、超时、服务器内部错误等
  • SuccessKilledService为SuccessKilled 实体提供 基础的增删改查（CRUD）服务，通过继承 IService<T> 来实现。

RedisService

RedisService 类是一个用于操作秒杀相关 Redis 缓存的工具类，它封装了对 Redis 的读写逻辑，主要目的是提升查询效率、减轻数据库压力、标识秒杀状态等

主要职责

  • 查询秒杀活动缓存（如果没有则查数据库并回填到 Redis）；
  • 写入/删除 Redis 缓存中的秒杀活动数据；
  • 管理秒杀是否结束的标识位（布尔值标识）；
  • 封装 Redis 访问逻辑，避免业务代码中重复操作 Redis。

技术点总结

  • 使用了 Redis 的过期机制和 setIfAbsent 机制，确保高并发下的操作一致性。
  • 缓存穿透控制：缓存未命中时自动加载数据库并回填，防止大量请求直击数据库。

3.2.2 config包

StateMachineConfig

用于控制“秒杀活动状态机”逻辑的核心配置类，它基于 Spring State Machine 状态机框架，通过配置状态、事件、状态转换规则、监听器、持久化机制来驱动一个流程（比如：秒杀活动的生命周期）按照预期的步骤运行。

目前秒杀活动状态的控制基于Spring Statemachine状态机实现，使用状态机的优点：

  • 统一控制活动状态，便于状态的集中维护；
  • 防止业务状态被随意更改，保证状态的可控更新；

  • StateMachineConfig 配置了 秒杀活动的完整生命周期状态机，包括状态、事件、状态转换逻辑、监听器和 Redis 持久化支持，是活动流程控制的核心配置。

ThreadPoolConfig

线程池配置类，用于在 Spring 容器中注册一个 ThreadPoolExecutor 类型的 Bean，供项目中的异步任务或并发操作复用。
提供一个可复用的线程池 taskExecutor，用来统一管理项目中的并发任务，比如执行秒杀异步逻辑、发送MQ、处理回调、记录日志等。

参数 含义
corePoolSize = 2 核心线程数：即使空闲也会保留 2 个线程
maximumPoolSize = 10 最大线程数上限为 10，超过就进入队列或拒绝
keepAliveTime = 1 分钟 非核心线程闲置 1 分钟后会被销毁
LinkedBlockingDeque<>(100) 队列最大缓存任务数是 100
CallerRunsPolicy 拒绝策略：当线程和队列都满了，任务由提交任务的线程自己执行（不会丢任务）

3.2.6 handler包

AbstractPreRequestHandler 抽象类

抽象基类，提供预处理器统一接口和执行顺序控制
用于请求前的统一处理流程（如校验、限流、日志、鉴权等）

DatabasePreRequestHandler

DatabasePreRequestHandler 是一个用于 数据库初始化/重置的请求预处理器，在某些业务场景中（如模拟秒杀环境或初始化测试数据），该处理器会：

  • 重置指定秒杀活动的库存数量
  • 清空该秒杀活动下的已成功秒杀记录

MongoPreRequestHandler

MongoPreRequestHandler 类的作用是：在执行秒杀压测或测试之前，清空 MongoDB 中该秒杀活动的相关订单记录，以保证测试数据干净、不会受到历史数据影响。

PreRequestHandler 接口

定义一个统一的“秒杀请求预处理”操作规范

PreRequestPipeline

统一调度和执行所有预处理器（PreRequestHandler）的逻辑，按照优先级顺序依次执行每个预处理步骤。

  • 入参是秒杀请求的数据对象 SeckillWebMockRequestDTO，包含诸如秒杀 ID、秒杀库存等信息。
  • 会遍历所有注册的 AbstractPreRequestHandler 实现类，按照 getOrder() 指定的顺序依次调用 handle(request) 方法。
  • 如果某个处理器出错，捕获异常并记录日志，继续执行后面的处理器，不中断整个流程。

RedisPreRequestHandler

RedisPreRequestHandler 类是一个预处理器组件，其作用是在执行秒杀前，清理和初始化 Redis 中与秒杀活动相关的缓存数据，以确保 Redis 缓存环境处于干净且正确的状态。

StateMachinePreRequestHandler

这个 StateMachinePreRequestHandler 类是一个预处理器组件，用于在秒杀活动开始前，通过状态机服务来初始化和管理秒杀活动的状态流转，是预处理责任链中的第三步

Handler的作用

秒杀系统的特点是高并发、数据敏感、状态复杂，所以在每次活动开始前，需要完成一系列的准备工作
这些 Handler 就像“启动前检查清单”，每个负责一个环节，从数据、缓存、状态、历史记录等多个维度做好准备，确保秒杀系统在高并发下也能稳定运行。
假设你运行一个新的秒杀模拟任务，流程如下：

顺序 处理器 功能
0 DatabasePreRequestHandler 重置数据库库存，清理订单记录
1 RedisPreRequestHandler 清除缓存、设置为活动进行中
2 StateMachinePreRequestHandler 初始化状态机、检测是否可重启、启动活动状态
3 MongoPreRequestHandler 清除 Mongo 中的订单记录

3.2.10 mock.strategy

GoodsKillStrategy

接口 GoodsKillStrategy 是一个 秒杀策略接口，用于支持策略模式，目的是根据不同的策略，执行不同的“秒杀处理逻辑”。

  • 定义了一个统一的秒杀处理方法 execute(…)

策略1：AtomicUpdateStrategy原子更新策略

实现了秒杀策略接口 GoodsKillStrategy 的一种具体策略实现，属于原子更新策略（Atomic Update）

AtomicUpdateStrategy 更强调：

  • 使用 数据库乐观锁机制 或 原子性更新语句（如 UPDATE … SET number = number - 1 WHERE number > 0）
  • 来保障高并发环境下的数据一致性与库存安全

策略2：AtomicWithCanalStrategy

AtomicWithCanalStrategy 是一个秒杀策略的具体实现类，结合了数据库原子性更新操作与**Canal监听 binlog（数据库变更日志)**的架构思路，来完成高并发秒杀的处理。

在秒杀时：

  1. 利用 数据库层的原子更新操作（SQL语句直接减少库存） 来防止超卖。
  2. 利用 局部同步锁（按商品 ID 加锁） 来控制并发。
  3. 将用户秒杀成功信息插入数据库（后续可通过 Canal 监听该表的 binlog 进行异步处理，比如发放优惠券、通知用户等）。
  4. 在库存耗尽时，通知状态机进入“结束计算”状态。

策略3：RedisMongoReactiveStrategy

RedisMongoReactiveStrategy 类的策略是处理秒杀请求的异步逻辑。它主要通过以下几个步骤：

  • 异步执行秒杀请求。
  • 使用 Redis 来判断秒杀商品库存，并进行增量操作。
  • 若秒杀成功，发送消息到消息中间件，进行 MongoDB 保存操作。
  • 若秒杀失败（库存不足），通过状态机检查活动状态，并发送秒杀结束的消息。

策略4：RedissonStrategy

通过分布式锁 Redisson 保证在高并发下对同一个商品的秒杀操作是线程安全的，避免超卖问题。

  • RedissonStrategy 是一种 基于 Redisson 分布式锁的秒杀策略，它通过给每个秒杀商品加锁来确保同一时间只能有一个线程处理某个商品的秒杀逻辑，从而实现并发控制和库存一致性。

策略5：SentinelLimitStrategy

SentinelLimitStrategy 是一个基于 Sentinel 的限流策略，用于在高并发场景下保护系统资源，防止秒杀接口被过载调用导致系统崩溃。它是 GoodsKillStrategy 接口的一个实现，核心是利用 Sentinel 做流量控制（限流）。

  • 通过 Sentinel 实现限流保护机制，限制每秒进入秒杀系统的请求数量；
  • 一旦请求超过阈值，Sentinel 会触发 blockHandler 方法，进行降级处理，而不会继续执行秒杀逻辑；
  • 通过 Sentinel 的流控规则对指定方法做限流
  • Sentinel 的限流是基于滑动窗口算法实现，性能开销低

策略6：SynchronizedLockStrategy

采用的是最传统的 Java 本地锁 synchronized 关键字来控制并发操作，防止秒杀超卖。

它的核心思想是：对每个商品 ID 建立一个监视对象（Object），然后用 synchronized 关键字对这个商品加锁，实现单商品的并发控制。

  • SynchronizedLockStrategy 是一种基于 Java 本地锁、按商品粒度加锁的秒杀策略，适用于单机项目，简单易实现，但不适合多节点部署。

策略7：ZookeeperLockStrategy

基于 Zookeeper 分布式锁的秒杀策略。它通过 Apache Curator 提供的 InterProcessMutex（分布式可重入锁）来控制对秒杀商品的并发访问，确保在分布式部署环境下的数据一致性和线程安全。

  • 提供的一种 可重入、阻塞式分布式锁实现
  • 保证在多个服务节点中，某一时刻只有一个节点可以获得锁来操作该商品。
  • 最后释放锁，无论执行成功与否，必须释放锁防止死锁。

1.1.1 Sychronized同步锁

一、synchronized 是怎么用的？
在 SynchronizedLockStrategy 策略类中，synchronized 被用于 按商品粒度加锁，控制对同一个商品的并发请求。

二、锁加在了哪里？
锁加在了 ConcurrentHashMap<Long, Object> seckillIdList 中的 商品 ID 对应的锁对象 上：

  • 每个商品 ID 有一把独立的锁。
  • 同一时间内，只能有一个线程执行同一个商品的秒杀逻辑。
    总结：对每个商品进行单独的加锁

三、它解决了秒杀中的哪些问题？

  • 高并发下库存超卖： 同时只有一个线程能扣库存
  • 多线程重复下单： 同步锁保障同一商品只被一个线程修改
  • 数据不一致： 扣库存 + 记录成功信息在一个锁内，保证原子性

四、但它有什么局限？

  • 只适合单机： synchronized 是 JVM 内部锁，不适用于多台服务器部署
  • 性能差 在高并发下会导致线程等待，吞吐量低

总结一句话：
synchronized 同步锁在 GoodsKill 中加在了 商品 ID 映射的锁对象上，用于控制每个商品的并发请求，解决了并发下的库存超卖和重复下单问题，但仅适合单机部署的秒杀系统。

1.1.2 数据库乐观锁

一、什么是乐观锁？
乐观锁是一种并发控制策略，它假设多个事务并发操作时不会发生冲突，因此在操作数据时不加锁。只有在更新数据时才检查数据有没有被其他事务修改。

二、GoodsKill 中的乐观锁使用场景

解决超卖问题：在 秒杀操作 → 减库存 这个流程中，如果多个用户同时抢购同一个商品，而没有并发控制，会导致库存被减成负数，即“超卖”。

乐观锁的作用就是：在更新库存时校验库存是否仍是“预期值”，如果不是，说明库存已经被别的线程改过了，就放弃更新，防止错误减库存。

三、实现方式（源码分析）
在 SeckillServiceImpl的reduceNumberInner方法中:

  • 商品库存 number > 0
  • 如果满足条件，则执行 SQL：UPDATE seckill SET number = number - 1
  • 如果 update == 0，说明：库存已经被抢完了，或者数据被其他线程修改了 → 当前线程更新失败（秒杀失败）。

四、总结：
GoodsKill 使用乐观锁策略，确保在高并发下只有在库存仍然大于 0 时才允许减库存，从而有效防止超卖和数据不一致的问题，同时保持系统高性能运行。

1.1.3 Redisson分布式锁

一、Redisson 分布式锁加在了哪里？

在策略类 RedissonStrategy 中使用的:

  • getLock(requestDto.getSeckillId() + “”) 是为 每个商品 ID 动态生成一把分布式锁。
  • 加锁粒度是：商品级别，每个商品 ID 拥有自己独立的锁。
  • 使用的是 Redisson 提供的 RLock 分布式可重入锁（基于 Redis 实现）。

二、它解决了秒杀中的哪些核心问题？

  • 分布式环境并发控制 多台服务器部署时，确保某一时刻只有一个线程在处理某个商品的秒杀逻辑
  • 避免超卖： 通过对库存扣减加锁，防止多个线程同时扣库存导致超卖
  • 保证库存一致性： 保证在执行秒杀逻辑（减库存、写成功记录）时数据一致性
  • 替代 synchronized： synchronized 只在单机有效，而 Redisson 适用于集群环境

✅ 集群测试（使用 RedissonLock）

总结一句话：

在 GoodsKill 项目中，Redisson 分布式锁被加在每个商品 ID 的锁对象上，用于控制分布式环境中同一商品的并发秒杀请求，从而有效防止库存超卖、数据错乱、秒杀异常等问题，是应对高并发场景下跨节点秒杀操作的关键手段之一。

1.1.5 Redis 计数 + MongoDB 异步持久化

RedisMongoReactiveStrategy类

使用Redis进行秒杀商品减库存操作，秒杀结束后异步发送MQ，使用MongoDB完成数据落地

核心逻辑

  • Redis 计数：利用 Redis 的原子性操作（如 INCR 或 DECR）来快速扣减库存，记录秒杀成功的请求。
    • 对 Redis 中的商品秒杀计数进行 +1；
    • 若计数 <= 库存，则秒杀成功；
    • 发送秒杀成功消息（包含手机号、商品ID、注释等）到绑定通道，异步落库 MongoDB（即“最终写入数据库”）。
  • MongoDB 异步持久化：将秒杀成功的订单数据异步写入 MongoDB，避免数据库操作阻塞主流程。

异步持久化流程

  • 消息队列：项目使用 Spring Cloud Stream（默认绑定 RabbitMQ 或 Kafka）作为消息中间件。StreamBridge 将订单数据（SeckillMockSaveVo）发送到消息队列的 seckillMongoSave 通道。
  • 订单服务消费：goodskill-order-provider 模块的 OrderApplication 配置了一个消息消费者，监听 seckillMongoSave 通道，接收消息后将订单数据保存到 MongoDB。

解决了秒杀中的哪些问题

  1. 高并发下的性能瓶颈
    • 问题：传统秒杀系统中，库存扣减和订单写入通常直接操作关系型数据库（如 MySQL）。在高并发场景下，数据库的锁竞争和 I/O 操作会导致性能瓶颈，甚至引发数据库宕机。
    • 解决方案：
      • Redis 计数：将库存扣减操作移到 Redis，内存操作速度远超数据库，单节点 Redis 可处理数万 QPS，极大提升了并发处理能力。
      • 异步持久化：订单写入 MongoDB 的操作通过消息队列异步执行，主流程无需等待数据库响应，响应时间从毫秒级降到微秒级。
  2. 超卖问题
    • 问题：在高并发下，多个请求可能同时读取到相同的库存值，导致库存扣减不准确，出现超卖（卖出数量超过实际库存）
    • 解决方案：
      • Redis 原子操作：使用 DECR 命令确保库存扣减是原子性的，只有当库存大于 0 时才允许扣减，彻底避免超卖。
  3. 数据库压力过大
    • 问题：秒杀场景下，短时间内大量订单写入会导致数据库压力激增，可能引发连接池耗尽或慢查询。
    • 解决方案：
      • MongoDB 异步写入：MongoDB 是一个高性能的 NoSQL 数据库，适合高吞吐写入场景。通过消息队列异步写入，订单数据逐步持久化，平滑了数据库的瞬时压力。
      • 消息队列缓冲：消息队列作为缓冲层，吸收了高并发请求的峰值流量，订单服务可以按自身节奏消费消息，避免数据库直接面对流量洪峰。

1.2 哪些是同步，哪些是异步？

系统在处理秒杀请求时，提供了两种并行的处理方式——同步通道和异步通道

  • 同步通道是指请求的处理流程是实时的、阻塞的,用户需要等待处理完成。
  • 异步通道是指请求的处理流程是非阻塞的，用户发出请求后，系统立即返回一个初步响应, 用户无需等待所有操作完成

同步通道的实现

  • SynchronizedLockStrategy：使用 Java 的 synchronized 本地锁，按商品 ID 加锁，串行处理请求。
  • AtomicUpdateStrategy：通过数据库的乐观锁（如 UPDATE … WHERE stock > 0）实现库存扣减。
  • Redisson分布式锁

异步通道的实现

  • RabbitMQStrategy：通过 RabbitMQ 消息队列异步处理秒杀请求。
  • RedisMongoReactiveStrategy：使用 Redis 计数扣减库存，通过消息队列异步写入 MongoDB

3.1 Handler 流程的执行顺序？

执行顺序：

  1. DatabasePreRequestHandler
  2. RedisPreRequestHandler
  3. StateMachinePreRequestHandler
  4. MongoPreRequestHandler
顺序 Handler 名称 主要作用
0 DatabasePreRequestHandler 重置数据库中指定秒杀商品的库存、清理成功秒杀记录
1 RedisPreRequestHandler 清空 Redis 中相关缓存、设置商品状态为“进行中”
2 StateMachinePreRequestHandler 初始化状态机，触发状态变更（重置 → 开始）
3 MongoPreRequestHandler 删除 MongoDB 中历史订单数据

3.2 在高并发下如何确保这些 Handlers 的顺序性？

  • 核心机制：顺序性由单线程调用责任链保证
  • 责任链的触发入口 PreRequestPipeline.handle() 是同步串行调用的。
  • 系统可以同时有多个请求并发进来，每个请求各自启动一条完整的预处理流程（在自己线程内），但每条链上的 handler 是顺序执行的，不会乱序或并发执行。

3.3 是否存在线程安全问题？

  • 每个 handler 类本身是单例的（@Component），但 handler 只读取配置或执行外部操作，不依赖共享可变状态，因此是线程安全的。

3.4 为什么不使用异步方式？是否可以用多线程提升性能？

预处理流程本质上是“初始化 + 校验 + 清理”的串行步骤，比如先清数据库、再清 Redis、最后初始化状态机，顺序不能乱。
如果你用异步或并行执行，反而会破坏这套语义正确性，比如：

  • Redis 还没清理就启动状态机，可能导致状态异常；
  • 数据库还没清空，Mongo 清理了也没意义；
  • 某个异常未处理会提前终止整个链条。

  • 状态可视化调试
