OGV Agent 技术亮点详解与面试复习

这份文档用于在面试前复习当前项目中三个简历亮点：

  1. Agent 长任务执行与恢复；
  2. 业务子 Agent 配置化和权限过滤；
  3. 多格式文档理解链路。

文档以当前 app/ogv-agent-gateway 代码和 Git 提交记录为依据。项目是团队共同建设的系统，文中“系统实现”不等于“个人全部负责”；面试表达应根据自己的实际提交、需求记录和代码熟悉程度，把“负责”与“参与”区分开。

1. 先建立整体认知

1.1 项目解决什么问题

OGV Agent Gateway 面向 OGV 运营场景，将自然语言请求转换为可控的业务操作。用户从 Web/H5/企微进入聊天接口，主 Agent 负责理解意图、拆解任务和选择业务域，业务 Agent 再通过 Tool/Skill 调用具体服务。

它不是单纯的 LLM 问答接口。系统还需要处理：

  • 一个请求需要多步、跨轮次执行；
  • 某些 Tool 会产生真实写副作用，不能由模型直接决定是否执行；
  • 图片生成等下游操作是异步的；
  • 用户权限会决定模型能看到哪些能力；
  • 用户上传的文件格式复杂、体积不可控，不能直接放入 Prompt；
  • 服务重启、网络超时、模型重试后仍需要恢复状态。

因此项目的核心工程问题可以概括为：

如何把模型的不确定推理，约束到一个有状态、可校验、可恢复、可审计的后端执行流程中。

1.2 三个亮点之间的关系

长任务解决“执行过程可恢复”，动态子 Agent 解决“能力如何组织和授权”，文档链路解决“非结构化输入如何安全地进入 Agent 上下文”。三者共同构成 Agent 应用的工程闭环。

1.3 面试中的项目开场

建议不要说“我做了整个 Agent 平台”。可以这样说：

我参与了 OGV 智能运营 Agent 平台建设，主要深入了三条后端链路：长任务的计划、批次执行和故障恢复；业务子 Agent 的 Paladin 配置化和权限装配；以及多格式文档的异步解析、分片读取和内嵌图片提取。我的工作重点是把模型调用接入可持久化的后端协议，而不是只封装一次模型 API。

3. 亮点一：Agent 长任务执行与恢复

3.1 背景：为什么普通 Agent 调用不够

单轮聊天通常可以采用：

但运营场景可能是：

如果只依赖模型上下文，至少会有五类问题：

  1. 请求超时后，内存中的执行位置丢失；
  2. 进程重启后，无法知道哪些对象已经完成；
  3. 模型重试可能再次调用已成功的写 Tool；
  4. 异步结果只带外部任务 ID，无法可靠关联父任务；
  5. 用户发出的“继续”无法确定对应哪一个任务。

所以需求不是“让模型多调用几次 Tool”，而是需要一套服务端任务协议。

3.2 设计目标和非目标

设计目标

  • 任务计划可持久化；
  • 批次进度可恢复；
  • 用户必须确认完整计划后才能开始受控执行；
  • 同一任务同时只有一个有效运行轮次；
  • 旧请求不能覆盖新状态；
  • 异步结果可以准确回到对应的父任务；
  • 任务可以暂停、继续、重试、取消和自动续跑；
  • 外部副作用不确定时先核对，不能盲目重试。

非目标

  • 不承诺所有下游系统都提供严格 exactly-once；
  • 不把模型输出当成可信的状态机命令；
  • 不让 Redis 单独替代业务下游的幂等能力；
  • 不把所有单轮查询都强行建成长任务。

3.3 任务数据模型：把过程变成可恢复事实

AgentTaskCheckpoint 是整个模块的核心。它不是简单的“任务是否完成”标记，而是保存了恢复所需的最小事实集。

任务归属

  • taskId：唯一任务 ID；
  • userId：防止不同用户互读或互控任务；
  • sessionId：把任务绑定到聊天会话；
  • objectiveSummary / objectiveDigest：记录用户目标和摘要指纹。

计划和步骤

  • planVersion：计划修订次数；
  • confirmedPlanVersion：用户确认过的版本；
  • planDigest：规范化计划的摘要；
  • steps：高层步骤列表；
  • currentStepNo / nextStepNo：当前和下一步；
  • planRef：复杂计划的外部引用；
  • stepCursor：步骤内部的批次位置。

运行和并发

  • runId：本次自动续跑的运行轮次；
  • runLeaseUntil：运行租约到期时间；
  • version：checkpoint 的乐观版本；
  • continuationSeq：续跑序号；
  • pendingNotificationId：待消费的续跑通知。

副作用和异步结果

  • operationId：当前受控写操作的稳定引用；
  • operationCursorDigest：操作对应批次位置的摘要；
  • operationRef：下游操作或结果核对引用；
  • asyncTaskRef：轮询 ID、外部任务 ID、父计划版本、父步骤和操作 ID；
  • asyncResultStatus：异步结果状态。

当前代码中包含以下状态：

常见状态语义：

状态 语义 允许的下一步

3.5 执行 SOP：从用户请求到任务完成

Step 1：判断是否需要长任务

由 Agent 根据任务结构判断，而不是只看对象数量。需要考虑：

  • 是否包含多个步骤；
  • 是否存在步骤依赖；
  • 是否涉及多个写操作；
  • 是否必须等待异步结果；
  • 是否可能超过单轮上下文或时间预算；
  • 是否需要自动续跑。

单次只读查询不应创建长任务，因为额外状态和通知会增加复杂度。

Step 2：创建任务

agent_task_create 调用 AgentTaskCheckpointService.createTask：

  1. 规范化用户 ID 和会话 ID；
  2. 校验目标摘要长度；
  3. 生成 UUID；
  4. 初始状态设为 PLANNING；
  5. 初始化 version=1、时间和任务截止时间；
  6. 通过 Store 写入 Redis。

此时只创建计划容器，不允许执行业务写操作。

Step 3：提交完整计划

agent_task_submit_plan 将模型生成的高层步骤交给服务端校验：

  • 计划 JSON 是否能解析；
  • 步骤编号是否正确；
  • 结构化批次模式下，所有副作用步骤是否提供 batch；
  • batch 总项数是否达到要求；
  • 计划引用是否超过大小限制。

校验成功后：

计划没有保存成功时，不应让模型继续执行，而应使用原任务 ID 和最新版本修正后重新提交。

Step 4：用户一次整体确认

agent_task_control(CONFIRM) 只允许在 AWAITING_PLAN_CONFIRMATION 状态执行，并把：

同时写入一条正常续跑通知。暂停、继续、取消和重试也通过同一个受控入口处理，避免自然语言被直接当作任意状态变更。

Step 5：开始运行轮次

续跑消费者调用 agent_task_begin_run，服务端验证：

  • 通知 ID 是否仍是该任务的 pending notification；
  • continuation kind 是否匹配；
  • 确认版本是否等于当前计划版本；
  • 任务是否已过期；
  • 当前状态是否允许运行；
  • 当前是否已有有效 run。

验证通过后创建新的 runId 和租约。通知 ID 校验可以防止旧通知重复消费。

Step 6：准备副作用操作

如果当前步骤会产生写副作用，模型必须先调用 agent_task_prepare_operation。服务端把任务、计划版本、运行 ID 和当前游标绑定成稳定操作引用，然后中间件打开执行栅栏。

执行顺序是：

LongTaskExecutionGuardMiddleware 会拒绝：

  • 还没有任务的写操作；
  • 计划尚未确认的写操作；
  • 没有当前运行轮次的业务执行；
  • 没有准备操作引用的副作用调用；
  • 与当前步骤或当前游标不匹配的调用；
  • 在核对模式下调用不安全的写 Tool。

Step 7：确定性批次执行

DeterministicBatchCoordinator 使用服务端保存的游标处理批次：

含义可以理解为第 3 步已经处理到第 5 项。每处理一项：

  1. 解析游标并校验属于当前步骤；
  2. 调用批次执行器处理单项；
  3. 校验执行器返回有效 checkpoint 版本；
  4. 更新累计进度摘要；
  5. 如果还有剩余项，保存下一个游标；
  6. 如果当前步骤完成，推进到下一高层步骤。

游标由服务端推进，而不是由模型自由生成，避免跳项、重复项和跨步骤执行。

Step 8：异步等待和自动续跑

图片生成等下游异步任务需要保存父子关系：

结果回到系统后，先验证这些引用，再决定是：

  • 记录成功结果并推进计划；
  • 继续等待；
  • 进入失败重试；
  • 进入结果核对。

如果当前轮只完成了一部分批次，系统保存进度并入队 continuation。正常流程不需要用户再次发送“继续”。

Step 9：记录结果和终态收口

agent_task_record_outcome 接受受控结果类型，服务端根据结果、当前状态、游标、运行轮次和异步引用计算下一状态。模型只能提供进展摘要和下一步建议，不能直接伪造服务端状态。

3.6 为什么不能声称 exactly-once

这是面试中很容易被追问的地方。

假设本地服务调用下游写接口：

此时本地无法仅凭超时判断副作用是否发生。如果直接重试，可能重复写入；如果永远不重试，又可能丢失业务进度。

因此当前设计是：

  • 通过 operationId、版本、运行租约和操作引用减少重复执行；
  • 无副作用失败进入 WAITING_RETRY；
  • 已发起副作用但结果未知进入 RECONCILIATION_REQUIRED 或 UNCERTAIN_SIDE_EFFECT；
  • 恢复轮次先调用只读核对 Tool，确认结果后再继续；
  • 仍然依赖下游接口的业务幂等能力，系统本身不宣称跨系统严格 exactly-once。

准确表述是“实现了可恢复的幂等控制和不确定副作用处理”，而不是“保证所有写操作只执行一次”。

3.7 Redis 和并发控制

AgentTaskCheckpointStore 不只是普通 Redis get/set：

  • 保存 checkpoint 时带 expectedVersion；
  • 通过 CAS/脚本保证读取版本和写入版本一致；
  • 版本不一致时拒绝旧请求；
  • 同时处理 runId、租约、通知和异步引用；
  • 对通知消费进行状态校验，避免重复消费；
  • 任务过期、终态保留和中间状态 TTL 分开处理。

面试时可以把它概括为：

Redis 负责跨请求、跨进程保存任务事实；Service 负责业务状态机；Store 负责原子版本更新；Middleware 负责限制 Agent 的调用顺序；Coordinator 负责确定性批次推进。

3.8 关键异常场景

场景 正确处理
计划未确认就调用写 Tool Middleware 拒绝，返回需要确认计划
两个续跑请求同时执行 expectedVersion 或 run 租约失败，只有一个轮次生效
运行租约过期且没有操作引用 进入安全重试等待
运行租约过期但已经有操作引用 进入结果核对或异步监控恢复
异步结果回到旧计划 父计划版本不匹配，拒绝覆盖当前任务
批次游标不属于当前步骤 拒绝执行，避免跨步骤或跳项
连续多轮没有进展 停止自动续跑，转为等待用户重试或中止
任务超过截止时间 进入 EXPIRED，不再自动执行
用户暂停 保存可恢复状态，清除当前 run 元数据

3.9 面试追问和回答模板

问：为什么要把计划保存下来？

答：如果每轮都让模型重新规划，步骤和批次边界可能变化，已经完成的工作可能被重复执行。保存完整计划、版本和摘要后，后续轮次按同一份事实继续；需要变更时显式生成新版本。

问：runId 和 version 有什么区别？

答：runId 表示一次执行轮次或租约，主要用来识别当前续跑是否仍属于合法运行；version 是 checkpoint 的乐观并发版本，任何状态写入都要基于预期版本，防止旧请求覆盖新状态。

问：为什么游标要由服务端维护？

答：模型适合决定意图和输出摘要，不适合成为可靠的进度数据库。服务端游标能保证批次只前进、不会越界，并且可以在重启后从 Redis 恢复。

问：任务恢复时为什么不能直接让模型看历史消息？

答：历史消息可能不完整、顺序不可靠，也不能证明某个外部副作用是否已经发生。恢复必须依据 checkpoint、版本、操作引用和异步父子关系等结构化事实。

问：为什么需要执行守卫？

答：Prompt 只能给模型行为建议，不能作为副作用安全边界。守卫在 Tool 调用层再次校验任务状态、确认状态、运行 ID、操作引用和调用模式，能把错误调用挡在业务接口之前。

4. 亮点二：业务子 Agent 配置化与权限过滤

4.1 背景：静态装配的扩展成本

早期每个业务域 Agent 由 Java 类静态定义：

这种方式的问题是：

  • 新增业务域要新增或修改 Java 类；
  • Tool、Skill、提示词和权限绑定散落在代码中；
  • 权限变更需要重新发布；
  • 业务域配置容易误引用系统能力；
  • AgentFactory 需要维护越来越多静态域列表。

因此需求不是“把 Java 类换成 JSON”这么简单，而是要把业务差异配置化，同时保证配置不会突破系统能力边界。

4.2 目标和边界

适合配置化的内容

  • 业务域是否启用；
  • agentCode 和描述；
  • 子 Agent system prompt；
  • 可使用的 Tool；
  • 可使用的 Skill；
  • 每项能力所需的 permission codes。

不允许配置化绕过的内容

  • 主 Agent 的固定路由规则；
  • 公共域系统级长任务 Tool；
  • SYSTEM Tool/Skill 的访问边界；
  • Spring Bean 的实际实现和下游调用逻辑；
  • 用户基础权限本身。

  3. 原始 JSON 变化时先解析，不直接修改当前线上快照；
  4. Parser 完整校验所有域和能力；
  5. 校验通过后生成不可变 ConfiguredDomain；
  6. 更新配置版本并使受影响的 Agent 缓存失效；
  7. 新请求使用新快照组装 Agent；
  8. 解析失败时保留旧快照，避免一份坏配置破坏全部路由。

4.5 能力目录：为什么不直接用 Bean 名

AgentCapabilityCatalog 建立两张索引：

使用稳定的 capabilityId 有三个好处：

  • Paladin 配置不依赖 Spring Bean 名或实现类名；
  • 业务配置契约与 Java 重构解耦；
  • 可以在启动和刷新时校验“一种实现只能对应一个能力 ID”。

Tool 还会检查是否声明有效的 @Tool 方法；Skill 会检查 classpath 资源、运行时 Skill 实现和 action 名称。

4.6 配置校验的实际内容

Parser 会检查：

  • domains 必须是数组，域数量不能超过上限；
  • enabled 必须明确；
  • agentCode 符合格式，不能使用主 Agent 或公共域保留值；
  • description 和 systemPrompt 不能为空且不能超长；
  • Tool/Skill 数组必须存在，不能同时为空；
  • capabilityId 必须已经注册；
  • USER 能力必须有非空权限码；
  • 权限码要符合格式和长度限制；
  • 同一个域不能重复绑定同一 Tool/Skill；
  • 同域能力名称不能冲突；
  • 业务域不能引用 SYSTEM Tool/Skill；
  • Skill 资源目录必须可以读取。

这些校验把“配置错误”尽量提前到刷新时，而不是等用户发起请求、模型尝试调用时才暴露。

4.7 USER 与 SYSTEM 能力隔离

CapabilityVisibility 目前分为：

  • USER：普通业务能力，必须绑定权限码；
  • SYSTEM：系统级辅助能力，不依赖用户权限，不允许业务配置任意引用。

例如公共域中的长任务 checkpoint、临时状态、通知能力属于系统协议的一部分，不能因为某个业务域配置了一个 capabilityId 就直接暴露出去。

这是一种“装配期隔离”，不是仅靠 prompt 告诉模型“不要调用”。

4.9 缓存和热更新

动态配置和权限过滤都涉及 Agent 实例缓存。缓存不能只按用户 ID，因为同一用户的权限集合可能变化；也不能只按配置版本，因为不同用户看到的能力不同。

当前思路是组合：

变更处理：

  • 用户权限变化：产生新的权限指纹，不复用旧 Agent；
  • Paladin 配置变化：替换配置快照，清理相关 supervisor cache；
  • 当前执行中的任务：继续以已确认的计划和 checkpoint 为事实，不在执行中途偷偷替换任务计划。

4.10 动态配置面试问答

问：为什么不让模型直接选择所有 Tool？

答：模型可见能力本身就是安全边界。把无权 Tool 注册给模型，再靠 prompt 约束，会扩大误调用和越权风险。系统在 Agent 组装阶段按用户权限裁剪 Toolkit。

问：配置热更新失败怎么办？

答：先在独立对象中完整解析和校验，只有全部成功才替换不可变快照；失败时保留旧配置并记录错误，避免半套配置进入运行时。

问：为什么业务域不能引用 SYSTEM Tool？

答：SYSTEM Tool 承担任务协议、状态和通知等平台控制能力，开放给业务域会让业务配置绕过平台安全规则。通过 CapabilityVisibility 和 AgentCapabilityCatalog 在配置解析阶段拒绝引用。

问：新增一个业务域是不是完全不需要发版？

答：如果能力实现已经作为 Tool/Skill Bean 注册，新增业务域主要可以通过配置完成；如果是全新业务能力，仍然需要开发、测试和发布新的 Tool/Skill 实现。

5. 亮点三：多格式文档理解链路

5.1 背景：从“上传文件”到“可被 Agent 使用”

文档能力不是把 MultipartFile 接收成功就结束了。Agent 需要知道：

  • 文件是什么类型；
  • 有哪些 Sheet、页、段落或结构；
  • 读取哪一部分最相关；
  • 是否存在可展示的内嵌图片；
  • 文件和解析结果是否仍属于当前用户、是否已经过期。

如果把全文直接拼进 Prompt，会遇到上下文过长、成本高、内容无法定位和图片丢失等问题。因此系统采用：

让 Agent 先看结构，再按需读取局部内容。

5.2 文件类型和统一 Parser

统一接口 DocumentParser 将格式差异隔离在解析器内部。当前代码覆盖：

  • XLSX；
  • CSV；
  • DOCX；
  • PDF；
  • PPTX；
  • TXT；
  • JSON。

解析器不直接返回一个无限长字符串，而是向回调写入 (sheetNo, partNo, value) 分片，并最终生成 Manifest。

这样扩展新格式时，主要工作是：

  1. 增加 DocumentMeta.FileType；
  2. 实现 DocumentParser；
  3. 注册为 Spring Bean；
  4. 增加必要的图片提取和安全限制；
  5. 补充 Tool 和测试。

5.3 上传与异步解析 SOP

Step 1：上传鉴权

DocumentUploadAccessFilter 先校验上传身份和请求条件。DocumentController.upload 只接受已验证的用户名，成功后调用 DocumentService.upload。

Step 2：快速返回元数据

上传接口返回 HTTP 202 和：

  • fileId；
  • 原文件名；
  • 文件类型；
  • 当前状态；
  • 过期时间。

它不等待完整解析完成，避免大文件阻塞聊天请求。

Step 3：异步执行

DocumentParseService.submit 将临时路径加入 activePaths，提交到专用 documentParseExecutor。解析期间通过状态元数据更新进度。

Step 4：预扫描 OOXML

XLSX、DOCX、PPTX 等文件本质上是 ZIP 包。解析前先扫描条目数、解压体积、图片大小和压缩率，提前拒绝危险文件。

Step 5：上传 BFS

原文件先上传 BFS，Manifest 保存可访问的下载 URL。这样后续用户或 Agent 可以获得原文件引用，同时解析数据与原文件生命周期分开管理。

Step 6：提取图片

  • PDF 使用 PdfEmbeddedImageExtractor；
  • Office 使用 OfficeEmbeddedImageExtractor；
  • 每张图片生成可引用的 image ID 和元信息。

Step 7：写入分片和 Manifest

解析器输出内容分片，DocumentRedisStore 写入 Redis。所有分片成功后写 Manifest，最后才把文档状态发布为 READY。

这个顺序保证了：Agent 看到 READY 时，Manifest 和正文分片已经完整可读。

5.4 Manifest 为什么重要

Manifest 是 Agent 与文档存储之间的稳定契约，至少需要描述：

  • schema version；
  • 文件 ID、文件类型和文件名；
  • Sheet、页、段落或内容块结构；
  • 分片编号和顺序；
  • 图片 ID、格式和引用位置；
  • 原文件下载 URL。

它解决了三个问题：

  1. Agent 不需要猜测文件内部结构；
  2. document_read 可以按 part 或 sheet 精确读取；
  3. 文档格式解析与 Agent Tool 参数解耦。

5.5 Agent 读取 SOP

约束重点：

  • fileId 必须使用临时引用中的 UUID，不能由模型根据文件名自行拼接；
  • XLSX/CSV 必须指定 sheetNo；
  • 读取正文前先 inspect；
  • 不需要图片时不自动加载所有图片；
  • 用户要求展示图片时原样返回工具 URL；
  • 文档全文不能写入 Agent 临时状态或长期记忆。

5.6 Redis 分片和生命周期

如果把所有解析结果放在一个 Redis value 中，会遇到单值过大、局部读取浪费和失败清理困难等问题。因此使用：

分别写入 Redis，并根据用户名和 fileId 生成精确 key。

生命周期包括：

  • 解析中：临时状态和进度；
  • READY：Manifest、分片和原文件引用；
  • FAILED：保留短时间错误状态，方便前端诊断；
  • EXPIRED：删除或自然过期；
  • 本地临时文件：解析完成或失败后删除，定时任务清理遗留文件。

5.7 文件安全限制

当前 DocumentParseService 对不可信文件进行多层限制：

限制 防护目标
ZIP 条目数 防止大量小文件耗尽解析资源
ZIP 总解压字节数 防止压缩包展开过大
XML 单条目大小 防止单个 XML 膨胀
shared strings/styles 大小 针对 Excel/Office 的高风险结构限流
压缩率 防止 ZIP Bomb
单图和总图片大小 防止图片资源耗尽
图片数量 防止大量嵌入资源
Redis 单文件写入量 防止临时存储被单文件占满
Manifest 字节数 防止结构元数据过大
解析超时和任务截止时间 防止后台任务无限运行
临时文件保留时间 防止本地磁盘泄漏

失败处理不是简单返回异常：解析失败时删除已写分片，写入失败状态和 failure code，并缩短失败状态 TTL。

5.8 为什么先上传 BFS 再写 READY

BFS 原文件 URL 和 Redis 解析结果都属于文档可用条件的一部分。如果先把状态标记为 READY，再异步上传或写分片，Agent 可能读取到不完整数据。

5.9 文档模块面试问答

问：为什么不把文件直接传给大模型？

答：不同模型和接口对文件类型支持不一致，全文也可能超过上下文窗口。系统先解析成 Manifest 和分片，Agent 先看结构，再按需读取相关内容，成本、延迟和可控性更好。

问：为什么解析要异步？

答：Office/PDF 解析、图片提取和 BFS 上传可能较慢。上传接口只返回 fileId 和状态，后台线程负责解析，前端通过 status 接口查询，避免占用聊天请求。

问：如何判断一个文档已经可以读取？

答：只有 Manifest、内容分片和必要的原文件引用都成功写入后，才通过 publishReady 把状态改成 READY。失败时删除已写 key，避免暴露半成品。

问：为什么要限制压缩率？

答：Office 文件是 ZIP 容器，攻击者可以构造极高压缩比的文件。只限制上传体积不够，还要限制展开后的体积、条目数和压缩率，避免解析时占满内存、CPU 或磁盘。

问：为什么图片单独抽取？

答：纯文本解析会丢失图表、封面和嵌入图片。Manifest 保存 imageId，Agent 只有在问题需要时读取指定图片，既保留视觉内容又避免无关图片进入上下文。

6. 三个亮点的共同工程方法

6.1 让模型决定“意图”，让服务端决定“事实”

适合交给模型：

  • 用户意图识别；
  • 业务域选择；
  • 高层计划草案；
  • 进展摘要；
  • 对文档内容的自然语言分析。

必须由服务端决定：

  • taskId、fileId、operationId；
  • planVersion、checkpoint version；
  • 当前状态是否合法；
  • 游标是否越界；
  • 用户是否有权限；
  • 文件是否超限；
  • 异步结果属于哪个父任务；
  • 是否允许真正调用写 Tool。

这是整个项目最值得提炼的设计原则。

6.2 把不可信输入变成结构化边界

项目中有三种不可信输入：

  1. 模型生成的 Tool 参数和计划；
  2. Paladin 动态配置；
  3. 用户上传的文件和文档引用。

对应策略：

输入 结构化边界
模型计划 JSON、步骤、计划摘要、状态机和版本校验
模型 Tool 调用 Middleware、权限 Tool 装配、操作引用
Paladin 配置 Parser、格式限制、能力目录、SYSTEM 隔离
上传文件 文件类型、ZIP 扫描、大小限制、超时和 TTL
文档引用 用户绑定的 fileId、Manifest、part/imageId

6.3 先定义失败语义，再定义 happy path

面试时可以说明自己的设计习惯：

我不会只按正常路径把模型调用串起来，而是先问每一步失败后能否安全重试、是否已经产生副作用、状态是否需要恢复、数据多久过期。然后再决定需要哪些字段、版本和状态。

这也是为什么长任务中有 RECONCILIATION_REQUIRED，文档解析有失败清理和短 TTL，动态配置有旧快照保留。
