OGV Agent 项目面试复盘 SOP

适用范围：2026.07-2026.09 在 ogv-agent-gateway 上的工作复盘。

使用方式：面试前先看“项目总览”和“个人贡献边界”，再按目标岗位选择长任务、动态子 Agent、文档理解三个模块深入复习。文档中的类名、状态和提交号来自当前仓库代码；个人负责程度应以自己的实际提交和工作记录为准。

1. 一分钟项目介绍

1.1 项目定位

OGV Agent Gateway 是面向 OGV 运营人员的自然语言操作平台。用户通过对话提出查询或操作需求，主 Agent 负责意图识别、任务拆解和业务域路由，业务 Agent 通过 Tool/Skill 调用下游服务。系统同时提供会话持久化、权限过滤、文档理解、图片任务和长任务恢复能力。

1.2 个人工作口径

推荐使用下面这段开场，不要把团队平台说成个人独立完成：

我参与了 OGV 智能运营 Agent 平台建设，主要负责三条工程链路：一是把多步骤 Agent 请求做成长任务，支持计划确认、分批执行、状态持久化和异常恢复；二是参与把业务子 Agent 从代码静态注册改成 Paladin 配置化生成，并接入权限过滤；三是建设多格式文档上传、异步解析、分片读取和内嵌图片提取链路。我的重点不是单纯写一个模型调用，而是把模型的不确定输出约束到可恢复、可校验的后端流程里。

1.3 技术栈

Java、Spring Boot、AgentScope、DashScope、Redis/Redisson、Reactor/SSE、Paladin、BFS、PDFBox、EasyExcel、Commons CSV。

2. 需求演进时间线

提交历史显示，这不是一次性开发，而是先建立最小闭环，再围绕状态不一致、恢复失败、配置扩展和文件格式逐步收敛。

2.1 如何解释“为什么提交记录很多”

可以这样回答：

Agent 任务的难点不在第一次调用成功，而在中断、重试、异步等待和用户控制下仍保持状态一致。开发过程中先实现主流程，再通过提交逐个修复恢复规划、批次游标、通知重复消费、确认收口和失败分类等边界问题，因此提交记录体现的是状态机逐步收敛，而不是重复改同一处代码。

3. 总体架构和请求链路

4. 模块一：Agent 长任务执行与恢复

4.1 需求背景

普通聊天请求适合“一问一答”，但运营任务可能包含多个步骤、多个对象、异步图片生成或需要用户确认的写操作。如果把所有工作放在一次 Agent 调用中，会出现：

  • 上下文或请求超时，任务只完成一部分；
  • 模型重复调用同一个写 Tool；
  • 进程重启后不知道执行到哪一步；
  • 异步任务返回时无法判断属于哪个父任务；
  • 用户只能反复输入“继续”，系统无法自动推进；
  • 计划未确认时就开始产生副作用。

目标是把 Agent 的自由形式推理约束为服务端可持久化、可校验、可恢复的任务协议。

4.2 方案总览

核心对象是 AgentTaskCheckpoint，由 AgentTaskCheckpointService 管理，并通过 AgentTaskCheckpointStore 写入 Redis。

任务至少包含以下信息：

  • taskId、userId、sessionId：任务归属；
  • status：当前生命周期状态；
  • planVersion、confirmedPlanVersion、planDigest：计划版本和内容指纹；
  • steps、currentStepNo、nextStepNo：高层步骤；
  • stepCursor：当前批次游标；
  • runId、runLeaseUntil：当前执行轮次和租约；
  • operationId、operationCursorDigest：当前写操作的稳定标识；
  • asyncTaskRef：外部异步任务与父计划的绑定；
  • version：乐观并发版本；
  • pendingNotificationId、continuationSeq：自动续跑通知；
  • lastFailureType、resumeStatus：失败分类和恢复状态。

代码中的状态包括：PLANNING、AWAITING_PLAN_CONFIRMATION、RUNNING、WAITING_CONTINUATION、WAITING_ASYNC_RESULT、WAITING_RETRY、RECONCILIATION_REQUIRED、PAUSED、COMPLETED、FAILED、CANCELLED、EXPIRED。

4.3 标准执行 SOP

Step 1：判断是否需要长任务

判断依据不是“对象数量大于某个阈值”或用户是否说了“批量”，而是综合：

  • 是否有多个高层步骤；
  • 是否存在步骤依赖；
  • 是否需要等待异步结果；
  • 是否会执行多个写操作；
  • 单轮请求是否有足够预算完成；
  • 是否需要服务端自动续跑。

若只是单次、无副作用、单轮可完成的查询，不应为了形式创建长任务。

Step 2：创建任务

通过 agent_task_create 创建任务，保存目标摘要和会话归属。此时仍不能执行写操作。

Step 3：提交完整计划

通过 agent_task_submit_plan 保存完整高层步骤、计划引用和必要批次游标，服务端生成或校验计划版本和摘要。

关键原则：

  • 计划必须覆盖全部剩余工作，而不是只保存当前一批；
  • 批次游标由服务端维护，模型不能随意跳过或回退；
  • 计划提交后进入 AWAITING_PLAN_CONFIRMATION；
  • 没有持久化计划，不允许开始业务执行。

Step 4：等待一次整体确认

用户确认后调用 agent_task_control(CONFIRM)。系统校验任务 ID、会话、版本和当前状态，然后把任务推进到可运行状态。

暂停、继续、停止、重试也统一通过受控命令处理，避免把自然语言直接映射为任意状态变更。

Step 5：开始唯一运行轮次

通过 agent_task_begin_run 创建当前 runId 和运行租约。一次任务在同一时刻只能有一个有效运行轮次，避免重复续跑或并发轮次同时消费同一游标。

Step 6：执行批次

DeterministicBatchCoordinator 根据当前步骤和 stepCursor 读取待处理项：

  1. 校验游标属于当前步骤且没有越界；
  2. 执行单个批次项；
  3. 获取执行结果和最新 checkpoint 版本；
  4. 更新已完成数量与进度摘要；
  5. 写回下一个游标；
  6. 发生失败时停止当前批次，进入可重试或需核对状态。

独立只读查询可以在运行时允许并行；图片提交、结果绑定、写操作和任务状态写入必须按协议串行。

Step 7：等待异步结果或安排续跑

如果当前步骤依赖图片等外部异步结果，则保存：

  • 外部任务 ID；
  • 轮询 ID；
  • 父计划版本；
  • 父步骤编号；
  • 对应操作 ID 和游标摘要。

结果到达后先核对父任务和操作引用，不能只根据一个外部 sessionId 推断归属。当前批次完成但仍有剩余时，写入 pendingNotificationId 并安排下一轮，不要求用户正常回复“继续”。

Step 8：记录结果并收口

通过 agent_task_record_outcome 记录 STEP_COMPLETED、RETRYABLE_FAILURE、UNCERTAIN_SIDE_EFFECT、TASK_COMPLETED 等受控结果类型。服务端根据真实状态计算下一状态，而不是完全信任模型传入的状态。

4.4 幂等和副作用不确定性

面试中不要说“外部写操作严格 exactly-once”。更准确的表述是：

系统通过计划版本、运行租约、稳定操作 ID、游标摘要和结果记录降低重复执行概率；如果请求超时发生在外部系统已接受但本地未收到响应的窗口，系统不能凭空证明外部副作用是否发生，因此会进入 RECONCILIATION_REQUIRED 或 UNCERTAIN_SIDE_EFFECT，优先核对已有结果，而不是直接盲目重试。

准备操作的流程是：

  1. agent_task_prepare_operation 生成当前计划步骤下的稳定操作引用；
  2. 执行 Tool；
  3. 根据是否已经发起副作用分类失败；
  4. 无副作用失败可以安全重试；
  5. 副作用不确定时保留操作引用，进入核对或人工确认；
  6. 成功或失败结果写入 checkpoint。

4.5 为什么使用版本号

expectedVersion 用于乐观并发控制。Agent 读取任务后，只有在版本仍然匹配时才能提交计划、开始运行、准备操作或记录结果。这样可以拒绝：

  • 过期的旧轮次继续写状态；
  • 两个续跑请求同时推进同一个游标；
  • 用户在任务已经暂停或完成后重复提交旧命令；
  • 异步回调覆盖更新后的任务状态。

4.6 关键代码证据

  • AgentTaskCheckpointService：任务生命周期、计划、运行轮次、操作引用、异步绑定和续跑。
  • AgentTaskCheckpointStore：checkpoint 和通知的 Redis 持久化。
  • AgentTaskCheckpointTool：暴露创建、读取、提交计划、控制、开始运行、准备操作和记录结果等 Tool。
  • LongTaskExecutionGuardMiddleware：限制不安全的任务调用，注入当前任务上下文。
  • DeterministicBatchCoordinator：服务端掌控批次游标和确定性批量执行。
  • AgentTaskCheckpoint.Status：任务状态枚举。
  • LongRunningTaskWorkflowSkill：给 Agent 的长任务协议说明。

4.7 长任务面试问答

问：为什么不能直接让模型循环调用 Tool？

答：模型循环没有可靠的持久状态、版本校验和失败恢复语义。请求超时或进程重启后，模型不知道哪些步骤已经完成，也无法安全判断外部副作用是否发生。服务端 checkpoint 把计划、游标和结果变成可验证的状态机。

问：如何避免重复执行？

答：在写操作前生成与任务、计划版本、步骤和批次游标绑定的稳定操作引用；执行后记录结果。并通过 expectedVersion、runId 和执行守卫拒绝旧轮次或未授权状态的调用。对于外部结果不确定的情况不直接重试，而是进入核对状态。这里是“降低重复执行并支持恢复”，不是承诺所有下游都严格 exactly-once。

问：为什么要保存完整计划，而不是每轮现生成？

答：每轮重新规划可能改变目标、步骤顺序或批次边界，导致已经完成的工作被重复处理。完整计划和 planVersion 让后续轮次有稳定依据；需要变更时显式进入计划修订，而不是隐式覆盖。

问：服务重启后如何恢复？

答：Redis 保存任务 checkpoint 和待处理通知。服务恢复后根据任务状态、运行租约、父任务引用和未消费通知重新建立续跑或异步监控；恢复时会先校验版本和归属，不直接从模型上下文猜测进度。

问：失败为什么分成可重试和不确定副作用？

答：网络超时可能发生在下游执行前，也可能发生在下游执行后。前者可以重试，后者重试可能造成重复写入。系统因此区分 RETRYABLE_FAILURE 和 UNCERTAIN_SIDE_EFFECT，后者优先核对结果。

5. 模块二：业务子 Agent 配置化与权限控制

5.1 需求背景

早期业务域 Agent 由 Java 类静态装配。新增一个业务域通常需要新增或修改 Agent 类、绑定 Tool、配置提示词和权限码，扩展成本高，也容易把系统级能力暴露给业务域。

需求是把业务域差异放入 Paladin 配置，同时保留公共域长任务、状态读写等系统能力的代码控制和安全边界。

5.2 改造前后

ActivityDomainAgent、DeliveryDomainAgent、AiCreatorIncentiveDomainAgent 仍保留作历史装配定义，但当前代码已标记为 deprecated；公共域 CommonDomainAgent 仍固定注册，因为它承载系统级能力。

5.3 配置模型

配置键为 ogv_agent_business_domain_config，结构核心如下：

实际字段模型见 BusinessDomainAgentConfig。agentCode 会派生委托 Tool 名，例如 delivery-domain-agent 对应 delegate_to_delivery_domain。

5.4 配置加载 SOP

  1. AgentFactory 启动时读取配置源，初始化空或当前配置快照。
  2. 注册 Paladin 配置监听器，配置变更时获取原始 JSON。
  3. DomainAgentConfigParser 解析 JSON，拒绝空配置和非法结构。
  4. AgentCapabilityCatalog 根据稳定 capabilityId 找到 Spring Bean。
  5. 校验 Agent code、委托 Tool 名、Tool/Skill 重复、能力名冲突和资源可读性。
  6. 禁止业务域引用 CapabilityVisibility.SYSTEM 的 Tool/Skill。
  7. 为每个配置域构建不可变的 ConfiguredDomain。
  8. 生成新的配置快照，清理受影响的 Agent 缓存。
  9. 下一次请求按用户权限和新快照组装 supervisor Agent。

5.5 校验重点

解析器不是简单反序列化，而是配置边界的第一道防线：

  • 业务域数量不超过上限；
  • agentCode 必须符合约定格式，且不能使用主 Agent/公共域保留值；
  • description、systemPrompt、permissionCode 有长度限制；
  • Tool 和 Skill 必须是已注册能力；
  • 一个业务域内不能重复绑定同一 Tool/Skill；
  • Tool 必须声明有效 @Tool 方法；
  • Skill 必须存在 classpath 资源或实现运行时 Skill；
  • 同一业务域内 Tool 名、Skill ID 和 Action 名不能冲突；
  • 业务域不能引用系统级 Tool/Skill；
  • 每个 USER 能力必须声明权限码。

5.6 权限装配逻辑

权限有两层：

  1. 用户基础权限：UserPermissionService.resolve(userId) 根据 Paladin 用户权限配置得到权限集合。
  2. 请求权限范围：resolve(userId, permissionScope) 只保留基础权限中出现的 scope，不能通过请求参数增加权限。

能力装配时，只有用户拥有 Tool/Skill 绑定的任一权限码，能力才会注册到该用户的 Agent。SYSTEM 能力不依赖用户权限，但只允许系统内部按规则使用，不能由业务配置任意引用。

5.7 缓存和热更新

AgentFactory 使用用户权限指纹和业务域配置快照生成缓存键：

  • 权限集合变化时，新的权限指纹不会复用旧 Agent；
  • Paladin 配置变更时，更新配置版本并清理相关 supervisor 缓存；
  • 避免每个请求都重复解析配置和扫描 Tool；
  • 同时避免权限变更后继续使用旧能力集合。

5.8 动态配置面试问答

问：为什么要配置化，而不是继续新增 Java Agent 类？

答：业务域的差异主要是提示词、能力集合和权限映射，静态类会让每个业务域都产生重复装配代码。配置化后新增业务域只需要增加配置，AgentFactory 和能力实现保持不变，接入成本更低，也便于权限和能力统一校验。

问：如何防止配置把系统能力暴露出去？

答：Tool/Skill 在注册时区分 USER 和 SYSTEM 可见性。解析业务域配置时通过 AgentCapabilityCatalog.isSystemTool/isSystemSkill 拒绝 SYSTEM 能力；系统级能力只由固定的 CommonDomainAgent 装配，并由中间件和提示词约束使用场景。

问：配置热更新有什么风险？

答：主要风险是新旧 Agent 快照混用、缓存不失效和正在执行的任务能力集合变化。实现上先完整解析校验，再替换不可变配置快照；Agent 缓存按配置版本隔离，正在运行的长任务仍以已持久化的计划和任务上下文为准，而不是中途从模型重新猜测。

问：permissionScope 会不会造成越权？

答：不会。它是基础权限的交集过滤器，只能减少权限；不在用户基础权限中的 scope 会被过滤掉。

6. 模块三：多格式文档理解链路

6.1 需求背景

用户希望直接把 Excel、Word、PDF 等运营材料交给 Agent 进行查询、总结和分析。直接把原文件或全文放进 Prompt 会遇到：

  • 不同格式解析方式不同；
  • 大文档超出模型上下文；
  • Office/PDF 中的表格和图片不能只按纯文本处理；
  • 同步解析阻塞聊天请求；
  • 临时文件和 Redis 数据没有生命周期控制；
  • 恶意压缩包或超大文件可能耗尽资源。

6.2 端到端流程

6.3 解析器设计

DocumentParser 定义统一解析接口，当前覆盖：

  • XlsxDocumentParser
  • CsvDocumentParser
  • DocxDocumentParser
  • PdfDocumentParser
  • PptxDocumentParser
  • TextDocumentParser
  • JsonDocumentParser

解析结果不是简单拼成一个大字符串，而是写成带 schema/version、文件类型、页/Sheet 信息、分片索引和图片引用的 DocumentManifest。DocumentPartAccumulator 和 DocumentPartCodec 负责分片累积与编码。

6.4 异步和存储策略

  • 上传接口快速返回文件 ID 和解析状态，解析由独立 documentParseExecutor 执行；
  • 原文件和可访问图片上传 BFS，便于后续引用和展示；
  • Manifest、元数据和正文分片写 Redis；
  • document_inspect 先返回结构，Agent 再按需调用 document_read；
  • XLSX/CSV 必须指定 sheetNo，其他格式按文档类型读取；
  • 通过文件 ID、用户名和分片编号构造 Redis key，避免不同用户或不同文件串数据；
  • 解析成功、失败、过期分别使用不同 TTL；
  • 临时本地文件由定时任务清理，解析中的文件通过 activePaths 防止被误删。

6.5 内嵌图片处理

Office 文件通过 ZIP 内部媒体资源提取图片，PDF 通过 PDFBox 提取嵌入图片。Manifest 保存图片的 imageId、类型和引用关系，Agent 只有在用户问题确实需要图片时才调用 document_image_read，避免把无关图片全部加载进上下文。

6.6 安全和资源上限

当前代码对不可信文件设置了多层限制：

  • ZIP 条目数量；
  • ZIP 总解压体积；
  • XML 单条目大小；
  • shared strings 和 styles 大小；
  • 压缩率，防止 ZIP Bomb；
  • 单文件 Redis 写入量；
  • Manifest 最大字节数；
  • 单文件图片数量；
  • 单图和总图片大小；
  • 解析超时和任务截止时间；
  • 临时文件保留时长；
  • 失败状态较短 TTL，避免错误数据长期占用。

6.7 文档模块面试问答

问：为什么要异步解析？

答：文件解析、BFS 上传和图片提取可能耗时较长，不能占住聊天请求线程。异步解析让上传接口先返回 fileId，前端通过状态接口查看进度，Agent 只在解析完成后读取内容。

问：为什么先 inspect 再 read？

答：先获取结构可以让 Agent 知道文件有哪些 Sheet、页、分片和图片，再按问题读取局部内容，减少上下文和 Redis 读取量，也避免模型盲目使用错误的 sheet 或 part 编号。

问：为什么不把全文一次性交给模型？

答：长文档会超出上下文窗口，成本和延迟也更高。Manifest + 分片读取让模型只获得当前问题需要的内容，并能对表格、页码和图片进行定向访问。

问：如何防止恶意文档？

答：对 OOXML ZIP 先检查条目数、总解压体积和压缩率，再限制 XML、图片、Manifest 和 Redis 数据量，同时设置解析截止时间和临时文件清理。这样即使文件格式合法，也不能无限制消耗服务资源。

问：文档 ID 如何防止被伪造？

答：Tool 使用上下文中的临时文档引用，要求 fileId 逐字使用引用中的 UUID；不能用文件名、路径或 URL 自行拼接 ID。读取服务还会按用户和文件状态校验，错误 ID 与过期 ID 分开处理。

7. 三个模块的通用开发 SOP

7.1 需求澄清

每接到一个 Agent 能力需求，先问清楚：

  1. 是查询还是写操作？是否有外部副作用？
  2. 一轮请求能否完成？是否需要等待异步结果？
  3. 是否需要用户确认？确认粒度是单次 Tool 还是完整计划？
  4. 任务中断后需要恢复到哪一层：任务、步骤、批次还是单项操作？
  5. 是否需要跨请求、跨进程或跨实例共享状态？
  6. 哪些能力属于用户域，哪些属于 SYSTEM 能力？
  7. 输入文件是否不可信？大小、格式、生命周期和访问边界是什么？

7.2 方案设计

  • 先画状态和数据流，再决定 Tool/Service/Store 的职责；
  • 让模型负责意图和摘要，让服务端负责 ID、版本、游标、状态转换和资源限制；
  • 对可重试、不可重试和副作用不确定分别建模；
  • 把外部系统返回的任务 ID 与本地父任务绑定；
  • 用稳定能力 ID 做动态配置，不把 Spring Bean 名直接暴露成业务配置契约；
  • 所有临时数据写入前定义 TTL 和清理路径；
  • 用失败场景反推接口，而不是只从 happy path 设计。

7.3 实现顺序

  1. 定义领域对象和状态枚举。
  2. 实现 Store 和基本读写。
  3. 实现 Service 的状态转换和版本校验。
  4. 用 Tool 暴露最小动作。
  5. 在 Middleware/Coordinator 中限制模型调用顺序。
  6. 接入通知、异步任务或文件解析器。
  7. 补充 UI/SSE 展示和错误映射。
  8. 用单测覆盖状态边界、配置非法输入、文件限制和 Tool 参数。

7.4 验证清单

长任务

  • 任务创建后未提交计划，写 Tool 是否被拒绝？
  • 未确认计划时，是否不会开始批量副作用？
  • 同一 expectedVersion 重复提交是否被拒绝？
  • 暂停、继续、停止、重试后的状态是否正确？
  • 游标是否只能前进且不能跨步骤？
  • 当前轮执行一部分后进程重启，能否恢复剩余项？
  • 外部异步结果回调到达时，是否校验父任务和操作引用？
  • 失败发生在副作用前后时，是否进入不同处理路径？

动态 Agent

  • 非法 JSON、重复 Agent code、重复 Tool 名是否启动失败或拒绝刷新？
  • 未注册 capabilityId 是否不能生成 Agent？
  • 业务域引用 SYSTEM Tool/Skill 是否被拒绝？
  • 用户没有权限时，模型是否看不到对应 Tool？
  • permissionScope 是否只能收窄权限？
  • 配置热更新后，旧 Agent 缓存是否失效？

文档

  • 7 种格式是否都能生成 Manifest？
  • XLSX/CSV 的 sheet 参数错误是否可解释？
  • 先 inspect 后 read 的调用顺序是否明确？
  • 超大 ZIP、异常压缩率和过多图片是否被拒绝？
  • 解析失败数据是否会过期清理？
  • Office/PDF 内嵌图片是否能通过 imageId 定向读取？
  • 用户 A 是否不能读取用户 B 的 fileId？

8. 如何把贡献说准确

8.1 可以说的事实

  • “我负责/参与了长任务 checkpoint、计划和批次恢复链路。”
  • “我实现了计划版本、运行轮次、操作引用和结果记录等状态字段或相关逻辑。”
  • “我参与了 Paladin 业务域配置解析、能力目录和权限装配。”
  • “我负责了文档异步解析、分片存储、内嵌图片或安全上限中的具体部分。”
  • “我通过提交记录验证了从基础能力到边界修复的演进过程。”

8.2 不建议直接说

  • “我独立设计并完成了整个 OGV Agent 平台。”
  • “所有写操作都是 exactly-once。”
  • “所有业务域 Tool 都已经接入真实系统。”
  • “动态配置完全不需要代码发布。”能力实现新增仍然需要开发和发布，配置化主要减少业务域装配代码。
  • “文档解析把全文永久存储在 Redis。”当前是临时数据和 TTL 管理。

8.3 个人贡献核对表

面试前把下面每项标成“独立负责 / 主要参与 / 了解”：

  • AgentTaskCheckpointService 的状态转换；
  • AgentTaskCheckpointStore 的 Redis key、TTL 或 CAS/版本逻辑；
  • LongTaskExecutionGuardMiddleware 的调用约束；
  • DeterministicBatchCoordinator 的游标和批次执行；
  • Paladin 配置模型和 DomainAgentConfigParser；
  • AgentCapabilityCatalog 和 Tool/Skill ID 映射；
  • 用户权限与 permissionScope；
  • DocumentService 上传和状态接口；
  • DocumentParseService 异步调度和资源限制；
  • 具体格式解析器、图片提取器或 Redis 分片存储；
  • 测试、预发验证、日志和故障排查。

如果只是阅读或配合，不要使用“负责设计”；改成“参与实现”“参与联调”或“熟悉其调用链路”。

9. 面试前 30 分钟复习顺序

0-5 分钟：复述项目

说清楚用户、主 Agent、业务域 Agent、Tool/Skill 和三条个人工作线。

5-15 分钟：画长任务状态流

至少能手动画出：

并能解释 expectedVersion、runId、stepCursor、operationId 的作用。

15-20 分钟：讲动态配置

从静态 Java Agent 类讲到 Paladin JSON，再讲解析校验、SYSTEM 隔离、用户权限过滤和缓存刷新。

20-25 分钟：讲文档链路

从上传、异步解析、Manifest、分片、BFS、图片提取到 inspect/read/image_read，并说明为什么要做资源限制。

25-30 分钟：准备一个失败案例

优先准备下面三个之一：

  1. 为什么计划必须持久化，如何修复恢复时重复规划；
  2. 外部写操作超时后为什么不能盲目重试；
  3. 文档解析为什么要从 Excel/Word 扩展成统一 Parser 和 Manifest。

回答结构统一使用：现象 → 原因 → 方案 → 边界 → 验证。
