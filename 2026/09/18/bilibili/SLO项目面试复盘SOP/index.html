SLO 异常自动化诊断项目面试复盘手册

使用目的

这份手册用于面试前恢复项目上下文，并帮助我在面试中完整回答四类问题：为什么做、怎么设计、难点在哪里、结果与不足是什么。内容根据原始需求说明、日志指标设计稿、当前 Java 代码、Git 提交记录和本地分析产物整理。

文档中的信息分为三类：

  • 已实现：当前代码可以验证的能力，可以作为项目事实陈述。
  • 原始设想：需求或设计稿中提出、但当前代码未完整落地的能力，面试时不能表述为已完成。
  • 复盘建议：基于现状总结的改进方向，用于回答“如果再做一次会怎么优化”。

个人复习时可以保留内部服务名和字段；对外面试时，应将服务名替换为“内容网关”“播放鉴权服务”“内容服务”，不要展示内部域名、IP、Cookie、日志全文和组织路径。

一页速记

简历表述

负责 SLO 异常自动化诊断工具设计与落地，基于 Java 和 Spring Boot 打通 Watcher 与 Billions 数据链路，采用 MAD 异常检测、接口增量对比、异常窗口加权采样等方案，构建覆盖异常发现、日志采集、16 维聚合、基线对比和批量分析的 CLI 流水线，并通过并行抓取与基线缓存提升多服务故障定位效率。

三十秒回答

这个项目解决的是 SLO 抖动后人工跨 Watcher 和日志平台排查成本高的问题。以前需要先找异常日期，再看错误接口和时间段，最后到日志平台逐条判断下游、实例、可用区或业务参数是否异常。我把这条链路做成了 Java CLI：先用 MAD 识别异常天，再做接口和基线增量对比，定位异常时间窗口，然后分时采样 Billions 日志，聚合成 16 个诊断维度。批量版本还增加了四线程并发、基线缓存和失败窗口拆分重试，最终沉淀可复用的 JSON 证据供人工或大模型生成根因报告。

两分钟回答

项目起因是部分核心服务在某些时段达不到 SLO，可用率下降时错误日志可能达到数千甚至更多。原排查方式依赖人工在质量平台确认异常日期和错误接口，再到日志平台切时间范围、拼查询条件、抽样日志，最后靠经验判断是下游服务、单实例、可用区、请求复杂度还是业务数据导致，过程重复且容易受采样偏差影响。

我先把人工步骤拆成确定性流水线：SLO 日报采集、异常日期检测、错误面板采集、错误接口与时间窗口检测、日志查询、指标聚合和基线对比。异常天使用中位数和 MAD，避免固定阈值无法适配不同流量级别的服务；接口层同时看绝对增量和增长倍数；时间窗口将异常日与基线日相同时刻对齐，过滤常态高峰。日志侧不一次性拉全天数据，而是等分窗口采样；异常窗口内再按错误密度分配配额，查询超时时拆分窗口重试。

最终聚合结果覆盖错误类型、下游服务、Gateway 实例、下游 IP、可用区、业务参数、请求和响应大小、超时配置、调用方及分钟趋势等维度。V2 将基线结果持久化并复用，支持多日期批量分析。当前实现属于确定性诊断流水线，而不是自主推理 Agent；Java 程序负责把证据做准，最终解释由外部分析指令或人工完成。

需求背景

业务问题

原始需求关注的是服务在某些时段无法达到 99.999% 可用率，同时 Service 层错误数显著上升。可能原因很多，包括下游服务变慢或不可用、数据库和缓存问题、单 Pod 或单 IP 故障、可用区异常、特定剧集数据、批量请求过大，以及 deadline 在调用链传播过程中被耗尽。

真正的难点不是“看到错误数升高”，而是把错误量继续缩小到可行动的范围：哪一天、哪个接口、什么时间段、哪类错误、哪个下游、是否集中在实例或区域、是否由特定业务参数触发。

原人工流程

  1. 在 Watcher 的 SLO 报表中选择服务和日期范围。
  2. 观察 Service 层错误数、请求可用性和告警量，找异常日期。
  3. 进入根因面板，按接口查看错误数时序和错误码。
  4. 手工记录错误最多的接口及时间段。
  5. 到 Billions 选择应用，拼接接口路径和返回码条件。
  6. 调整查询窗口并抽取日志。
  7. 阅读大量日志，判断错误类型、下游、实例、可用区和业务参数分布。
  8. 选择正常基线，再判断哪些变化与异常相关。

这个过程跨平台、依赖个人经验，而且每个服务和日期都要重复执行。日志数量大时，简单取前 N 条还会导致样本集中在最后几分钟。

需求演进

阶段一 从人工步骤抽象出流水线

最初设想是串联已有 Python 文件，形成“输入服务名，输出最近一周 SLO 抖动原因文档”的八步流程：抓取 SLO、识别异常日、抓取错误面板、识别接口和时段、查询日志、聚合指标、调用 AI、输出原因。

这一阶段的关键贡献是把模糊的“自动分析 SLO”拆成可独立验证的步骤，并明确每一步的输入和输出。没有这一层拆解，模型只能面对大量原始日志，难以稳定判断。

阶段二 建立可解释的日志指标体系

对真实日志样本分析后，设计从简单计数扩展为诊断维度。设计稿特别关注以下模式：

  • 同一 trace 产生多条错误日志，错误数可能被请求扇出放大。
  • 多个下游同时以极低耗时报 DEADLINE_EXCEEDED，可能不是下游都慢，而是剩余 deadline 已不足。
  • 错误均匀分布在多个 IP 时，不应误判为单实例故障。
  • 大批量参数可能使请求处理时间超过 deadline。

这一步把“让 AI 看日志”改造成“先把日志压缩成有诊断含义的结构化特征，再进行解释”。这是项目最重要的方法论。

阶段三 完成 Java CLI 和多场景命令

当前项目使用 Java 17、Spring Boot 3.4、WebClient、Jackson 和 Picocli，形成分层架构，并提供自动发现、指定日期、两日对比、增量接口、批量对比和精确查询等七个命令。

阶段四 从单次运行演进到可复用批处理

V2 的重点不再是增加一个命令，而是解决重复抓取和大批量分析的成本：

  • 按服务建立稳定目录，持久化基线日志和聚合结果。
  • 已存在基线聚合时跳过重复请求。
  • 已存在日期结果时跳过重复处理。
  • 使用四线程并发处理多个接口。
  • 在异常窗口内按错误密度加权采样。
  • 单窗口超时时拆成两个子窗口继续查询。

Git 历史显示，初始版本和 2.0 版本集中在 2026 年 5 月完成；2.0 主要新增 V2 批处理、query 命令、聚合维度、采样和分析说明。

为什么采用 CLI

这个阶段的核心诉求是快速复用内部平台能力、支持离线批量排查，而不是建设多人在线系统。CLI 的优点是部署成本低、参数明确、容易保存中间产物，也便于和外部分析命令组合。代价是缺少任务调度、权限治理、可视化状态和多人协作能力；如果要产品化，再演进为任务服务更合适。

端到端 SOP

步骤一 接收分析目标

输入：应用服务名、时间范围或基线日、目标日、增量门槛、可选接口过滤条件。

动作：CLI 校验必填参数，并使用 DateParser 兼容 5月18、05-18、2026-05-18 和完整时间格式。

输出：统一的 epoch 秒时间范围。

检查点：结束时间必须晚于开始时间；未指定目标日的批量命令默认取最近七天。

步骤二 拉取 SLO 日指标

输入：服务名和近 N 天范围。

动作：调用 Watcher 应用详情接口，获取 SLB、Service、API Gateway 的错误数、可用性、告警和错误预算信息。

输出：slo_report.json。

检查点：主流程只使用今天零点之前的完整天，避免当天未结束导致错误数不可比。

步骤三 识别异常日期

输入：按天组织的 SLO 数据。

动作：以 Service 错误数为主指标，计算中位数与 MAD。阈值为 median + 3 × MAD；MAD 为 0 时，使用中位数三倍或 1000 兜底。超过阈值的日期按错误数降序取 Top N。

辅助解释：检查 SLB、Service、API Gateway 可用性相对中位数是否下降，告警是否超过三次，Service 错误预算是否耗尽。

输出：anomaly_days.json。

为什么不用固定 3000：不同服务流量级别不同，固定阈值对低流量服务过高、对高流量服务过低；中位数和 MAD 对尖峰更稳健。

步骤四 获取错误面板并识别接口毛刺

输入：异常日期的起止时间。

动作：拉取 30 秒粒度的 GRPC 错误面板。基础流程先计算所有接口每个时间点的错误总量，以全天平均值五倍为毛刺阈值，合并连续超阈值点；再统计毛刺窗口内错误最多的接口，并以接口峰值的 20% 收缩核心区间。

输出：error_data.json 和 error_spikes.json。

检查点：这一算法适合自动发现明显尖刺，但持续性缓慢劣化可能不容易被均值五倍阈值捕获。

步骤五 基线对比和增量接口筛选

输入：基线日和目标日的错误面板。

动作：按接口累计全天错误数，计算 diff = target - baseline 和 ratio = target / baseline；默认要求增量不低于 50 且倍率不低于 1.5。基线为 0、目标大于 0 时视为新增接口。

输出：increased_apis.json，同时统计错误码变化和热点分钟。

为什么同时使用绝对量和倍率：只看倍率会放大小样本噪声，例如 1 增长到 3；只看绝对量又可能忽略小体量接口的显著恶化。

步骤六 识别相对基线的异常窗口

输入：某接口在基线日和目标日的 30 秒时序。

动作：按相同 HH:mm:ss 对齐两天数据，目标点需超过基线同时刻约三倍，且绝对增量大于 2。连续异常点先合并，间隔不足五分钟的窗口再次合并。窗口不足五分钟则向两侧扩展，超过两小时则选择错误增量最密集的子窗口，最后按窗口总错误数取 Top 3。

输出：time_windows.json，包含开始、结束、总错误数、峰值和相对倍率。

价值：用基线同时刻抵消日常流量高峰，比单纯使用目标日全局均值更能识别真正的异常增量。

步骤七 查询和采样日志

输入：服务名、接口路径、返回码和时间窗口。

动作：ApiNameParser 将 /path:-504 拆成路径和返回码，并根据服务选择 server.path 或 _server_path 字段生成查询条件。Billions 单页最多查询 200 条。

全天采样：将一天拆为 48 个窗口，每窗最多 50 条，使样本覆盖全天，而不是集中在最后发生的日志。

异常窗口采样：将窗口再拆为 10 段，总配额 500。活跃段先获得最低配额，剩余配额按错误数分配。

容错：单窗口查询失败时拆成前后两个子窗口重试；子窗口仍失败则跳过，不中断整次分析。

输出：logs.json、baseline_logs.json 或 target_logs.json。

步骤八 多维聚合和基线差异

输入：采样日志集合。

动作：逐条解析日志字段，按错误、入口、下游、实例、区域、业务参数、大小、配置、调用方和时间维度累加。对耗时计算平均值、P95 和最大值，对 trace、用户、实例和下游 IP 去重。

输出：aggregate.json、baseline_aggregate.json、target_aggregate.json 和 diff_result.json。

检查点：聚合结果代表样本分布，不等于完整日志总体；结论应结合样本量、采样策略和基线共同判断。

步骤九 批量复用和结果沉淀

输入：一个基线日和多个目标日。

动作：V2 先选择基线日主要错误接口并预取日志，聚合结果保存到服务固定目录。后续目标日直接复用基线聚合；存在 increased_apis.json 的日期跳过。多个接口通过固定四线程池并行处理。

核心算法

MAD 异常检测

设每天 Service 错误数为 x1...xn：

MAD 比均值和标准差更不容易被少量尖峰拉高，适合历史窗口较短、异常点比例低的情况。当前实现没有乘常见的 1.4826 标准化系数，因此它是业务阈值规则，不应包装成严格的正态统计检验。

边界：只有七天数据时样本较少；周期性强、连续多天异常或整体水平缓慢抬升时，中位数本身也可能被污染。更成熟的版本可引入同星期基线、季节分解或分位数模型。

两阶段毛刺检测

第一阶段对每个 30 秒点汇总所有接口错误量，以全量平均值乘五作为阈值，找连续超阈值窗口。第二阶段在窗口内按接口累计错误数，取 Top N，再以该接口峰值的 20% 找核心区间。

优点：实现简单、解释直接，可以先缩小时间再缩小接口。

不足：平均值会受尖峰影响；固定五倍和 20% 依赖经验；对平台型高基线服务和持续小幅劣化不够敏感。

诊断逻辑

  • 错误集中于一个 Gateway Pod：优先排查该实例的 CPU、内存、GC、线程池和连接池。
  • 错误集中于一个下游 IP：优先排查该实例过载、卡死或发布差异。
  • 同一服务多个下游 IP 均匀异常：更可能是下游服务整体容量或公共依赖问题。
  • 多个下游同时以很短耗时失败：考虑上游 deadline 已耗尽、网络或注册发现等公共问题。
  • 某业务 ID 占比显著：排查热点内容、缓存击穿或异常数据。
  • 大请求桶平均耗时明显更高：考虑限制批量大小、拆分调用或调整超时策略。
  • 错误数明显高于独立 trace 数：说明单请求产生多条错误日志，不能把日志条数直接当受影响请求数。

设计稿与实现差异

日志设计稿曾提出单独的 Trace 级联表、耗时分布直方图和客户端版本维度。当前代码实现了全局 trace 去重和重试放大倍率，但没有完整输出“每个 trace 涉及哪些下游、最大最小耗时和级联模式”的表；也没有独立的 ts 直方图和客户端版本表。面试时可以说这些分析启发了现有指标，但不能说全部落地。

工程设计与取舍

为什么先做结构化证据而不是直接把原始日志交给模型

原始日志数量大、字段噪声多，直接送入模型存在上下文成本、隐私风险、采样不稳定和结论不可复现的问题。聚合层把大量日志压缩成稳定指标，模型或人工只需比较分布变化，并且每个结论都能回到 JSON 证据复核。

为什么保留原始数据和中间产物

流水线每一步都落盘，便于断点复查、算法重跑和问题定位。如果只输出最终文本，一旦结论有疑问就无法判断是数据抓取、窗口识别、采样还是解释环节出了问题。

为什么基线使用指定正常日

指定正常日实现简单、口径清楚，适合快速验证。但它可能受到星期、活动和流量结构差异影响。原始需求提出“上周同时段或近七天平均”，当前代码主要使用单日基线。后续可建设同星期、同时间段的多日稳健基线。

为什么线程池固定为四

日志查询属于 I/O 密集任务，并发可以缩短多个接口的处理时间；固定小线程池可以避免对内部日志平台造成过高并发。当前数字是经验配置，没有自适应限流和性能压测数据，面试时不要声称有具体百分比提升。

为什么不是 Web 服务

项目先验证诊断链路和数据口径，CLI 更容易快速迭代，也避免提前引入任务队列、数据库、权限和前端。若覆盖更多团队，应把抓取和分析封装成异步任务，增加状态机、审计、配额和可视化报告。

为什么不把它称为完整 Agent

当前执行路径由代码预先定义，没有“观察、推理、选择工具、再观察”的动态循环，也没有内置大模型服务。它更准确的定位是确定性 SLO 诊断流水线，或 Agent 的工具与数据准备层。外部分析指令可以读取产物生成报告，但决策循环不在 Java 项目内部。

案例复盘

案例一 内容服务接口错误激增

本地产物显示，某内容服务的一个列表接口在目标日错误量从 1986 增长到 9106，绝对增量 7120，约为基线的 4.59 倍。系统首先通过错误面板累计识别该接口，再输出增量列表，后续按接口采集目标日日志并生成聚合结果。

面试讲法应关注方法，不必暴露真实接口名：

  1. 先用绝对增量和倍率共同筛选，排除小样本噪声。
  2. 查看时间窗口，确认是全天持续劣化还是少量尖刺。
  3. 对比错误类型，判断是内部错误、超时还是不可用。
  4. 查看下游服务与 IP 分布，区分单实例与服务级问题。
  5. 查看业务参数和请求大小，判断是否由特定内容或大批量请求触发。
  6. 将结论限定为“最可能原因和下一步验证”，不把样本相关性说成确定因果。

案例二 鉴权服务异常窗口

一个实际窗口聚合包含 8 条样本、8 个独立 trace、7 个 Gateway 实例和 7 个下游 IP，错误全部为 INTERNAL，且全部指向同一个下游服务与接口。平均耗时约 0.2015 秒，P95 约 0.2100 秒；下游 IP 和 Gateway 实例较分散。

基于这些证据，合理判断是：问题集中在特定下游调用，但不像单 Gateway Pod 或单下游 IP 故障，更接近下游服务级行为或统一超时边界。由于样本只有 8 条，不能直接断言根因，需要继续结合基线日相同接口分布、发布记录、下游监控和完整 trace 验证。

这个案例适合展示“如何排除错误假设”：看到某个下游占 100% 不代表某台机器有问题；IP 和调用实例分散恰好削弱了单点故障假设。

证据规模的正确表达

当前仓库 batch_diffv2 目录包含 3 个服务、33 个日期目录和 1600 余份 JSON 产物，说明流程在多个服务和日期上运行过。这个数字可以证明工具经过实际数据验证，但不能等价为线上全量覆盖，也不能替代准确率、召回率或 MTTR 改善数据。

结果与价值

可以确认的结果

  • 将跨 Watcher 和 Billions 的手工排查过程固化为可重复执行的 CLI 流水线。
  • 支持从服务级异常逐层收敛到日期、接口、错误码、时间窗口和日志维度。
  • 通过分时采样降低时间偏置，通过异常密度加权提高关键窗口的样本利用率。
  • 通过基线缓存、并行处理和失败窗口拆分提高批量运行的可用性。
  • 保存原始数据、中间结果和聚合证据，支持复查和二次分析。

不能夸大的结果

  • 没有可靠数据证明 MTTR 降低了多少百分比。
  • 没有建立根因识别准确率、召回率或人工标注评测集。
  • 没有完成 Java 内部的大模型调用和自主 Agent 循环。
  • 当前应用查询字段只对少量服务做了显式映射，不能声称应用清单中的 48 个服务全部接入。

更稳妥的影响表达

我把依赖人工经验的跨平台排查步骤变成了可复用的数据流水线，并把大量原始日志压缩成可解释、可对比的结构化证据。项目已经在多个真实服务和日期上生成分析产物，验证了从异常发现到日志归因的链路可行性；下一阶段需要补齐评测、服务配置化和产品化能力。

已知问题与复盘

当前代码问题

  1. 聚合器已将下游服务和可用区编号调整为 5_下游服务失败 和 8_可用区维度，但差异计算仍读取旧的 4_下游服务失败 和 7_可用区维度，导致部分 diff_result.json 的对应数组为空。
  2. batch-diffv2 跳过已处理日期时，不会先读取旧 summary.json，最后可能用本次列表覆盖历史汇总。
  3. pipeline 命令定义了 --log-limit，但没有传入编排器，内部仍使用固定采样数量。
  4. README 仍描述旧的四个命令、10 维聚合和 Java 内部 AI 分析，与当前代码不一致。
  5. src/test 没有实际测试代码，算法阈值、字段缺失和 HTTP 异常缺少回归保障。
  6. 应用查询字段映射只硬编码了三个服务，原始 CMDB 清单中存在 _server_path、server.path、HTTP 以及无日志等多种情况，尚未配置化。

如果重新做一次

第一步先补测试和数据契约。使用 MockWebServer 固定 Watcher 与 Billions 响应，对日期解析、MAD、窗口合并、采样配额和 16 维聚合做单元测试，并为字段缺失准备样例。

第二步把服务元数据配置化。将应用级别、基线日期、查询字段、协议和日志可用性从硬编码迁移到配置中心或 CMDB，同步解决多服务接入问题。

第三步建设基线与评测。用同星期、同时间段的多日中位数代替单日基线；收集历史故障与人工根因，评估异常检测召回率和根因候选准确率。

第四步产品化。把 CLI 改造成异步任务服务，增加任务状态、限流、重试策略、产物索引、权限控制和报告页面。

第五步再引入 Agent。将 SLO 查询、错误面板、日志查询、聚合和 Trace 检索封装为工具，让模型根据证据缺口决定是否扩大时间范围、切换接口、追加采样或查询发布记录，并设置成本和最大轮次。

面试高频问答

这个项目最难的地方是什么

最难的不是 HTTP 接口串联，而是把模糊的人工判断转换成稳定、可解释的数据口径。比如错误日志多不等于失败请求多，因为一个 trace 可能扇出多条下游错误；看到多个下游超时也不一定是多个服务同时变慢，可能是 deadline 在前置环节耗尽。为此我先设计聚合维度和基线对比，再让上层解释结论，而不是直接让模型阅读原始日志。

为什么选择 MAD

不同服务错误量级差异很大，固定阈值难以通用；均值和标准差又容易被少量尖峰拉高。MAD 基于中位数，对离群点更稳健，计算和解释也简单。当前只有短时间窗口，所以它是实用启发式规则，不是完整的时序预测模型。

如何降低误报

日期层使用相对历史分布；接口层同时要求绝对增量和增长倍率；时间层与基线日相同时刻对齐；日志层再验证错误类型、下游、实例和区域是否呈现一致变化。多层证据交叉验证，比单一阈值更可靠。

如何选择基线

当前工具使用人工指定的正常日，优点是口径明确、实现简单。缺点是可能存在星期和业务活动差异。更成熟的方案是取过去若干个同星期、同时段的中位数，并排除发布、活动和历史故障日。

为什么需要采样而不是全量日志

日志平台有查询和返回限制，全量拉取成本高，而且故障日可能有大量重复日志。分时采样保证全天覆盖，异常窗口加权采样提高关键时间段分辨率。结论中保留样本量和 trace 去重指标，避免把样本分布误认为总体精确比例。

采样会不会遗漏根因

会，因此采样不是一次性定论。系统先通过错误面板确定接口和时间窗口，再在窗口内加权采样；如果证据不足，可以用 query 命令扩大样本或缩小到特定接口和时间段。后续 Agent 化也应围绕“证据不足时追加查询”建立循环。

如何区分下游慢和 deadline 耗尽

主要看实际耗时、错误类型、同 trace 的多下游行为和基线变化。较长耗时集中于单一下游更像下游真慢；多个下游在很短时间内同时 DEADLINE_EXCEEDED，更像剩余 deadline 不足。当前代码能提供下游耗时和 trace 去重，但完整的 Trace 级联表仍是后续改进项。

为什么用 Java 和 Spring Boot

Java 适合团队现有工程体系，Spring Boot 提供配置绑定、依赖注入和 WebClient，Picocli 负责 CLI。选择 WebFlux 主要是为了 WebClient，而当前编排代码仍以阻塞式调用为主；如果追求端到端响应式，需要进一步改造，不能仅凭用了 WebClient 就说系统是全响应式。

并发如何控制

V2 使用固定四线程池并行处理接口。这样可以利用 I/O 等待时间，又限制对内部平台的并发压力。每个任务内部捕获异常，单接口失败不会终止所有接口；最终在 finally 中关闭线程池。后续可以增加信号量、速率限制、指数退避和可配置线程数。

缓存如何保证一致性

当前缓存是文件级复用：只要基线接口的 aggregate.json 存在且可读，就视为命中。它没有把基线日期、聚合版本和查询条件写入缓存键，因此基线变化或指标升级时可能复用旧数据。改进方案是增加 manifest，缓存键包含服务、日期、接口、返回码、采样参数和聚合版本。

为什么输出 JSON 而不是直接生成报告

JSON 便于机器处理、差异比较和重复解释，也保留每一步证据。报告是解释层，可以由不同模板或模型生成；数据层不应和一次性的自然语言结论绑定。

这是 Agent 项目吗

严格来说不是完整 Agent。它有自动选择异常日期、接口和窗口的能力，也能调用多个数据源，但执行流程是固定的，没有大模型驱动的动态工具选择和反思循环。更准确的说法是 SLO 诊断流水线，以及未来 Agent 的工具和证据层。

大模型在项目里做了什么

原始目标包括用 AI 根据聚合表生成根因文档，仓库也保留了分析指令；但当前 Java 代码没有内置大模型客户端。我的表述会区分清楚：已完成结构化证据生成，最终根因解释由外部 Claude 或人工完成。

如何证明项目有效

当前能证明的是链路可运行，并在多个服务和日期生成了接口、窗口、日志与聚合产物。还不能证明根因识别准确率或 MTTR 改善。要做严格验证，需要收集历史故障、人工确认根因和处理结果，形成离线评测集，统计异常检测召回率、候选根因 Top K 命中率和分析耗时。

遇到新服务字段不一致怎么办

当前通过 ApiNameParser 为少量服务映射 server.path 或 _server_path。CMDB 材料表明还有 HTTP、无日志和其他情况。正确演进方式是把查询字段、协议和模板变成服务元数据配置，并在任务启动前做日志可用性探测。

系统如何处理部分失败

错误面板抓取失败会跳过该日期；日志窗口失败会拆半重试，仍失败则跳过该子窗口；单接口处理异常只记录错误，不影响其他接口。代价是最终报告可能使用不完整样本，所以产物中还应增加成功窗口数、失败窗口数和覆盖率，目前这部分还不完整。

为什么保留固定阈值

项目处于工程验证阶段，固定阈值便于解释和调试。阈值集中在命令参数或算法常量中，已经支持部分调整。后续应按服务历史分布自动校准，并记录阈值版本，避免同一结果无法复现。

如果错误是缓慢增长而不是尖刺怎么办

均值五倍的毛刺算法可能漏掉慢性劣化。可以增加滑动窗口斜率、EWMA、分位数带或累计偏差检测；同时 compare 和 diff 命令仍能通过全天基线增量发现持续增长，因此不同命令是互补的。

如何保护敏感信息

Cookie 通过本地配置或环境变量提供，不提交仓库。原始日志和聚合产物包含服务名、IP、业务 ID 等内部信息，只应保存在受控目录；对外报告需要脱敏 IP、用户标识、trace 和内部组织路径。若引入外部模型，还必须限制发送字段并经过合规评估。

你个人承担了什么

基于现有材料可以稳妥表述为：我参与或负责了需求流程抽象、Java 流水线实现、异常和窗口算法、日志指标聚合、批量缓存与采样优化，并基于真实产物迭代分析维度。若实际协作中存在他人负责的模块，面试时应按真实分工进一步收窄，不要把团队成果全部归为个人。
