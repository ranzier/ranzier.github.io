一个典型风险是，创建导航卡时下游已经成功，但返回超时，模型把它当作失败再次调用，导致重复创建。我们为计划内写操作建立稳定标识并记录执行状态和结果，将模型的多次调用关联到同一次业务操作。已有结果就复用，结果不确定就先核对，避免直接重放写操作。

1. 简单介绍一下你这个项目的作用吧？

这是一个面向 OGV 运营场景的多 Agent 智能操作平台，主要目的是把运营人员原来需要在多个系统中手动完成的查询、分析和批量操作，统一转化为自然语言驱动的智能任务。

平台以主 Agent 作为统一入口，负责理解用户意图、拆解任务，并根据业务场景调度不同的子 Agent。各个子 Agent 可以通过配置动态加载提示词、工具、技能和权限，因此新增业务场景时通常不需要重新开发整套流程。

项目重点解决了三类问题：一是通过计划、步骤和批次机制执行耗时较长的任务，支持暂停、继续、重试以及服务重启后的恢复；二是对批量写操作增加用户确认、权限校验和幂等保护，避免模型重复调用或越权执行；三是支持 Excel、PDF、Word、PPT 等多种文件的异步解析，让 Agent 能够按需读取文档内容，而不是把整个文件一次性塞进模型上下文。

简单来说，它不是一个只负责问答的聊天机器人，而是一个能够理解运营需求、调用业务工具、处理文档，并且安全、持续地完成复杂运营任务的 Agent 执行平台。

2. 能举个这个Agent可以帮我做事情的具体例子吗？

可以用“根据 Excel 批量调整番剧的运营配置”这个场景来理解。Annotation 1

假设运营人员上传了一份 Excel，里面列了 200 部番剧，以及每部番剧需要调整的配置，然后对平台说：

“帮我检查这份表里的番剧，确认当前配置，把需要修改的内容整理给我，确认后再批量更新。”

平台会按下面的流程处理：

  1. 读取文件、核对数据。 解析 Excel，提取番剧编号和目标配置，调用对应的业务查询工具，检查番剧是否存在、当前配置是什么，并找出编号错误、重复记录等问题。
  2. 生成执行计划。 把需要修改的内容整理出来，例如“200 条记录中，150 条需要更新，40 条已经符合要求，10 条存在异常”，让运营人员确认修改范围。
  3. 确认后分批执行。 用户确认后，平台按计划调用业务工具完成更新，记录每批的进度和操作结果，减少重试造成的重复执行。
  4. 处理异常并汇总结果。 任务执行过程中可以暂停、继续；发生中断时，根据已保存的进度恢复。最后向用户汇报成功、失败及需要人工处理的记录。

原来运营人员需要自己读表、逐条查询、进入业务系统修改，再手动统计结果；这个平台把这些步骤串成一个可以通过对话发起和管理的任务。具体能修改哪些配置，取决于平台已经接入的业务工具和用户权限。

业务 Agent 的实际数量和能力由 Paladin 配置、已注册 Tool/Skill 和用户权限共同决定，不能仅根据 Java 类的数量统计。

2. 公共域 Agent：负责通用能力与任务协调

公共域使用 ReActAgent 构建，代码中固定注册，主要包含：

  • 任务协调：创建任务、保存计划、处理整体确认、暂停、继续、重试、记录进度。
  • 文档理解：检查文档结构、按分片读取内容、读取内嵌图片。
  • 图片能力：查询生成参数、提交图片生成、查询结果、调整图片尺寸。
  • 辅助能力：BV 号转换、受控临时状态读写等。

具体状态转换与持久化由它调用的服务端工具完成。公共域的定义见 CommonDomainAgent.java。

3. 业务子 Agent：负责领域内的具体操作

业务子 Agent 同样使用 ReActAgent，按配置绑定领域提示词、Tool、Skill 和权限。

主 Agent 负责把需求交给合适的领域；业务子 Agent 负责在本领域内选择工具、组织参数、执行并解释结果。

当前代码有两点需要区分：

  • 活动域的查询、创建、配置工具，以及投放项目查询、创建、预算工具，仍返回 mock 数据。
  • 搜索导航卡工具、上述创作激励查询与诊断工具，已有真实接口调用实现。

同时，活动、投放、创作激励的静态 Agent 装配类已经标记为弃用。当前业务域由 Paladin 动态生成，所以这三个领域应理解为代码中已有的业务划分和能力示例；线上实际开放哪些领域，需要看实际配置。注册逻辑见 AgentFactory.java。

另外，意图识别、Planner、Aggregator 是当前 Agent 承担的职责：路由和汇总主要由主 Agent完成，长任务规划由公共域承担，没有分别独立注册成三个 Agent。

5. 当用户请求一个问题之后，整个系统是怎么执行的？分成简单和复杂两种情况说明。

两种情况都由 主 Agent 理解需求并选择处理方式，区别在于：简单请求通常在单轮完成；需要跨轮、异步依赖或批量处理的复杂请求，会先保存计划，确认后按状态推进。

一、共同的准备过程

用户发起请求后，系统先完成以下工作：

  1. 获取身份和权限：确定用户可以使用哪些能力。
  2. 准备上下文：结合当前消息、会话历史、附件引用及已有任务状态。
  3. 装配可用 Agent：根据 Paladin 配置和用户权限，过滤各领域的 Tool、Skill，生成领域能力描述及委派工具列表。
  4. 主 Agent 调用大模型：结合上下文和能力描述，判断直接回答、追问、委派领域，还是先进行长任务规划。

已有待确认操作、部分任务恢复等请求，可以先由服务端专用逻辑处理。

二、简单请求：选择领域，调用工具，返回结果

例如：

“查询这个 UP 主的待签约列表。”

具体来说：

  1. 主 Agent 选择领域：根据能力描述判断该请求属于创作激励业务，通过 SubAgentTool 委派。
  2. 子 Agent 选择业务工具：检查 UP 主标识、分页参数等；缺少必要信息时追问。
  3. 程序执行调用：完成相应参数与权限校验，通过集成层访问业务接口。
  4. 根据结果决定下一步：结果足够就形成答案；需要补充查询时继续调用工具。
  5. 输出结果：满足直返条件时使用领域答案，否则由主 Agent 汇总回复，并保存会话状态。

简单请求也可能包含多次工具调用，关键是能否在当前轮次可靠完成。如果只是欢迎语或能力说明，也可能由主 Agent直接回答。

三、复杂请求：先规划和确认，再分步执行

例如：

“先生成一张符合规格的宣传图，再用它创建搜索导航卡。”

这包含“等待图片生成结果，再创建卡片”的异步依赖。

具体分为七步：

  1. 判断是否需要长任务流程
    主 Agent 综合任务规模、步骤依赖、异步等待和单轮预算判断；明显批量场景还会由规则标记，并通过执行守卫要求先规划。

  2. 委派公共域制定计划
    公共域加载长任务工作流，完成必要的只读查询，创建任务，再提交包含完整步骤、处理领域和主要副作用的结构化计划。

  3. 持久化并等待确认
    服务端将计划、版本和任务状态保存到 Redis，进入等待整体确认状态。本轮展示计划，确认后的后续请求才开始执行业务。

  4. 绑定确认版本，启动执行
    用户确认后，服务端记录已确认的计划版本，安排续跑事件；开始运行时再次检查任务状态、事件和版本是否有效。

  5. 按步骤执行
    普通步骤由主 Agent 委派对应领域执行；包含已注册批次动作的步骤，可以由服务端批次执行器逐项推进。

  6. 记录结果并跨轮推进
    保存真实结果、步骤位置、执行游标和异步任务引用。达到本轮预算时结束当前轮次，后续重新读取状态继续处理，无需用户按批次反复回复“继续”。

  7. 完成或处理异常
    全部完成后返回业务结果。执行结果不确定时先核对已有操作；计划实质变化时重新确认；无法安全继续时请求用户介入。

处理单位 当前轮次内的业务调用 持久化任务、计划和步骤
是否先规划 通常直接委派 先保存完整计划

8. 为什么不使用只做成一个Agent，而是做成多Agent系统？

结合我们当前的业务范围，多 Agent 的主要价值是划分职责、控制每次推理的能力范围，以及方便不同业务域独立扩展。 单 Agent 也能实现这些功能，但需要把更多领域规则和工具放进同一个执行上下文。

1. 不同业务域的规则差异较大

我们的系统既处理活动、投放、创作激励，也处理文档、图片和长任务。

如果全部放在一个 Agent 中，它需要同时理解所有领域的提示词、工具参数和执行规则。拆分后：

这样，每个领域 Agent 只需要关注当前开放给它的能力，有利于减少无关规则和工具对决策的干扰。

2. 分开“跨域编排”和“领域执行”

例如“生成宣传图，再创建导航卡”：

  • 主 Agent 负责协调图片生成与导航卡创建的先后关系。
  • 公共域负责规划、图片生成和异步结果处理。
  • 业务域负责导航卡参数组织及物料接口调用。

这些职责分开后，主 Agent 可以根据真实中间结果继续委派，领域 Agent 专注完成自己的业务步骤。

3. 方便业务域独立配置和扩展

我们已经通过 Paladin 配置业务子 Agent 的提示词、Tool、Skill 和权限绑定。

新增业务域时，如果需要的工具已经存在，可以通过新增域配置完成装配；新增业务能力则补充对应工具实现。修改某个领域的规则，也能将影响集中在该领域。

4. 让能力边界更清楚

系统先按用户权限过滤能力，再为各子 Agent 组装工具集。

例如，活动域只持有配置给它的活动能力，公共域持有任务协调和通用能力。这样更方便审查“哪个 Agent 能调用哪些工具”。

这里要注意：真正的权限保障来自代码中的权限过滤、执行守卫和操作确认。 多 Agent 的职责划分帮助我们组织边界，不能代替这些程序校验。

多 Agent 也有成本。 主 Agent 委派子 Agent 会增加模型调用、延迟和 Token 消耗，还需要处理上下文传递、结果汇总及委派错误。当前系统的主 Agent 每次只委派一个领域，因此也不能把“多个 Agent 并行加速”作为主要选型理由。

面试时可以这样回答：

我们覆盖多个运营业务域，各领域的规则和工具差异比较大，所以采用主 Agent 加领域子 Agent 的结构。主 Agent 负责意图理解、路由和跨域编排，子 Agent 负责领域内执行。这样可以控制单次推理涉及的工具范围，并支持业务域独立配置和扩展。代价是增加调用成本和协作复杂度，因此我们保留统一主入口，并通过权限过滤和执行守卫约束实际执行。

11. 为什么使用AgentScope这个框架？

使用 AgentScope Java 构建 Agent 系统，核心优势在于它专为 Java 企业级生产环境设计，将多智能体协作所需的工程化能力（如分布式部署、状态恢复、安全隔离）封装成了开箱即用的组件，而非仅仅提供基础的模型调用封装。

🏢 贴合 Java 企业技术栈，降低集成成本

对于以 Java 为主的技术团队，AgentScope Java 提供了原生支持，避免了为了构建 Agent 而被迫引入并维护 Python 技术栈的问题。它可以直接以 Maven 依赖的形式嵌入现有的 Spring Boot 工程，利用 Java 生态成熟的监控、部署和并发模型。该框架已在阿里集团内部 13+ 业务线生产使用，经过了企业级场景的检验。

🧠 工程化的“外壳”：HarnessAgent 保障长任务稳定

单纯的 ReActAgent 只能处理单轮推理，而生产环境的 Agent 往往需要长时间运行。AgentScope 提供的 HarnessAgent 在推理内核外增加了一层工程基础设施，解决了长任务中的常见痛点：

  • 状态可恢复：通过稳定的 sessionId，即使进程重启或跨节点部署，也能完整恢复对话和任务状态，避免“失忆”。
  • 上下文可控：内置自动压缩策略，当工具调用结果过大时，会自动将内容转存到磁盘并在上下文中保留引用，防止超出模型的上下文窗口限制。
  • 工作区持久化：Agent 的人格设定、长期记忆和技能都存储在文件系统中，修改配置或记忆无需重新编译代码，实现了 Agent 的“自我进化”。

0.2 AI问题

下面的问题更关注“整个项目为什么做、怎么设计、如何落地、你的贡献是什么”，适合作为项目整体介绍后的面试追问。回答是示例话术，涉及数据的部分需要替换成真实情况。

1. 这个平台主要解决什么业务问题？

OGV 运营工作中存在大量跨系统、重复且步骤较长的操作，例如读取运营材料、生成执行方案、调用业务工具并批量落地。传统方式依赖人工串联，效率较低，也容易出现遗漏。平台希望通过多个业务 Agent 协作，把自然语言需求转换为可确认、可执行、可恢复的任务。

2. 为什么要做多 Agent，而不是一个大模型加一组 Tool？

不同业务域的提示词、工具、权限和操作规则差异较大。如果全部放到一个 Agent 中，上下文会比较复杂，工具选择也更容易混乱。我们使用主 Agent 负责任务理解和路由，业务子 Agent 负责具体领域能力，从而实现职责隔离、权限隔离和独立迭代。

3. 系统整体架构是什么样的？

整体可以分为四层：

  • 接入层：接收用户请求、文件和任务控制指令。
  • Agent 编排层：完成意图识别、子 Agent 路由、计划生成和执行控制。
  • 能力层：提供业务 Tool、Skill 和文档理解能力。
  • 基础设施层：Redis 保存任务状态，Paladin 管理动态配置，BFS 存储文件，业务服务负责实际操作。

4. 一个用户请求从进入系统到执行完成，完整流程是什么？

用户请求首先由主 Agent 理解，并选择对应的业务子 Agent。子 Agent 根据用户输入和文档内容生成执行计划；涉及写操作时，需要用户确认。确认后，系统按照计划逐步调用工具，持续记录执行进度和结果，最后汇总执行情况返回给用户。

5. AgentScope 和 DashScope 分别承担什么角色？

AgentScope 主要用于组织 Agent、Tool 调用和多 Agent 协作流程；DashScope 提供底层大模型能力。我们在框架之上补充了任务状态管理、权限控制、动态配置和文档理解等面向生产环境的能力。

6. 这个系统与普通聊天机器人的核心区别是什么？

普通聊天机器人主要生成文本，而这个系统需要执行真实业务操作。因此除了模型效果，还必须解决任务状态、权限、幂等、异常恢复、人工确认和可观测性等工程问题。核心目标不是“回答得像”，而是“执行得正确且可控制”。

7. 系统如何划分主 Agent 和业务子 Agent 的职责？

主 Agent 负责理解需求、识别业务域和选择子 Agent，不直接承载复杂业务规则。业务子 Agent 只暴露自己领域内的 Tool 和 Skill，并配置对应权限。具体写操作最终仍由确定性的业务接口执行，模型主要承担理解、规划和参数组织。

8. 为什么让模型生成计划，而不是直接调用业务接口？

复杂运营任务通常包含多个步骤，而且用户需要在执行前了解系统准备做什么。显式计划可以提高可解释性，也方便用户确认、任务恢复和失败重试。对于简单只读操作，可以缩短流程；对于批量写操作，则必须经过计划和确认。

9. 如何控制模型的不确定性？

主要通过缩小模型的决策范围来控制。模型负责理解和规划，但实际执行依赖结构化 Tool；工具参数需要经过校验，写操作还受到任务状态、用户确认和权限的约束。同时记录每一步输入、输出和状态，方便发现问题和人工介入。

10. 为什么选择 Redis 保存任务状态？

任务状态需要频繁读写，并且要支持服务重启后恢复。Redis 的访问延迟较低，也适合保存任务游标、执行状态和临时结果。对于有明确生命周期的数据，可以通过 TTL 控制存储时间；如果后续需要长期审计，还需要再落到持久化数据库。

11. 系统如何保证业务安全？

安全控制不依赖模型自行判断。我们从 Agent 能看到哪些 Tool、调用者是否具备权限、任务是否已经确认、当前状态是否允许执行等多个层面进行校验。真正的业务接口还会保留自身的鉴权和参数校验，Agent 层不会绕过原有安全边界。

12. 多 Agent 之间如何协作，是否会互相直接调用？

目前以主 Agent 路由到业务子 Agent 为主，尽量减少子 Agent 之间自由调用。这样执行链路更容易追踪，权限关系也更清晰。如果任务需要跨业务域协作，由编排层统一组织，而不是让 Agent 自主形成不可控的调用链。

13. 项目中最难的工程问题是什么？

最难的不是接入模型，而是把模型的概率性输出接入确定性的业务系统。尤其是长任务、批量写操作和异常重试场景，需要同时处理任务状态、用户确认、幂等、恢复和权限问题。我们的思路是把这些约束放在确定性的执行框架中，而不是依靠提示词保证。

14. 如何评估这个平台是否有效？

可以从三类指标评估：

  • 效率：任务平均耗时、人工操作步骤减少量。
  • 质量：计划成功率、工具调用成功率、任务完成率。
  • 安全与稳定性：重复写入次数、异常恢复成功率、越权拦截数量。

面试时最好补充真实数据，例如“平均处理时长从多少降低到多少”，不要编造指标。

15. 你在项目中的职责边界是什么？

我主要负责平台中偏执行基础设施的部分，包括长任务执行与恢复、业务子 Agent 配置化以及多格式文档理解。主 Agent 的部分路由逻辑和具体业务 Tool 由团队其他成员共同建设。我也参与了这些模块之间的协议设计和联调，但不会把整个项目描述成个人独立完成。

16. 你和业务方、其他研发是如何协作的？

业务方负责明确实际操作流程、风险点和验收标准；各业务研发提供可调用的领域接口；平台侧负责 Agent 编排、统一协议和安全控制。对于不明确的业务语义，我们会先固化为结构化规则或工具参数，再交给模型使用。

17. 项目上线前如何测试？

除了普通单元测试和接口测试，还需要重点覆盖 Agent 场景，包括模型输出不合法、工具调用失败、执行中断、重复请求、权限不足、配置热更新和大文件解析等情况。对于写操作，会在测试环境使用可回滚或模拟数据验证完整执行链路。

18. 出现线上问题时如何定位？

需要通过任务 ID 串联用户请求、Agent 路由、计划版本、步骤状态和工具调用结果。定位时先判断是模型规划问题、框架状态问题，还是下游业务接口问题。对于执行失败的任务，可以根据任务状态决定重试、继续执行或人工终止。

19. 这个项目有哪些设计取舍？

我们没有追求完全自主的 Agent，而是选择“模型规划加确定性执行”的方式。这样灵活性会受到一定限制，但更适合涉及真实业务写操作的场景。配置化也不是无限开放，而是在可校验的 Tool、Skill 和权限范围内提供动态能力。

20. 如果重新做一次，你会改进什么？

我会更早建立统一的任务事件模型和评测体系。任务事件模型可以降低状态排查和审计成本；评测体系可以通过固定用例持续衡量路由、计划和工具调用效果，而不是主要依赖人工体验。另外，长期任务数据应进一步区分临时状态与持久化审计数据。

1.1 具体实现方式

1. 背景与目标

普通 Agent 通常在一次请求中完成“推理、调用 Tool、返回结果”。但批量运营任务可能包含多个步骤、几十个对象、异步等待和真实写操作，单轮请求无法可靠完成。

这套机制的核心目标是：

将模型生成的长任务转换为服务端可持久化、可确认、可分批推进、可恢复的状态机。

核心代码集中在 app/ogv-agent-gateway 模块。

7. 暂停、继续、停止和重试

统一入口是 controlTask：

  • PAUSE：保存原可恢复状态到 resumeStatus，进入 PAUSED，清理当前运行租约。
  • CONTINUE：恢复 resumeStatus，根据是否存在未闭合操作，选择正常续跑、结果核对或异步监控恢复。
  • CANCEL：进入 CANCELLED，清理后续通知和运行信息，不再启动新步骤。
  • RETRY：只允许从 WAITING_RETRY 或 RECONCILIATION_REQUIRED 发起。

暂停和停止是协作式控制：它们可以阻止后续步骤，但不能撤销已经发送到下游的写请求。

  • checkpoint JSON；
  • 活动任务集合；
  • 当前运行轮次；
  • 续跑通知队列；
  • 当前选中任务。

关键 CAS 判断是：

只有 expectedVersion 与 Redis 当前版本一致时才能保存。这样可以拒绝旧轮次、重复通知和并发控制请求。

Redis Key 使用相同的用户、会话 Hash Tag，使相关 Key 落在同一 Redis Cluster slot，从而能够由同一个 Lua 脚本原子更新。

9. 服务重启恢复

恢复依赖 Redis 中的持久化事实，不依赖 JVM 内存和模型对话记忆。

  • 通知尚未消费：服务恢复后仍可从 Redis 通知队列拉取并继续。
  • 批次部分完成：根据 currentStepNo + stepCursor 从下一项继续。
  • 执行中服务退出：runLeaseUntil 到期后，下一次加载任务会执行生命周期归一化。
  • 尚未发起副作用：进入 WAITING_RETRY，可以安全重试。
  • 已有异步任务：进入 WAITING_ASYNC_RESULT 或恢复监控。
  • 副作用已发起但结果未知：进入 RECONCILIATION_REQUIRED，先查询真实结果。

当前实现不是“应用启动时全量扫描并立即拉起所有长任务”，而是由未消费通知、异步轮询事件或用户再次进入会话触发恢复。

10. 执行守卫的作用

Prompt 和 Skill 只是指导，真正的安全约束位于 Tool 调用前的 Middleware。它会拒绝：

  • 没有创建任务就直接执行多项业务操作；
  • 没有保存计划或计划未经确认；
  • 未读取真实 checkpoint 就执行控制命令；
  • 没有有效 runId 就执行计划步骤；
  • 核对轮次再次执行写操作；
  • 超过单轮预算后启动新业务调用；
  • 任务状态调用和业务调用放在同一批执行；
  • 一个 reasoning 同时启动多个非并行安全业务 Tool。

这使模型只能在服务端允许的状态转换范围内行动。

11. 这项工作的准确总结

这项工作的本质不是“用 Redis 保存一个任务状态”，而是建立了一套长任务执行协议：

通过持久化计划版本、状态机、步骤和批次游标，将长任务拆成多个有租约的执行轮次；用户只需整体确认一次，后续由 Redis 通知驱动自动续跑；通过版本 CAS、运行租约和执行守卫防止旧请求并发推进；在超时或服务重启后，根据 checkpoint 和下游操作引用恢复到安全状态。

需要保留两个技术边界：

  1. 系统提供的是可恢复和幂等控制，不应宣称跨下游系统严格 exactly-once。
  2. 当前专门的长任务测试主要覆盖执行守卫，CheckpointService/Store/Coordinator 缺少直接单元测试，面试中不宜表述为“状态机已有完整自动化测试覆盖”。

1.2.1 自己想到的问题

1. 没有这个长任务机制之前，你的agent是怎么执行的？也就是为什么你要设计一个长任务执行机制？

没有长任务机制之前，Agent 主要在一次聊天请求中，通过多次“模型推理—调用工具—观察结果”来完成工作。设计长任务机制，是为了让复杂任务在跨请求、异步等待和服务重启之后，仍能有依据地继续执行。

我核对了引入长任务前的代码。当时已经有多 Agent 调度、会话状态持久化和图片生成结果轮询，所以面试时不能说“以前什么状态都不保存”或者“以前只能调用一次工具”。真正缺少的是独立于聊天上下文的业务任务进度管理。

以前系统已经能进行多 Agent 调度和多次工具调用，但复杂任务的推进主要依赖当前请求里的模型循环，以及后续请求加载的会话上下文。

引入长任务机制后，我们把完整计划、步骤、批次和执行进度保存为服务端任务状态。模型仍然负责理解需求和选择能力，但执行时需要遵循已确认的计划，每轮记录结果，再依据保存的进度继续；中断后也有明确的恢复依据。

1. 之前的 Agent 是怎么执行的？

用户发送一条消息后，后端加载对应的会话上下文，由主 Agent 判断交给哪个业务子 Agent。子 Agent 根据需求调用工具，拿到结果后继续推理，必要时再调用其他工具，最后返回答案。

例如用户问“搜索卡片的准入条件和申请流程”，Agent 可以先搜索规范，再打开相关文档，最后整理答案。虽然内部调用了多次模型和工具，但整体仍是在这一次请求中完成的。

如果工作没有完成，需要下一轮继续，后续判断主要依赖已经保存的会话内容和工具调用记录。当时还没有一套统一的业务任务记录，明确保存“完整计划是什么、哪些对象处理完了、下一批从哪里开始”。

2. 为什么这种方式不足以支撑复杂任务？

主要有四个问题：

  • 一次请求的执行时间有限。 对多个对象逐项处理、等待异步结果，可能无法在一次请求内完成。仅仅延长超时时间，仍然不能解决进程重启和中途失败的问题。
  • 会话记录不能直接充当可靠进度。 聊天中可能记着“已经处理了一部分”，甚至保留了工具结果，但恢复时仍需要重新推断哪些成功、哪些失败。上下文压缩后，逐项细节也可能不完整。
  • 异步完成不等于整个任务完成。 以前已经能轮询图片生成结果，但“图片生成好了”之后，如果还要继续处理后续步骤，就需要知道它属于哪个整体任务、后续依赖是什么，而不仅是通知用户结果。
  • 任务控制缺少明确对象。 用户说“暂停”或“继续”，系统需要知道控制哪个任务、当前状态是否允许、应该从哪里接着做。这些都需要服务端的任务状态来支撑。

如果涉及写操作，还会出现更敏感的问题：下游可能已经执行成功，只是响应没有返回。这时不能让模型根据一句“失败了”就重新执行，必须保留操作记录，并在结果不确定时先核对。

3. 长任务机制具体补上了什么？

我把一次复杂请求拆成可持久化的计划、步骤和批次，由服务端保存任务状态、计划版本、执行位置和操作结果。

用户先确认完整计划，系统再开始执行。每轮只处理一定范围的工作，记录真实进度，再由系统安排后续执行。下一轮从保存的状态继续，用户也可以对明确的任务发出暂停、继续、停止或重试指令。

这里的“一次确认”指的是对完整计划的一次整体确认。计划发生实质变化、权限不足，或者外部操作结果不确定时，仍然需要用户介入。

2. 你能介绍一下你这个长任务执行机制吗？

这个长任务机制，主要是为了解决 Agent 在处理多步骤、批量操作或异步任务时，单次请求做不完，以及中断后难以可靠恢复的问题。我的做法是，把任务计划和执行进度交给服务端管理，让整个任务能够跨多轮请求持续推进。

具体来说，主要有下面几个部分。

第一，先规划，再执行。
Agent 收到复杂需求后，先把目标拆成完整的执行计划，明确每个步骤做什么、步骤之间有什么依赖。如果某一步需要处理多个对象，就进一步拆成批次。计划保存到 Redis，再展示给用户确认。确认会绑定当前计划版本，后续如果计划发生实质变化，就需要重新确认，避免执行内容超出用户同意的范围。

第二，分轮执行，并自动续跑。
用户确认后，系统开始按计划执行。每轮都有执行时间预算，接近预算时就收口当前工作，保存已经完成的步骤、批次位置和结果，再安排下一轮执行。下一轮读取这些状态，从未完成的位置继续推进，正常情况下不需要用户反复回复“继续”。

对于图片生成这类异步操作，提交后会保存外部任务标识，并关联到当前任务和步骤。系统监控到结果后，再推进依赖这个结果的后续工作。

第三，把进度保存在服务端。
Redis 中保存任务状态、计划版本、执行位置和操作结果。模型负责理解需求、规划和选择工具，具体能否推进、进度如何更新，由 Java 服务校验。同时通过版本校验和运行租约，限制并发执行，防止两个续跑请求同时处理同一段任务，或者旧请求覆盖新状态。

第四，支持任务控制和异常恢复。
暂停后不再推进新的工作；继续时读取已保存的进度；停止后终止后续推进；重试则结合失败原因和已有结果决定如何恢复。这些控制主要作用于后续执行，已经发到下游的请求不一定能立即撤回。

服务重启后，系统根据持久化的任务状态、待处理通知和运行租约，判断应该继续执行、恢复异步监控，还是等待人工处理。

第五，对写操作增加保护。
执行前检查任务是否建立、计划是否确认，以及本次操作是否属于合法执行范围。同时为计划内操作生成稳定标识并记录结果，降低重试导致的重复执行风险。如果请求已经发出，但无法确认下游是否执行成功，就先核对结果，必要时让用户介入。

这套机制的核心是：用服务端可持久化、可校验的状态管理复杂任务的执行过程。 普通的知识查询仍然直接在单轮中完成，只有需要跨轮执行、等待异步结果或恢复进度的任务，才进入这套机制。

3. 能举一个具体的例子吗，当用户输入一个复杂的任务时，当前的agent会怎么执行？

可以，以代码中已经实现的批量图片生成为例。前提是当前账号开放了图片生成权限，并且从网页端发起；你前面使用的纯知识问答 Agent 未必开放这项能力。

假设用户输入：

“帮我为这 20 个运营主题分别生成一张海报，每个主题独立生成，统一使用横版比例，最后把结果按主题对应展示。”

下面的回复和进度数字都是示意，实际以工具返回为准。

1. 主 Agent 识别需求，交给公共子 Agent 规划

主 Agent 判断这是多个独立对象的批量处理，需要统一管理进度，因此先交给公共子 Agent。

公共子 Agent 读取图片生成和长任务的处理规则，查询当前可用模型及支持的参数。主题描述、尺寸等必要信息不完整时，会先向用户补充确认。

这时只做规划所需的查询，还不会提交图片生成请求。

2. 创建完整计划，等待一次整体确认

前置检查通过后，系统创建任务，把 20 个主题及各自的生成参数保存为结构化批次，形成执行计划，例如：

“将为这 20 个主题分别生成一张横版海报。各主题独立提交，生成结果按原主题编号展示。是否确认执行？”

计划和当前版本保存到 Redis，任务进入等待确认状态。

用户回复“确认”后，系统确认的是这一版完整计划，正常执行时不再逐张询问。

3. 服务端按批次推进，保存真实进度

确认后，服务端校验任务状态和运行资格，再开始提交生成请求。

每提交一项，系统都会保存外部图片任务编号，并启动对应的结果监控，然后记录该项进度。

这里有一个关键区别：这 20 张图片相互独立，因此上一张提交成功并建立监控后，就可以提交下一张，无须等上一张生成完成。 当前代码的批量提交由服务端按计划推进。

假设本轮处理了前 8 项，就会保存类似这样的信息：

内容 保存的信息
整体目标 为 20 个主题分别生成海报
已完成提交 第 1～8 项
下一项位置 第 9 项
已提交任务 各项对应的外部任务编号
生成进度 由各自的异步监控跟踪

4. 一轮做不完，系统自动续跑

如果接近本轮执行时间预算，系统保存进度，安排后续执行。

下一轮重新校验状态后，从第 9 项继续。用户不需要再回复“继续”，也不会因为换了一轮请求就重新提交前 8 项。

如果任务量较小，一轮能够完成全部提交，就直接完成这一阶段，不会为了分批而强行拆成多轮。

5. 图片异步生成，结果按原编号展示

后台持续查询已经提交的图片任务。哪张先生成完成，就处理哪张的结果，同时保留“原主题编号—图片任务—结果链接”的对应关系，避免完成顺序不同导致图片配错主题。

反馈时会区分：

“20 项生成请求已全部提交，部分图片仍在生成中。”

和：

“对应图片已生成，可以查看结果。”

提交完成和生成完成是两个不同阶段。 不能仅因为拿到了任务编号，就告诉用户图片已经生成成功。

6. 中途异常时，根据已有记录处理

例如第 9 项提交时发生网络超时：

  • 如果能确定请求尚未发出，可以根据失败原因安排恢复。
  • 如果请求已经发出，但不知道下游是否受理，就记录为结果不确定，先核对，避免重复生成。
  • 如果服务重启，则根据 Redis 保存的任务进度和监控记录恢复，核对运行状态后继续处理。

用户中途说“暂停”，系统会停止继续推进新的提交；已经提交到图片服务的任务可能仍会生成。之后说“继续”，系统再从保存的位置恢复。

这个例子里，长任务机制管理的是完整计划、批量提交进度以及跨轮恢复；异步监控管理的是每一张图片提交之后的生成结果。如果需求变成“先生成图片，再基于生成结果继续编辑”，后续步骤就必须等前面的真实结果返回后才能执行。

4. 当前系统是如何识别一个任务是复杂任务还是简单任务的？

当前系统采用“代码规则识别明显的多项任务 + 模型判断步骤依赖和单轮可完成性 + 执行时预算兜底”的方式。 它没有一个统一的复杂度评分，也不是单纯按照输入字数或工具调用次数判断。

这里的“复杂”，主要指需要统一管理执行计划、跨轮推进或等待异步结果的任务。一个问题即使需要搜索多份文档，只要本轮可以可靠完成，也不一定要创建长任务。

1. 先通过代码规则识别明显的多项处理请求

进入 Agent 执行前，服务端会检查用户消息和图片附件，主要组合判断两类信息：

  • 是否要求逐项处理：例如“分别”“各自”“逐个”“批量”“分批”等表达。
  • 是否确实有多个处理对象：例如存在多张图片、明确的数量，或者至少两条编号清单。

例如：

“为这 20 个主题分别生成海报。”

同时包含“20 个”和“分别生成”，会命中多项任务规则。

“把这几张参考图融合成一张海报。”

虽然有多个输入，但目标是一个合成结果，代码中有相应排除规则，避免仅凭附件数量就认定为多个独立任务。如果它还有其他复杂依赖，则再由模型判断。

命中规则后，服务端会要求先进入规划流程。 主 Agent 不能直接把请求拆成多个普通业务委托来执行；执行守卫会拦截这种调用，要求先委托公共域创建并保存完整计划，等待用户确认。

这部分依据是请求判断逻辑和首次规划约束。

2. 没有命中明显规则的任务，由模型结合业务流程判断

有些复杂任务没有“批量”等明显表达，甚至只有一个处理对象。例如：

“先生成一张图片，再基于生成结果继续编辑，输出最终版本。”

它虽然只有一个目标，但后一步必须消费前一步的异步生成结果，无法在当前请求里同步取得全部依赖。主 Agent 的提示词和图片工作流因此要求：在第一次提交生成请求之前，就建立覆盖完整依赖链的计划，并取得整体确认。

模型判断时参考的因素包括：

  • 输入规模和需要处理的对象数量；
  • 步骤之间是否存在依赖；
  • 工具耗时和是否需要异步等待；
  • 返回结果的体量；
  • 是否涉及产生实际影响的操作；
  • 当前一轮剩余的执行预算。

反过来，“先搜索规范，再打开文档，最后总结”虽然也有多个步骤，但依赖能够同步获取、本轮可以可靠完成，就可以直接执行。

这部分属于模型遵循提示词和工作流的语义判断，不能说服务端已经能确定性识别所有复杂需求。 明显多项任务有代码规则约束，任意自然语言依赖的理解仍然存在模型判断边界。

依据见主 Agent 的判断要求。

3. 执行过程中，用实际耗时做兜底

一开始认为能在单轮完成，也可能遇到下游响应慢、结果比预期大等情况。因此系统还会跟踪本轮执行预算。

预算到达后，代码会限制新的业务调用，给进度保存和收尾留出空间。工作流要求 Agent 根据实际完成数量、耗时、失败和异步等待情况，重新评估剩余工作：

  • 保守估计再一轮能够完成，可以安排一次普通续跑。
  • 预计还需要多轮，则建立或修订完整长任务计划，取得用户确认。
  • 一次普通续跑之后仍未完成，要求升级为长任务，避免无限串联普通续跑。

这里要区分：预算限制由代码执行，剩余工作量的评估和规划仍有模型参与。

4. 判断需要长任务，不代表一定要使用批次

“计划、步骤、批次”并不是每个复杂请求都必须具备的三个层级：

请求特点 处理方式
单轮可完成的查询、分析 普通 Agent 流程
需要跨轮或等待异步依赖 创建完整计划，按步骤推进
多个参数已确定、相互独立的同类操作 在步骤中使用批次，前提是服务端已有对应批次执行器
同时包含独立操作和依赖步骤 批次与普通步骤组成混合计划

所以，这个设计既要判断“需不需要长任务”，也要进一步判断“哪些工作适合批次执行”。依赖上一阶段图片 URL 的后续编辑，就不能提前伪装成参数完整的独立批次。

面试时可以这样回答：

我们采用规则和模型结合的方式。服务端先识别明显的多对象、逐项和批量处理需求，命中后通过执行守卫强制先规划，不能直接执行业务操作。对于没有明显批量表达的任务，由主 Agent 根据步骤依赖、异步等待、工具耗时和单轮预算判断是否需要长任务。例如单次知识查询一般直接完成，但先生成图片、再消费生成结果继续编辑，就需要提前建立完整计划。执行过程中还会根据实际预算重新评估，避免最初判断过于乐观。判断需要长任务后，再根据工作是否独立、参数是否完整、有没有对应批次执行器，决定使用普通步骤还是结构化批次。

5. 将复杂任务抽象为计划、步骤和批次：计划、步骤和批次具体是怎么抽象的？

这三个概念分别管理不同范围：计划描述整个任务，步骤描述一个业务阶段，批次描述某个阶段里可以重复执行的同类工作。 在当前代码中，计划包含有序步骤，每个步骤可以选择携带一组批量工作项，并不是所有步骤都有批次。

可以先看它们的对应关系：

层级 解决的问题 主要内容
计划 整个任务要做什么，用户同意了什么 整体目标、完整步骤列表、计划版本、确认版本
步骤 当前正在完成哪个业务阶段 标题、说明、所属业务域、是否产生实际影响、是否等待异步结果
批次 这个阶段如何处理多个同类对象 已注册的业务动作、每个对象各自的执行参数

1. 计划：把用户需求变成一份可以确认、保存和恢复的执行方案

例如用户说：

“为这 20 个运营主题分别生成一张横版海报。”

Agent 先完成模型参数等必要查询，再创建任务，提交完整计划。

计划会明确：

  • 整体目标是为 20 个主题分别生成海报；
  • 需要执行哪些业务步骤；
  • 每个步骤具体做什么；
  • 本次计划的版本，以及用户确认的是哪个版本。

它不只是回复给用户的一段文字。服务端会解析、校验并保存计划，执行时读取这份已保存的内容。 用户调整了实质要求，需要修订计划、更新版本，并重新确认。

从代码结构看，目前没有单独的“计划表”或独立计划对象，而是由一份 Redis 任务记录同时保存计划内容和执行状态。

2. 步骤：按业务阶段拆分，不按每次模型调用拆分

一个步骤表示需要完成的业务阶段，例如：

“为全部主题提交图片生成请求。”

这个步骤需要说明由哪个业务域处理，是否会产生实际操作，以及完成条件是什么。

步骤不等于一次工具调用，也不等于一轮聊天请求。 一个步骤可能需要处理很多对象，跨多轮才能完成；也可能只提交一个异步任务，但需要等待结果才能进入下一步。

例如另一个需求：

“先生成一张基础海报，再基于生成结果编辑出夜间版本。”

可以拆成两个有先后关系的步骤：

  1. 生成基础海报，等待真实结果返回。
  2. 使用前一步返回的图片，生成夜间版本。

当前实现主要通过有序步骤列表、当前步骤位置和异步等待状态管理这种顺序关系。它没有实现任意依赖关系的通用工作流图，因此面试时不宜描述成支持任意 DAG 的工作流引擎。

3. 批次：把同一个步骤中的重复操作，表示为“动作 + 工作项列表”

回到“20 个主题分别生成海报”的需求，不需要把每个主题都展开为一个高层步骤。可以在“提交海报生成请求”这个步骤里，保存 20 个独立工作项。

每个工作项都必须携带自己的完整业务参数。不能只写“剩下的照着第一张做”，让模型在续跑时重新猜测。

服务端收到计划后，会检查批量动作是否有对应执行器、每个工作项的参数是否合法。目前明确实现了结构化批次执行的是图片生成／编辑提交，并不是任意工具都能自动批量执行。

另外，依赖前一步结果的操作不能提前放进静态批次。例如第二张图片必须使用第一张生成后的 URL，这个 URL 在规划时还不存在，就需要作为后续依赖步骤处理。

4. “计划里的批次”和“每轮实际处理多少项”需要区分

计划里保存的是完整的 20 项工作，不要求模型提前写死“分成四批，每批五个”。

实际执行时，由服务端决定本轮处理范围。当前图片提交执行器的上限是一次处理最多 5 项，同时还会检查执行时间预算，预算不足时可以更早结束。

每成功处理一项，就保存结果和下一项位置。例如：

执行阶段 步骤 下一项位置
尚未执行 提交图片任务 第 1 项
成功提交前 5 项 仍是同一步骤 第 6 项
下一轮成功提交 5 项 仍是同一步骤 第 11 项
全部提交完成 当前步骤完成 推进下一步骤或结束计划

因此，执行轮次和业务步骤不是一一对应的。同一个步骤可以跨多轮推进，续跑读取服务端保存的位置。

在这个例子里，“该步骤完成”表示全部图片请求已成功提交并建立对应监控；图片最终生成完成，由各自的异步结果链路继续处理。

5. 谁负责抽象，谁负责保证它可以执行？

主要分工是：

  • Agent：根据需求和业务工作流，生成完整步骤，以及批量工作项的业务参数。
  • Java 服务：解析和校验计划、规范步骤编号、检查批次执行器、维护版本和执行位置、记录实际结果。
  • 用户：确认完整计划，明确授权范围。

对应代码可以看任务与计划模型、计划解析校验和批次推进逻辑。

面试时可以这样说：

我把复杂任务分成三个层级：计划管理整体目标、完整步骤和用户确认范围；步骤表示有明确业务含义的执行阶段；对于步骤内参数完整、相互独立的同类操作，再抽象为一个业务动作和多个工作项。Agent 负责生成业务计划，服务端负责校验和持久化。执行时由服务端控制每轮处理量，逐项保存结果和游标，所以一个步骤即使跨多轮执行，也能从明确的位置继续推进。

6. 并基于 Redis 持久化任务状态、计划版本、执行游标和操作结果：具体介绍一下是怎么持久化的？

当前实现是：为每个长任务保存一份完整的“任务检查点”，序列化成 JSON 写入 Redis；每次计划、进度或状态变化时，通过带版本校验的 Lua 脚本更新。 它不是等任务结束才保存，而是在执行中的关键节点持续保存。

可以从“存什么、什么时候存、怎么保证一致性”三个方面理解。

1. 一份任务记录保存计划和当前执行现场

每个任务都有独立编号，Redis 按“用户 + 会话 + 任务编号”定位这份记录。例如，下面是简化后的示意：

这份 JSON 主要包含：

内容 保存的信息
任务归属与目标 用户、会话、任务编号、整体目标
完整计划 有序步骤，以及步骤中的批量工作项
计划确认 当前计划版本、用户已经确认的版本
运行状态 等待确认、执行中、暂停、等待异步结果等
执行进度 当前步骤、批次下一项位置、进度摘要
操作信息 当前操作标识、外部任务编号、失败原因
恢复信息 当前运行轮次、租约、待处理续跑通知、异步任务关联

底层使用 Redis String 保存整份 JSON，更新时也是替换完整快照。 并不是把每个 Java 字段分别写成 Redis Hash 字段。

此外，还有一些配套数据：用 Set 保存当前会话的活动任务编号，用独立 String 保存当前运行标识；通知则使用有序集合和 Hash 保存调度索引及内容。

依据见任务存储实现。

2. 在关键节点保存，不依赖模型自己“记住”进度

以“分别生成 20 张海报”为例，保存过程如下：

时间点 持久化内容
创建任务 任务目标、归属、初始状态、初始版本和期限
提交计划 完整步骤、20 项业务参数、计划版本，状态变为等待确认
用户确认 记录确认版本，更新任务状态并安排后续执行
开始一轮 保存本轮运行标识和租约
每项操作之前 保存操作标识和当前处理位置
下游受理之后 尽早保存下游返回的任务编号
本项处理完成 保存结果摘要，推进到下一项
一轮结束 保存剩余进度，必要时同时写入续跑通知
暂停、停止或失败 保存新的状态以及恢复、核对所需信息

例如第 5 项提交成功后，系统会保存“前 5 项已提交”的真实结果，把下一项位置推进到第 6 项。

下一轮读到的是这份状态，不需要模型从聊天记录中推断“刚才好像做了五个”。

3. “操作结果”保存的是恢复所需的信息

这里需要准确区分：当前并不是给每一次操作建立一条永久、独立的结果流水。

任务检查点主要保存：

  • 当前尚未收口的操作标识和外部结果引用；
  • 已完成工作的结果摘要；
  • 异步监控关联；
  • 失败原因和下一步处理方向。

例如图片提交成功后，保存的是外部图片任务编号；批次推进时，会把每项提交结果累计到进度摘要中。图片文件本身不存进任务检查点。

这样，即使后续发生异常，也有依据查询已提交任务，而不是直接再次生成。当前快照和摘要都有大小限制，因此它也不能替代无限量的业务审计日志。

4. 通过版本号防止并发覆盖

系统有两种用途不同的版本：

  • 计划版本：标识用户确认的是哪一份执行方案。
  • 状态更新版本：标识这份任务快照更新到了哪一次，用来控制并发。

更新流程是：

  1. Java 服务读取任务及当前状态版本。
  2. 校验业务状态，构造更新后的快照，并将版本加一。
  3. Lua 脚本在 Redis 内比较“当前版本”和“本次预期版本”。
  4. 相等才写入，否则拒绝更新，要求重新读取任务。

例如两个请求都读到了版本 10，一个已经更新为 11，另一个再拿版本 10 提交，就会失败，避免把新进度覆盖成旧进度。

这就是乐观锁，也叫比较后更新。仅仅先在 Java 中判断版本再普通写入，会留下并发窗口，所以最后的比较和写入放在 Lua 中执行。

5. 状态更新和续跑通知一起写，减少中间状态

一次进度更新可能涉及多个 Redis 数据：

更新任务快照 → 调整活动任务索引 → 更新运行标识 → 删除旧通知 → 写入新续跑通知。

当前实现将这些需要协调的变更放进同一个 Lua 脚本，执行前检查版本、运行归属、数据类型和必要参数，减少“进度已经保存，但续跑通知没有写入”这类分步写入风险。

这些关联 Key 使用相同的 {用户:会话} 标记，使它们在 Redis Cluster 中落到同一个槽，支持脚本协调更新。

但这个原子范围只覆盖 Redis 内部。 调用下游生成图片和写入 Redis 不能组成同一个事务。因此，如果下游已经受理，而网关还没来得及保存编号就中断，仍然可能出现结果不确定，需要核对，不能承诺完全避免重复执行。

核心代码见带版本校验的更新脚本。

6. 设置有效期，恢复时重新读取并校验

任务数据不是永久保存。按当前默认配置：

  • 整体任务执行期限为 7 天；
  • 任务存储截止时间初始化为“执行期限再加 1 天”，也就是创建后约 8 天；
  • 等待计划确认的业务有效期为 30 分钟；
  • 单轮运行租约为 12 分钟。

这里的 30 分钟是确认有效期，不等于 Redis Key 的存活时间；“额外保留 1 天”也不表示任务一完成就重新计算一天 TTL。每次写入会根据已保存的存储截止时间计算剩余 TTL。

服务重启后，再按任务编号读取 JSON、还原任务对象，并检查状态、计划确认、运行租约和通知，决定继续执行、恢复监控还是先核对异常。

另外，简历里的“Redis 持久化”准确地说是把应用内任务状态保存到外部 Redis，使其不依赖网关进程内存。Redis 自身故障后能保留多少数据，还取决于 Redis 集群的复制及 AOF/RDB 配置；这部分不能仅凭当前应用代码保证。

面试时可以这样概括：

我为每个长任务维护一份 Redis 检查点，用 JSON 保存完整计划和当前执行状态。在计划提交、用户确认、操作前后和轮次结束等节点持续更新。更新采用版本校验加 Lua 脚本，把任务快照、运行标识和续跑通知协调写入，防止并发覆盖和状态脱节。恢复时读取检查点，根据已确认计划、步骤位置、批次游标及外部任务引用继续处理；对于下游调用与本地保存之间的不确定窗口，则先核对结果。

7. 什么叫做用户的一次确认？

“用户的一次确认”，指用户在任务开始执行前，对完整执行计划作一次整体授权。 后续系统在这份计划范围内分步骤、分批次执行，正常情况下不用反复询问。

例如用户说：

“帮我为这 20 个主题分别生成海报。”

Agent 先完成必要的参数查询，保存计划，再向用户说明：

“将为这 20 个主题各生成一张横版海报，使用已选定的模型和参数，分批提交，结果按主题编号展示。是否确认执行？”

用户回复“确认执行”，系统就把当前计划版本记录为已确认，开始按计划推进。第一批完成后，第二批、第三批由系统自动安排，不需要用户每批都回复“继续”。

这次确认有明确范围：

  • 计划内正常执行和续跑：沿用这次确认。
  • 计划实质变化：例如增加主题、修改生成要求，需要重新确认。
  • 出现结果不确定、缺少信息等异常：可能需要用户介入。
  • 具体工具另有执行确认要求：还要遵守该工具的确认机制。

另外，如果当前会话有多个待确认任务，系统需要先明确用户确认的是哪一个，不能把一句“确认”当成对所有任务的授权。

所以，简历中更完整的意思是：用户确认当前版本的完整计划后，系统在授权范围内自动推进，无需按步骤或批次重复确认。

8. 当用户暂停本次任务的时候，我们是怎么做到agent也暂停的，以及是怎么恢复的？

我们这里的“暂停”，是暂停任务的后续推进，并保存执行进度。它不会把正在运行的 Java 线程、模型请求，或者已经提交给下游的任务瞬间冻结。恢复时，也是在新的执行轮次中读取保存的进度，接着处理。

结合当前代码，可以分成下面几个环节理解。

1. 用户说“暂停”后，先确定要暂停哪个任务

用户在对话中发送“暂停这个任务”，后端会识别这是任务控制指令，找到当前会话对应的任务，再修改任务状态。这个过程有明确的后端处理逻辑，不只是让模型在回答中说一句“好的，已暂停”。

如果当前会话里存在多个可操作的任务，系统需要先确定目标，避免暂停错任务。

这里有一个当前实现的限制：同一用户、同一会话的请求会串行处理，暂停请求也需要获得处理机会。 因此，它主要是在轮次之间、等待异步结果等阶段生效，不能理解成用户一发“暂停”，当前模型调用就立即中断。

2. 暂停时，把任务状态和已有进度一起保存下来

后端处理暂停时，主要做三件事：

  • 将任务状态改为“已暂停”，记录恢复时应回到的状态。
  • 保留已经确认的计划、当前步骤、执行位置、已完成操作的结果，以及已经提交的异步任务信息。
  • 清理当前执行轮次的有效标记，以及等待触发的后续执行通知。

例如，一个任务总共需要处理 20 个对象，已经完成前 5 个，并保存了执行结果。暂停后，系统仍然知道前 5 个已经处理过，后续应当从第 6 个附近继续判断，而不是重新从第 1 个开始。

这些变化通过 Redis 中的原子更新完成，避免出现“任务已经标记暂停，但下一轮执行通知仍然有效”的状态不一致。

对应实现见 任务暂停与继续处理。

3. 为什么状态改成暂停后，Agent 就不会继续执行？

因为后续执行需要通过后端的状态校验，不能只靠模型自己决定“我要继续”。

正常情况下，一个长任务执行完当前轮次后，会通过后续通知启动下一轮。暂停时，系统会撤销相关通知；即使旧通知因为延迟等原因又被消费，开始执行前还会重新检查任务状态、通知是否有效，以及计划是否已经确认。处于暂停状态的任务不会因此开启新的执行轮次。

此外，执行过程中准备新的写操作、记录操作结果时，也需要校验当前任务是否仍处于允许执行的状态，以及执行轮次和版本是否有效。旧轮次不能继续使用已经失效的身份推进任务。

所以，这套机制的核心是：

通过持久化状态和执行入口校验，阻止任务继续推进，而不是挂起一个一直运行的线程。

对应校验见 开启执行轮次前的检查。

4. 已经发出去的异步任务，会跟着暂停吗？

一般不会。暂停父任务，不等于取消下游已经接受的工作。

例如，Agent 已经向图片生成服务提交了生成请求，用户随后暂停任务。图片生成服务可能仍然继续生成，当前平台不会因为父任务暂停，就自动把下游计算也冻结。

对于与父任务绑定的异步结果，系统在投递结果、准备推进父任务时，会检查父任务是否暂停。如果已经暂停，这个结果不会直接把父任务重新唤醒。

可以理解为：下游可以把已经接到的工作做完，但父任务先停在这里，等用户继续后再处理后续流程。

5. 用户说“继续”后，如何恢复？

恢复时，系统首先读取 Redis 中保存的任务快照，然后根据暂停前的实际情况决定下一步，而不是一律重跑。

主要有几种情况：

  • 上一步已经完成，下一步尚未开始： 根据保存的执行位置，安排新的执行轮次，接着处理。
  • 已经提交异步任务，结果还没回来： 继续等待原来的异步任务，不重复提交。
  • 异步任务的监控需要恢复： 恢复对原任务的结果监控。
  • 某次操作是否成功还不确定： 先查询、核对原操作结果，再决定是否继续，避免直接重试造成重复执行。
  • 原本还在等待用户确认： 继续等待对应确认，“继续”不能绕过必要的计划确认或工具确认。

随后，系统创建新的执行轮次，让 Agent 根据持久化的计划、进度和结果继续工作。因此，恢复依赖的是 Redis 中的任务记录，不依赖原来的线程还活着，也不只依赖模型记住聊天历史。

6. 用一个具体例子串起来

假设用户要求生成 20 张图片，系统按每批 5 张推进。

第一批已经提交，提交结果和对应的异步任务信息也保存到了 Redis。用户在后续轮次启动前说“暂停”，系统就将任务设为暂停，并撤销后续推进通知。

此时，第一批已经提交的图片可能仍在生成，但系统不会继续提交第二批。

用户之后说“继续”，系统会先检查第一批的实际状态：

如果提交记录完整，就沿用原来的生成任务，按计划推进后续批次；如果存在某张图片是否提交成功的不确定情况，就先核对这次提交，而不是直接再生成一遍。

最后还要区分一个容易混淆的操作：网页上响应过程中的“停止生成”，当前实现主要是中断本次响应请求；它不等同于把长任务状态改成“已暂停”。 真正的任务暂停，需要经过前面这套任务控制流程。

9. 整个长任务执行流程是按照状态机的方式控制流转的吗？

是的，整个长任务执行流程可以理解为按照状态机控制流转。 当前实现是在业务代码中，通过任务状态、流转规则和执行前校验来实现，并没有引入专门的状态机框架。

不过，它也不只是维护一个“运行中／已暂停”的状态，而是把任务当前状态、执行进度，以及下一轮如何触发结合起来管理。

1. 状态表示“任务现在可以做什么”

一个长任务并不始终处于运行状态。例如：

  • 等待用户确认时，不能正式执行计划内操作。
  • 正在执行时，可以按照计划推进步骤和批次。
  • 等待异步结果时，需要等待或查询已经提交的任务。
  • 等待续跑时，可以通过后续通知启动下一轮。
  • 已暂停时，不能继续推进业务步骤。
  • 执行结果不确定时，需要先核对结果，避免直接重复操作。
  • 已完成、已取消等终态，不再继续执行。

这些状态既用于展示进度，也会实际约束后端执行。

2. 事件触发状态变化，但需要满足条件

推动状态变化的事件包括用户确认、暂停、继续，以及当前轮次结束、异步结果返回、执行异常等。

例如，用户发送“继续”，系统并不是直接把状态改成“运行中”，而是先检查任务暂停前停在哪里：

如果下一步还没开始，就安排续跑；如果已经提交了异步任务，就继续等待原任务；如果上一次操作的结果不确定，就先进入结果核对流程。

因此，可以把它理解为：

当前状态 + 触发事件 + 校验条件，决定下一个状态以及需要执行的动作。

3. 状态流转和实际执行是分开的

这是这套设计比较关键的地方。

任务进入“等待续跑”，并不代表 Agent 已经开始运行。 系统还需要生成后续执行通知。通知被消费时，再检查任务状态、计划确认情况、通知是否仍然有效等条件，满足后才创建新的执行轮次。

这样，即使一条旧通知延迟到达，只要任务已经暂停，或者通知已经失效，也不能重新启动任务。

相关逻辑可以看 任务控制与执行入口校验。

4. 状态机决定“能不能执行”，执行进度决定“从哪里继续”

这两个概念需要分开理解。

例如，两项任务都处于“已暂停”，但一个刚完成第一个步骤，另一个已经执行到第二个步骤的第三批。仅凭“已暂停”这个状态，无法恢复执行。

12. 长任务下的上下文在运行的过程中是如何保存的呢？

1. 聊天上下文：保存“之前说了什么、工具返回了什么”

它在关键动作发生时更新，例如：

提交计划 完整步骤、计划版本、待确认状态

写操作前 稳定操作标识、对应步骤和游标

1.2.2 AI想到的问题

  1. 为什么需要单独设计长任务机制，直接让 Agent 连续调用 Tool 不行吗？

参考回答：普通 Agent 更适合在一次请求中完成较短的推理和工具调用，但复杂运营任务可能包含多个依赖步骤、批量写操作和异步等待，通常无法在一轮对话中稳定完成。如果只依赖模型上下文，一旦请求超时、模型重新生成、服务重启或者用户中途暂停，就很难准确判断之前执行到了哪里，还可能重复调用写接口。因此我把任务计划、执行位置和操作结果持久化，由服务端负责确定性推进，Agent 主要负责理解目标、生成计划和调用受控工具。

  1. 整个长任务模块由哪些组件组成？各自负责什么？

参考回答：整体上可以分成五部分：任务服务负责状态流转和业务校验；Redis 存储负责持久化任务事实；批次协调器负责按照已保存的进度逐项执行；续跑机制负责在一轮结束后触发下一轮；执行守卫负责在工具真正调用前做安全检查。各层职责是分开的，模型不能直接修改任务状态，存储层也不决定业务流程。这样即使更换 Agent 或者服务实例，任务仍然能够按照同一套规则推进。

  1. 计划、步骤和批次是怎么建模的？

参考回答：计划表示用户确认的完整执行方案，步骤表示有先后依赖关系的业务阶段，批次表示某个步骤中需要重复处理的一组同类对象。例如“为 100 个内容创建运营配置”可以拆成数据校验、批量创建、结果汇总三个步骤，其中批量创建步骤再拆成多个小批次。每个批次完成后都会保存进度，因此发生故障时只需要从未完成的位置继续，而不是重新执行整个计划。

  1. 任务状态机包含哪些状态？

参考回答：从业务阶段看，状态可以分为计划生成、等待用户确认、等待调度、正在执行、等待异步结果、等待重试、结果核对、暂停以及终态。终态又包括完成、失败、取消和过期。状态机不仅用于展示任务进度，更重要的是限制允许执行的动作，例如计划未确认时不能执行写操作，结果不确定时只能查询已有结果，已经结束的任务不能再次启动。

  1. 为什么同时保存 planVersion 和 confirmedPlanVersion？

参考回答：一个表示当前最新计划，另一个表示用户实际确认过的计划。每次用户补充要求或者系统重新生成计划时，当前计划版本都会变化，原来的确认立即失效。任务开始执行前必须确认“用户确认的版本就是当前版本”，从而避免用户确认的是旧方案，系统实际执行的却是修改后的新方案。这本质上是把用户授权和计划内容绑定在一起。

  1. “用户一次确认后自动续跑”是怎么实现的？

参考回答：用户确认完整计划后，系统会保存确认结果并创建一条续跑事件。执行器收到事件后读取最新任务状态，完成当前步骤或当前批次，再把新的执行位置和结果写回 Redis。如果后面还有工作，系统继续创建下一条续跑事件；如果需要等待异步结果，则暂时停止执行，结果返回后再恢复。因此用户只需要确认一次，后续推进由持久化状态和内部调度驱动。

  1. beginRun 为什么需要传入 notificationId？

参考回答：可以把它理解为一次性执行凭证。系统只有在收到与当前任务匹配的续跑事件时，才允许启动新一轮执行；已经消费过的事件、旧计划产生的事件或者重复投递的事件都会被拒绝。这样即使通知发生重复或乱序，也不会轻易启动两个相同的执行轮次。通知消费和任务状态更新还需要原子完成，避免通知已消费但任务没有真正进入运行状态。

  1. version、runId 和 runLeaseUntil 分别解决什么问题？

参考回答：任务版本解决并发覆盖问题，保证只有基于最新状态的请求才能保存；运行轮次标识用于区分当前执行和历史执行，避免上一轮的迟到结果污染新一轮；运行租约则解决服务异常退出后任务一直显示“执行中”的问题。租约过期后，系统会重新判断任务应该安全重试、等待已有异步结果，还是进入结果核对。三者分别处理并发、隔离和故障恢复。

  1. Redis 中的并发更新是怎么保证原子的？

参考回答：保存任务时会同时校验任务版本和当前运行轮次，只有二者都符合预期才允许更新。具体通过 Redis Lua 脚本，把任务内容、运行占用、活动任务索引和续跑通知放在同一次原子操作中完成。如果版本已经变化，说明有其他请求率先更新了任务，当前请求就会失败并重新读取最新状态。这样可以避免先写任务、再写通知过程中出现一半成功、一半失败。

  1. 批次任务怎样避免重复项、漏项和跳项？

参考回答：批次执行位置由服务端维护，而不是让模型自行描述。每一项执行前先记录当前要处理的最小操作单元，调用业务接口后再记录真实结果，结果保存成功后才推进到下一项。如果业务调用失败且确定没有产生副作用，就保留当前位置等待重试；如果是否成功无法确认，就停在当前位置先核对结果。这样可以尽量避免跳过数据，也不会因为模型重试而直接重复整批操作。

  1. 为什么每轮不把整个批次全部执行完？

参考回答：大批量操作可能超过模型单轮时间、服务请求超时或者下游接口承载能力。按固定大小拆分后，每轮只处理有限数量的数据，可以控制执行时间、上下文长度和下游压力。每个小批次也是一个恢复点，用户暂停或者服务异常时，最多只需要处理当前最小单元的不确定性。剩余数据由续跑机制自动进入下一轮。

  1. recordOutcome 为什么不允许模型直接提交任意状态？

参考回答：模型输出具有不确定性，如果允许它直接把任务修改为完成、失败或跳到任意步骤，就可能绕过计划和确认流程。因此模型只能上报有限类型的执行结果，例如取得进展、完成步骤、可重试失败或者结果不确定。最终应该进入什么状态、是否推进步骤、是否创建续跑事件，都由服务端结合真实任务状态计算。这样把业务状态机控制权留在确定性代码中。

  1. 暂停、继续和停止分别如何实现？

参考回答：暂停会保存当前执行位置和暂停前的阶段，同时停止启动新的执行轮次；继续时重新读取最新任务状态，判断应该继续正常执行、恢复异步监控，还是先核对未确认的操作结果。停止会把任务设置为终止状态，并清理后续调度，使系统不再执行剩余步骤。需要注意，暂停和停止只能阻止尚未发起的操作，无法撤销已经到达下游系统的请求。

  1. 重试失败和副作用结果不确定有什么区别？

参考回答：如果能够确定请求没有发送出去，例如参数校验失败或执行前就发生异常，那么重试不会造成重复写入，可以进入普通重试流程。如果请求已经发送，但因为超时或断连没有收到结果，就不能判断下游是否执行成功，此时直接重试可能产生重复数据。系统会把这种情况转入结果核对流程，优先通过查询接口、业务唯一键或者异步任务编号确认真实结果。

  1. 服务重启后，任务是如何恢复的？

参考回答：任务恢复依赖 Redis 中保存的计划、当前步骤、批次位置、操作记录、异步任务信息和待处理通知，而不依赖 JVM 内存。服务恢复后，在任务再次被加载或续跑事件被处理时，会检查上一次执行是否已经结束以及运行租约是否过期。如果没有发起写操作，可以从当前位置重试；如果已经发起写操作，则先核对结果；如果已经提交异步任务，则恢复对原任务的监控，而不是重新提交。

  1. 如果服务在业务接口成功后、保存 checkpoint 前宕机会怎样？

参考回答：这属于最典型的分布式不确定窗口：下游可能已经成功，但本地没有保存成功结果。如果直接重试，可能产生重复写入；如果直接标记成功，又没有证据。因此系统会在调用前先保存稳定的操作标识，恢复后根据这个标识查询下游结果。下游支持幂等键或结果查询时可以自动处理，否则就需要停止自动执行并转人工确认。

  1. 异步任务是怎样与父任务关联的？

参考回答：提交异步任务时，系统会同时保存外部任务编号以及它所属的父任务、计划版本、步骤和批次位置。异步结果返回后，必须验证这些关联仍然有效，才能推动父任务继续执行。这样可以避免旧计划产生的迟到结果误更新新计划，也能在服务重启后继续查询原来的异步任务，而不是重复创建一个新任务。

  1. 怎样防止任务无限自动续跑？

参考回答：系统会判断每轮执行是否产生了真实进展，例如步骤是否推进、批次位置是否变化或者是否获得了新的结果。如果连续多轮没有有效进展，就停止自动续跑，转为等待用户重试或人工处理。同时任务还有整体执行期限，超过期限后不再发起新的写操作。这样可以避免模型或下游异常导致任务持续空转。

  1. 为什么选择 Redis，而不是数据库或 MQ？

参考回答：长任务运行期间需要频繁读取和更新状态，还要完成版本校验、运行占用和续跑通知的原子更新，Redis 的低延迟和 Lua 脚本比较适合这种运行态协调。数据库更适合长期审计和复杂查询，MQ 更适合独立的可靠消息投递，但单独使用它们仍需要解决任务状态与消息之间的一致性。当前方案以 Redis 管理运行状态，如果业务要求更强的持久性，可以把关键操作流水和最终结果额外写入数据库。

  1. 这套机制能保证 exactly-once 吗？

参考回答：不能宣称跨系统严格的 exactly-once。平台内部可以通过版本控制、执行位置、稳定操作标识和结果记录降低重复执行概率，但如果下游已经写成功、本地却因为网络问题没有收到响应，平台无法凭自身状态证明下游结果。真正实现端到端幂等，需要下游接受并保存统一的幂等键，或者提供可靠的结果查询接口。当前更准确的描述是“可恢复执行和重复风险控制”。

  1. 执行守卫在长任务里解决了什么问题？

参考回答：提示词只能告诉模型应该怎么做，但不能保证模型一定遵守，特别是在模型重试、上下文压缩或者工具并行调用时。因此系统会在工具真正执行前检查任务是否已经创建、计划是否已经确认、当前是否具有有效执行资格，以及写操作是否已经完成必要准备。在结果核对阶段还会禁止调用写工具，防止把“查询结果”错误地变成“再次执行”。服务层会再做一次状态校验，形成双层保护。

  1. 你认为当前方案还有哪些改进空间？

参考回答：第一，可以推动所有写接口统一支持幂等键，让平台生成的操作标识真正贯穿下游系统。第二，可以把关键操作流水写入数据库，增强审计、追踪和长期恢复能力。第三，需要补充 Redis 故障、重复通知、网络超时和服务宕机等故障注入测试。第四，可以增加任务积压、租约超时、结果核对数量和无进展轮次等监控指标，方便及时发现异常任务。

2. 为计划内写操作分配固定标识并记录执行结果，降低模型重试及网络异常导致的重复执行风险；构建执行守卫在工具调用前校验任务、计划和用户确认状态，防止 Agent 绕过确认直接执行批量操作

2.1 具体实现方式

一、问题背景

Agent 与普通后端接口不同：模型可能因为超时、上下文续跑或服务重启重复生成同一个 Tool 调用；网络异常时，也无法仅根据“没有收到响应”判断请求是否已经到达下游。如果直接重试写操作，可能重复创建卡片、重复提交图片任务或重复回滚生产任务。

因此，这部分工作的核心不是简单增加一个重试，而是把写操作改造成受服务端状态机约束的协议：

模型负责选择动作和描述结果，服务端负责判断“现在是否允许执行、是否可以重试、下一状态是什么”。

  5. 业务 Tool 在真正发送 HTTP、RPC 或 MCP 请求前调用 markSideEffectAttempted。

七、执行守卫

LongTaskExecutionGuardMiddleware.java 在 next.apply(input) 之前检查 Tool 调用，因此约束不是仅靠 Prompt 提醒。

守卫主要限制：

  • 多项任务必须先加载长任务工作流、创建任务、提交完整计划并等待整体确认。
  • 任务已经创建后，下一次调用只能提交该任务的计划。
  • 计划保存后不能继续调用业务 Tool，只能向用户展示计划并等待确认。
  • 任务状态 Tool 和业务 Tool 不能在同一批执行。
  • 单次 reasoning 最多执行一个未声明为并行安全的业务调用。
  • 图片提交必须独占批次，并且副作用步骤必须先准备 operationId。
  • 核对轮次只能调用显式声明为 reconciliation-safe 的只读核对或监控恢复能力。
  • 超出本轮执行预算后，禁止开启新运行轮次和新业务写操作。
  • 系统续跑通知的 ID、类型和目标任务必须与 checkpoint 一致，旧通知不能启动新轮次。

守卫在 supervisor 和 domain 两层生效：前者限制跨业务域委托，后者限制叶子 Tool。Tool 的 planning-safe、reconciliation-safe、parallel-safe 等属性由 DomainAgentSupport 统一组装。

确认记录也通过 Lua 原子完成注册、PENDING -> EXECUTING 抢占和最终结果保存，避免两个确认请求同时取得执行权。

十、能力边界

这套实现保证的是平台内部的稳定关联、防止盲目重放和可恢复核对，不应表述为“所有外部写操作严格 exactly-once”。当前 operationId 并没有统一作为下游接口的幂等键传递；如果下游在请求成功后断网，平台仍需要依赖 operationRef、查询接口或业务流水核对真实结果。

另外，执行守卫防止的是任务协议越权，例如未规划、未确认、无运行租约或在核对轮次执行写操作。用户是否拥有某项业务权限，仍由 Tool 可见性、权限码和 Tool 自身权限校验负责。

面试时可以总结为：我把 Agent 写操作从模型自由调用改造成服务端约束的 Prepare-Execute-Record 协议，用计划版本、步骤和游标生成稳定 operationId；再结合副作用发出标记、结果分类、外部操作锚点、Redis CAS 和执行守卫，使请求未发出时可以安全重试、请求结果未知时只能先核对，从而降低模型重试、网络异常和并发续跑带来的重复写入与协议越权风险。

此时存在两种选择：

  • 不重新提交：可以避免这次重试带来的重复，但任务可能一直无法继续。
  • 重新提交：可以尝试完成任务，但如果上一次其实成功了，就会产生重复。

因此，对当前实现更准确的说法是：通过执行进度记录、未完成操作拦截和异常结果核对，降低重复执行风险；不能仅凭本地记录就宣称杜绝重复。

3. 执行守卫是什么？

执行守卫，就是放在模型发起工具调用与工具真正执行之间的一层后端拦截逻辑。 它根据当前任务的执行条件，决定这次调用能不能放行。

可以把它理解成“工具调用前的检查关卡”：

主要约束包括：

  • 需要先规划时： 要先创建任务并提交完整计划，不能直接执行批量业务操作。
  • 计划已经提交、正在等待确认时： 要先展示计划并等待用户确认，不能接着调用业务工具。
  • 执行计划内写操作时： 要先准备并保存当前操作的稳定标识，再调用对应工具。
  • 正在核对异常结果时： 只允许查询、核对或恢复监控，不能重新发起新的写操作。

如果不符合要求，守卫就阻止这次调用，并向 Agent 返回类似“请先提交完整计划”或“当前只能核对已有结果”的信息，引导它完成必要步骤。

这里需要区分两层保障：工具调用中间件负责拦截不符合流程的调用，任务服务还会在开启执行轮次、准备操作等入口检查计划版本、确认状态和执行身份。 两层配合约束执行流程。

4. 如何校验的任务、计划和用户确认状态？

具体是读取后端保存的真实任务状态，再判断当前是否满足执行条件。这里的校验分布在工具调用守卫和任务服务中，并不是每次调用工具都重新完整查询一遍 Redis。

1. 校验任务：是否真的存在，是否是当前目标任务

后端根据当前用户、会话和任务编号读取 Redis 中的任务记录。

如果记录不存在或已过期，就拒绝后续操作。对于任务控制和续跑请求，守卫还会检查：

  • 是否已经读取了目标任务的真实状态。
  • 本次操作的任务编号是否与已选定、已加载的任务一致。
  • 如果存在多个候选任务，是否已经明确选择目标。

所以，模型即使随便提供一个任务编号，也不能仅凭这个编号直接进入执行流程。

具体到当前项目，有两层配合：

在已接入守卫的受控批量执行链路中，通过执行前拦截和后端状态校验，阻止模型跳过计划确认直接操作。

2.2.2 AI想到的问题

  1. 这套机制主要解决什么问题？

参考回答：它主要解决两类风险。第一类是模型重试、请求超时或服务重启后，系统可能重复调用写接口；第二类是模型没有完成建任务、提交计划和用户确认，就直接执行批量写操作。我的处理思路是：写操作前先建立稳定身份，执行后保存结果；同时在工具调用层增加强制校验，把不符合流程的调用拦截在业务接口之前。

  1. 整体执行流程是什么？

参考回答：完整流程是先创建任务，再保存完整计划并让用户确认。任务进入合法运行阶段后，每个写操作都要先登记本次要执行的逻辑单元，再调用业务接口，最后根据真实结果记录成功、可重试失败或者结果不确定。只有结果保存成功后，系统才会推进批次位置或进入下一步骤。

  1. 为什么既需要稳定操作标识，又需要结果记录？

参考回答：操作标识只能说明“准备执行哪个逻辑操作”，不能证明这个操作是否已经成功。结果记录用于保存业务接口的真实返回、执行进度和下一步处理方式。两者结合后，系统恢复时才能判断应该直接继续、重新执行，还是先查询下游结果。如果只有操作标识而没有结果，任务仍然会停留在待核对状态。

  1. 什么叫“稳定操作标识”？

参考回答：稳定指的是同一个任务、同一个计划版本、同一个步骤和同一个批次位置，无论因为模型重试还是服务重启，计算出的操作标识都保持一致。不同计划版本、不同步骤或者不同批次项，标识则不同。这样系统可以区分“同一个操作的再次尝试”和“一个新的业务操作”。

  1. 稳定操作标识是如何生成的？

参考回答：代码会把任务身份、当前计划版本、步骤编号和批次位置组合起来，规范化后计算摘要。批次位置不会直接使用模型提供的任意文本，而是基于服务端保存的执行位置。计划变化后版本也会变化，因此旧计划和新计划中的操作不会错误地复用同一个标识。

  1. 为什么操作标识中不直接包含每次执行的运行轮次？

参考回答：因为运行轮次每次重试都会变化，如果把它作为稳定标识的一部分，同一个逻辑操作重试时就会生成新标识，失去防重意义。当前实现把“逻辑操作身份”和“本次执行轮次”分开保存：前者用于识别同一个业务操作，后者用于判断当前请求是否仍属于有效执行轮次。

  1. 为什么必须在调用业务接口之前生成操作标识？

参考回答：如果先调用业务接口，再保存操作标识，那么服务在两者之间宕机时，本地完全没有任何记录，却可能已经在下游产生了写入。提前保存后，即使调用过程中发生异常，系统至少知道当前存在一个尚未闭合的写操作，可以阻止盲目重试，并尝试通过下游业务标识查询真实结果。

  1. 准备操作时会做哪些校验？

参考回答：系统会检查当前任务是否处于有效运行阶段、当前步骤是否确实包含写操作、任务是否已经超过执行期限，以及是否存在上一次尚未核对完成的操作。如果已经有一个未闭合操作，就不能再准备新的写操作，必须先完成结果核对。这避免了多个不确定副作用同时存在，导致恢复逻辑无法判断。

  1. 写操作执行后记录哪些内容？

参考回答：主要记录当前操作对应的业务结果、批次执行位置、进展摘要、下游返回的业务引用以及下一步动作。对于异步任务，还会保存外部任务编号和轮询信息。这些信息的目标不是保存完整业务响应，而是保存足够支持恢复和核对的最小事实集。

  1. 为什么只允许记录有限的结果类型？

参考回答：模型不能直接决定任务应该进入任意状态，否则可能跳过步骤、提前结束任务或者绕过确认。当前实现只允许模型报告几类受控结果，例如取得进展、步骤完成、可重试失败、结果不确定、需要修订计划以及任务结束。服务端再结合当前任务状态计算真正的下一状态。

  1. 如何区分“可以重试”和“结果不确定”？

参考回答：关键是判断业务请求是否已经真实发出。如果在参数校验、权限检查或者调用前准备阶段就失败，可以认为没有产生副作用，允许安全重试。如果请求已经发给下游，但因为网络超时、连接中断或者响应解析失败没有拿到明确结果，就属于结果不确定，不能直接重试。

  1. 代码如何知道业务请求是否已经发出？

参考回答：具体业务工具会在真正调用 HTTP 或 RPC 接口之前标记“副作用已经开始尝试”。例如导航卡创建、生产任务回滚和图片提交等工具都在下游调用边界设置这个标记。发生异常时，上层根据该标记进行分类：尚未发起的按普通失败处理，已经发起但没有确定结果的进入核对流程。

  1. 网络超时后为什么不能直接重试？

参考回答：网络超时可能发生在下游处理之前，也可能发生在下游已经写成功、但响应返回失败之后。本地无法仅凭超时判断是哪一种情况。如果直接重试，可能创建重复数据或者重复修改业务状态。因此系统会保留操作标识和已有下游引用，先调用只读查询能力核对结果。

  1. 结果不确定后系统如何继续？

参考回答：任务会停止正常写入流程，切换到结果核对阶段。在这个阶段只允许读取任务状态、查询下游结果或者恢复已有异步任务监控，不允许再次执行写工具。如果确认原操作已经成功，就补录结果并继续计划；确认没有执行时，才能重新发起；仍然无法判断时，则等待人工处理。

  1. 如果业务调用成功，但保存结果失败了怎么办？

参考回答：这种情况不能对用户简单返回失败并允许再次执行，因为下游写操作可能已经完成。系统会保留已准备的操作信息，并尽量记录下游返回的业务引用。后续恢复时通过该引用核对真实结果；如果引用也没有保存成功，就进入更保守的不确定状态，禁止自动重复执行。

  1. 异步写操作如何记录结果？

参考回答：像图片生成这种操作，提交成功后不会立即产生最终结果。代码会先保存下游返回的任务编号，并把它与当前父任务、步骤和批次位置绑定，然后启动结果监控。即使监控进程中断，恢复时也只会重新监控原来的外部任务，不会再次提交一个新的生成任务。

  1. 为什么不能只通过 Prompt 要求模型遵守流程？

参考回答：Prompt 只能提供行为指导，不能成为副作用安全边界。模型可能因为上下文压缩、重试、错误推理或者并行工具调用而跳过流程。因此项目在 Tool 真正执行前增加了代码级守卫，只要任务状态、确认状态或运行条件不满足，就直接拒绝工具调用。

  1. 未创建任务时，守卫如何阻止批量写操作？

参考回答：系统会结合用户请求中的对象数量、编号列表、多图片输入以及“逐项处理”等语义，识别明显的多对象任务。一旦判定需要受控批量执行，当前请求只能先加载长任务工作流、完成必要的只读规划查询，然后创建任务。此时如果模型直接调用业务写工具，守卫会拒绝执行。

这里也存在一个边界：自然语言识别具有启发式性质，不能覆盖所有表达方式。因此代码还会结合已注册业务工具、调用数量和是否属于安全并行工具做第二层判断。

  1. 任务已经创建但计划还没提交时，会发生什么？

参考回答：任务创建成功后，守卫会把下一步限制为提交该任务的完整计划。模型不能继续加载无关能力、执行写操作或者只在自然语言中描述一个没有持久化的计划。只有计划经过服务端校验并成功保存，系统才会向用户展示并请求确认。

  1. 计划已经提交但用户尚未确认时，为什么仍然不能执行？

参考回答：计划提交只代表系统保存了执行方案，不代表用户已经授权执行。计划保存后，当前轮次会进入收口阶段，守卫禁止继续调用业务工具，只允许把完整计划展示给用户。用户确认后，系统还会核对确认的是不是最新计划版本，防止用户确认旧计划、系统执行新计划。

  1. 计划已经确认后，模型是不是就可以随意调用写工具？

参考回答：不可以。计划确认后还要由系统启动有效执行轮次，并限定当前唯一允许执行的步骤。对于有副作用的步骤，还需要先完成操作准备；如果任务已经暂停、取消、过期或者执行轮次失效，业务工具仍然会被拒绝。确认是必要条件，但不是唯一条件。

  1. 为什么不允许任务状态工具和业务工具在同一批调用？

参考回答：因为模型在发起业务调用时，必须基于任务状态工具返回的真实结果进行决策。如果两个调用同时提交，模型实际上还没有看到最新任务状态，就已经开始执行业务操作。项目要求先读取或更新任务状态，下一次推理再发起业务调用，从而形成明确的状态屏障。

  1. 为什么限制一次只能调用一个非并行安全的业务工具？

参考回答：多个写工具并行执行后，如果其中一部分成功、一部分超时，恢复时很难判断每个操作的真实结果，也难以确定批次位置。当前守卫默认只允许一个非并行安全调用，只有明确登记为可安全并行的只读或独立能力才能并行，并且还有数量上限。这种限制牺牲了一部分吞吐量，但显著降低了副作用恢复的复杂度。

  1. 结果核对阶段如何防止再次写入？

参考回答：结果核对会使用单独的运行模式，守卫只允许任务读取、结果查询和监控恢复等白名单操作。普通写工具和不匹配当前恢复类型的查询都会被拒绝。这样即使模型把“核对之前的结果”误解成“重新执行一次”，调用也无法到达业务接口。

  1. 整体计划确认和高风险工具确认有什么区别？

参考回答：整体计划确认表示用户同意执行完整任务方案；高风险工具确认针对的是某一次具体调用及其参数快照。对于需要单独确认的敏感工具，用户确认后只能执行保存下来的那份参数，不能由模型临时修改。重复确认会被识别为已经处理，不会再次执行工具。

  1. 模型重试或者两个请求并发执行时，如何避免重复推进？

参考回答：任务状态更新采用乐观并发控制，每次写入都必须基于读取时的版本。Redis 脚本会原子校验任务版本、当前执行轮次和相关操作信息，然后再更新任务和续跑通知。两个请求并发时，只有一个能保存成功，另一个必须重新读取状态，不能用旧结果覆盖新进度。

  1. 服务端批次协调器和执行守卫是什么关系？

参考回答：执行守卫负责回答“当前允不允许调用”，批次协调器负责回答“当前应该执行哪一项”。协调器从服务端保存的位置取出下一项，先准备操作，再调用业务执行器，最后保存结果。失败时不会推进位置，所以恢复后仍然处理当前项；成功保存后才进入下一项。

  1. 这套机制能保证所有写操作 exactly-once 吗？

参考回答：不能宣称跨系统严格 exactly-once。平台内部可以稳定识别逻辑操作、拒绝旧请求并保留结果核对信息，但如果下游成功而本地没有收到响应，最终仍然需要下游提供幂等键或者结果查询能力。更准确的说法是：系统显著降低重复执行和越权调用风险，并对不确定副作用提供可恢复的处理路径。

  1. 这套方案最大的取舍是什么？

参考回答：最大的取舍是用一定的执行复杂度和串行限制换取副作用安全。写操作前后都要持久化状态，部分工具不能并行，结果不确定时还需要额外核对，因此吞吐量会受到影响。但对于运营后台的批量写场景，可恢复性和避免重复修改通常比极致吞吐更重要。

  1. 当前方案还有哪些改进空间？

参考回答：第一，可以把稳定操作标识统一透传给所有下游，让下游真正按幂等键防重；第二，为关键写操作增加数据库审计流水，增强长期追踪能力；第三，完善工具副作用属性的统一注册，减少依赖自然语言识别；第四，补充并发请求、重复确认、结果保存失败和服务宕机等故障注入测试；第五，增加不确定操作数量、守卫拒绝原因和核对任务积压等监控指标。

3. 负责业务子 Agent 配置化改造，支持通过 Paladin 动态配置系统提示词、Tool、Skill 和权限码；实现配置解析、合法性校验、热更新及 Agent 缓存失效，降低新增业务域 Agent 的代码改动成本

十、Agent 缓存与失效

主 Agent 使用 Caffeine 缓存：

用户权限集合先过滤为“配置中实际绑定过的权限”，排序后计算指纹。权限完全相同的用户可以复用同一套 Agent 装配结果，避免为每个 userId 重复创建 Agent。

当前配置版本没有直接拼入缓存 key，而是通过以下方式保证一致性：

  1. createSupervisor 在读锁内读取快照并访问缓存；
  2. 配置更新在写锁内替换快照；
  3. 替换成功后调用 supervisorAgentCache.invalidateAll()；
  4. 下一次请求基于新快照重新构建 Agent。

读写锁避免出现“更新线程刚清完缓存，另一个线程又把旧快照 Agent 放回缓存”的竞态。

用户权限配置变化时，同样在写锁内刷新权限快照并清空 supervisor 缓存。userFingerprintCache 只缓存“权限集合到指纹”的纯计算结果，无需随业务配置失效。

十一、新请求如何生成 Agent

新请求调用 createSupervisor 后：

  1. 读取当前 DomainConfigSnapshot；
  2. 根据用户权限计算权限指纹；
  3. 按指纹查找 supervisor Agent 缓存；
  4. 遍历公共域和所有已启用业务域；
  5. 调用 DomainAgentSupport.createSpec 过滤 Tool、Skill；
  6. 无可见能力的域直接跳过；
  7. 为可见域创建 SubAgentTool；
  8. 将其注册为 delegate_to_xxx；
  9. 根据实际 delegate 列表生成主 Agent 路由 Prompt。

子 Agent provider 每次委托都会创建新的 ReActAgent，但其 Tool/Skill 集合和 Prompt 来自当前已校验配置及用户权限。

热更新影响后续请求，不会在一个正在执行的请求中修改现有 Agent 对象，也不会偷偷改变已经确认的长任务计划。

十三、能力边界

这项改造实现的是“业务子 Agent 编排配置化”，不是让配置中心动态上传和执行任意代码：

  • Paladin 只能选择已经部署的 Tool/Skill；
  • 新增全新业务能力仍然需要开发、测试和发布；
  • SYSTEM 能力不能被业务域配置引用；
  • 用户基础权限不会因为配置了 permissionCode 自动获得；
  • systemPrompt 可以动态更新，但不能绕过 Toolkit 的权限过滤；
  • 业务域坏配置保留旧快照；用户权限配置解析失败则按当前实现降级为空权限映射，属于 fail-closed 策略；
  • configDigest 主要用于日志观测，不承担安全校验或缓存键职责。

3. 实现配置解析、合法性校验、热更新及 Agent 缓存失效：这些分别是怎么做的？

这四项是一条完整的生效链路：把 Paladin 中的配置变成程序能使用的 Agent 定义，检查是否可用，再替换运行时配置，并清掉旧的 Agent 缓存。

1. 配置解析：把配置文本转换成可装配的 Agent 定义

Paladin 中保存的是一份 JSON，里面包含多个业务域，以及各自的提示词、工具、Skill 和权限码。

后端使用 Jackson 将 JSON 转成 Java 配置对象，然后逐个处理启用的业务域。

对于工具和 Skill，配置里填写的是能力标识。后端维护了一份能力目录，将这些标识映射到已经部署的 Spring Bean。例如，配置引用“知识搜索工具”，程序会找到对应的工具实例，生成工具与权限的绑定关系。

最终得到的是一组经过处理的业务域定义，可以交给公共装配逻辑创建 Agent。

所以，这一步不只是“读取几个字符串”，还包括把配置中的能力引用解析成程序中实际存在的能力。新增底层工具仍然需要开发、部署，不能只靠配置凭空生成。

对应实现见 配置解析器。

2. 合法性校验：确保配置能够正确、安全地装配

解析过程中会同步做几类检查：

校验类型 具体检查
基础结构 JSON 能否解析，业务域列表是否存在，是否明确配置启用状态
必填项与格式 Agent 标识、描述、提示词是否为空或超长，名称是否符合规则
重复与冲突 Agent 标识是否重复，工具是否重复，Tool 与 Skill Action 的名称是否冲突
能力有效性 引用的 Tool、Skill 是否已经注册，工具是否有有效方法，Skill 资源是否可读取
系统边界 业务域不能引用系统专用能力，也不能使用保留的 Agent 标识
权限绑定 每项能力必须配置非空、格式合法的权限码

例如，把工具标识拼错，或者给业务域配置了系统专用的长任务工具，都会拒绝这次配置。

权限码这里检查的是绑定是否完整、格式是否符合要求；它不会因为配置里写了某个权限码，就给用户授予这个权限。实际组装时，仍然需要根据用户已有权限筛选能力。

当前采用的是整份配置校验通过后才替换。如果其中一个启用的业务域配置错误，这次更新不会部分生效。

3.2.2 AI想到的问题

  1. 为什么要做业务子 Agent 配置化？

参考回答：改造前，每增加一个业务域，都需要新增一个 Java Agent 类，并在类中静态维护提示词、Tool、Skill 和权限绑定。随着业务域增加，这些类的结构高度重复，能力调整或权限变化也需要重新发布。配置化之后，已有能力之间的组合可以通过 Paladin 调整，新增业务域主要变成配置工作，Java 代码只保留通用装配逻辑和实际能力实现。

  1. 改造前后的架构有什么区别？

参考回答：改造前是每个业务域对应一个静态 Java 类，由这个类决定提示词和能力集合；改造后由 Paladin 提供业务域配置，配置解析器将其转换为统一的领域定义，再由 Agent 工厂根据当前用户权限组装对应的子 Agent。原来的活动、投放、创作激励等静态业务 Agent 类目前已经标记为废弃，公共域仍然固定在代码中，因为它包含任务状态、通知等系统能力。

  1. 哪些内容适合动态配置，哪些内容仍然保留在代码里？

参考回答：适合动态配置的是业务域开关、业务域标识、描述、基础系统提示词、Tool 和 Skill 的组合以及相应权限码。不适合配置化的是 Tool 的具体实现、下游接口调用、参数校验、风险确认规则和平台系统能力。也就是说，配置决定“组合哪些已部署能力”，代码决定“能力实际上做什么，以及是否安全”。

  1. 完整的配置加载流程是什么？

参考回答：服务启动时先注册 Paladin 配置监听器，然后读取当前业务域配置。配置经过 JSON 反序列化、字段校验、能力目录解析和权限绑定校验后，生成不可变的业务域快照。主 Agent 创建时读取这个快照，并根据当前用户实际拥有的权限过滤可见业务域和能力。Paladin 发生变化后，系统重新完成整套校验，成功后再替换快照并清理 Agent 缓存。

  1. 配置化后，新增业务域是不是完全不需要发版？

参考回答：不是。如果新业务域只是重新组合系统中已经存在的 Tool 和 Skill，可以主要通过配置完成；如果业务域需要新的下游接口或者新的业务能力，仍然要开发 Tool 或 Skill、编写测试并发布。配置化降低的是业务域装配和能力组合的改动成本，不是消除所有代码开发。

  1. 业务子 Agent 的配置中包含哪些核心内容？

参考回答：一个业务域主要包含是否启用、业务域标识、业务描述、系统提示词、Tool 列表和 Skill 列表。每项 Tool 或 Skill 通过能力标识引用已经部署的实现，同时绑定一个或多个权限码。业务域标识还会派生出主 Agent 调用该子 Agent 时使用的委托名称。

  1. 为什么配置中使用能力标识，而不是直接写 Java 类名？

参考回答：配置中心不应该感知 Java 包名和实现类，否则代码重构会直接破坏线上配置。当前代码通过能力目录把配置标识解析到已经注册的 Spring 能力实例，只允许使用系统已经部署和登记的能力。这样至少避免了配置通过反射实例化任意类，也可以在刷新阶段提前发现不存在的能力。

需要准确说明的是，当前实现中的能力标识实际来源于 Spring Bean 名称，因此仍然存在一定命名耦合。更完善的做法是通过专门注解或能力描述接口声明稳定 ID，使它不受 Java 类名和默认 Bean 命名规则影响。

  1. 为什么需要能力目录，直接从 Spring 容器按名称取 Bean 不行吗？

参考回答：能力目录不仅负责查找实例，还会建立能力标识和实现类型之间的双向索引，并检查同一种实现是否被多个标识重复注册。解析配置时，只有能力目录中的 Tool 和 Skill 才能使用。它相当于一个受控白名单，也为区分普通业务能力和系统能力提供统一入口。

  1. 配置解析器主要做了哪些基础校验？

参考回答：首先校验配置不能为空、业务域列表结构正确、业务域数量不能超过上限。然后校验每个启用域的标识格式、描述和系统提示词是否为空或超长。Tool 和 Skill 列表必须明确提供，并且不能同时为空。权限码也需要满足非空、长度和字符格式要求。

  1. 对于 Tool，还会进行哪些进一步校验？

参考回答：解析器会确认能力标识已经注册，并且不是仅供平台内部使用的系统能力。同一个业务域不能重复绑定同一种 Tool。Tool 本身还必须声明至少一个有效的工具方法，并检查工具名称是否合法，避免同一子 Agent 中出现名称冲突，否则模型无法确定应该调用哪个能力。

  1. 对于 Skill，会进行哪些进一步校验？

参考回答：Skill 必须能够被系统实际加载。静态 Skill 需要有可读取的 classpath 资源，动态 Skill 则需要实现运行时解析协议。如果 Skill 同时提供可执行 Action，还会检查 Action 是否为空、名称是否合法，以及是否与当前域中的其他 Tool 或 Action 冲突。这样可以尽量把资源缺失和注册冲突提前到配置刷新阶段。

  1. 为什么要限制业务域数量、提示词长度和权限码长度？

参考回答：配置中心内容最终会影响内存占用、Agent 提示词长度和模型上下文。如果完全不限制，错误配置可能一次创建大量业务域，或者把超长文本注入所有请求。长度和数量限制既是输入校验，也是资源保护手段，可以避免配置错误扩大为运行时故障。

  1. 为什么解析结果要转换成不可变快照？

参考回答：不可变快照可以保证一个请求在组装 Agent 时看到的是完整一致的配置，而不是正在被修改的中间状态。热更新时先在新对象中完成全部解析和校验，成功后一次替换引用。旧请求可以继续使用旧实例，新请求使用新快照，不需要在原对象上逐项修改。

  1. 用户权限是怎么计算出来的？

参考回答：系统先根据用户身份从 Paladin 权限配置中解析基础权限集合，同时支持所有用户共享的公共授权。请求还可以携带一个权限范围，但这个范围只能与用户基础权限取交集，不能增加用户原本没有的权限。因此请求参数只能缩小权限，不能通过声明权限码实现越权。

  1. 一个 Tool 绑定多个权限码时是什么语义？

参考回答：当前实现采用“拥有任意一个即可使用”的语义，也就是 OR。如果某个能力绑定了多个权限码，只要用户命中其中一个，能力就可以进入该用户的 Agent。这个语义需要在配置规范中明确，否则配置人员可能误认为必须同时拥有全部权限。

  1. 为什么要在 Agent 组装阶段过滤权限，而不是调用 Tool 时再校验？

参考回答：如果先把无权能力注册给模型，再依赖运行时拒绝，模型仍然能看到工具名称、描述和参数，并可能反复尝试调用。当前方案在组装阶段直接移除无权 Tool 和 Skill，使模型根本看不到这些能力。部分依赖具体业务配置的工具还会进行第二次运行时绑定，如果缺少必要业务配置，也不会注册到 Agent 中。

  1. 用户对某个业务域完全没有权限时怎么办？

参考回答：系统会先过滤该域下所有能力。如果过滤后 Tool 和 Skill 都为空，就不创建这个业务子 Agent，主 Agent 也不会获得对应的委托入口。这比创建一个空 Agent 后再返回“无权限”更干净，也减少了模型把请求错误路由到不可用业务域的概率。

  1. 如何防止 Paladin 配置把系统能力暴露给业务 Agent？

参考回答：平台将能力区分为普通业务能力和系统能力。任务状态、通知、临时状态等平台协议能力只允许由固定公共域装配。解析业务域配置时，如果发现引用了系统能力会直接拒绝整份配置，而不是依赖提示词告诉模型“不要调用”。

  1. 动态系统提示词会不会产生安全问题？

参考回答：会有风险，因此系统提示词不能代替权限和业务校验。当前解析器主要校验提示词非空和长度，提示词内容规范更多依赖配置发布流程，例如只描述角色定位、业务边界和行为基调，不应该在里面写权限绕过或具体工具调用规则。真正的能力范围由组装结果决定，即使提示词声称拥有某个 Tool，只要用户无权限，该 Tool 也不会出现在 Agent 中。

  1. 配置的提示词和最终子 Agent 提示词是什么关系？

参考回答：Paladin 配置的是业务域基础提示词。组装时系统还会追加统一的执行规则、语言要求以及当前用户实际可见的能力清单。能力清单根据权限过滤后的真实结果生成，而不是由配置人员手工维护，从而避免提示词中写着一个能力，但实际 Agent 没有该能力，或者反过来。

  1. Paladin 热更新具体是怎么实现的？

参考回答：服务启动时通过配置源注册监听器。配置发生变化后，监听器取得新的原始 JSON，重新执行完整解析和能力校验，生成新的领域快照。只有这些步骤全部成功后，系统才替换当前快照并清空主 Agent 缓存，后续请求会按照新配置重新组装 Agent。

  1. 配置更新失败时如何处理？

参考回答：由于新快照是在完整解析成功后才赋值，所以运行时配置解析失败时，旧快照不会被半成品覆盖，Agent 缓存也不会被清理。服务启动阶段则采用更严格的失败策略：配置源缺失、监听注册失败或者初始业务域配置非法都会导致启动失败，避免服务在未知能力集合下运行。

当前监听回调中没有单独做完善的异常捕获和告警，这是可以继续改进的地方。更完整的方案应该明确记录失败原因、配置摘要和刷新指标，同时保留最后一次成功快照。

  1. 热更新过程中如何保证线程安全？

参考回答：配置刷新和 Agent 创建通过读写锁协调。正常请求获取读锁并读取当前完整快照；热更新获取写锁，完成快照替换和缓存清理。在写锁释放前，新请求不会拿到“新配置配旧缓存”或者“旧配置配新缓存”的混合状态。

目前解析过程也在写锁内部完成，配置规模被限制后问题不大，但仍会增加刷新期间的请求等待。进一步优化可以先在锁外解析和校验，成功后只在写锁内完成快照替换和缓存失效。

  1. 为什么要缓存 Agent？缓存的依据是什么？

参考回答：Agent 组装涉及权限过滤、Tool 注册、Skill 解析和提示词构建，如果每次请求都重新完成会带来额外开销。当前实现会先计算用户在所有已配置能力中的有效权限集合，再对该集合生成指纹，权限集合相同的用户可以复用同一种主 Agent 装配结果。用户身份和会话状态由运行时存储隔离，不直接写入这个缓存键。

  1. 为什么缓存键里没有直接加入配置版本？

参考回答：当前代码的缓存键主要是权限指纹，业务配置变化时通过写锁下的全量缓存失效保证新请求重新创建 Agent。配置原文会计算摘要用于日志和识别快照，但没有直接拼入缓存键。这种方式实现简单，不过正确性依赖每条配置变更路径都必须执行缓存清理；另一种实现是把配置版本加入缓存键，可以减少漏清理风险，但需要处理旧缓存回收。

  1. 权限配置变化后，缓存怎么处理？

参考回答：用户权限配置也注册了独立监听器。权限配置刷新后，系统会清空主 Agent 缓存；下一次请求重新计算该用户的基础权限和有效权限集合，再构建或复用对应 Agent。权限指纹缓存按“权限集合”而不是用户 ID 保存，因此权限集合变化后自然会得到不同的指纹。

  1. 正在执行的请求会立即切换到新配置吗？

参考回答：不会强行修改已经创建并正在执行的 Agent。热更新主要对后续请求生效，正在执行的请求继续使用创建时的能力快照，这样可以避免执行到一半时 Tool 集合突然变化。相应地，紧急权限回收不能只依赖 Agent 缓存失效，关键写接口还应该在调用时重新校验权限或使用权限版本。

  1. 业务域被动态关闭后会发生什么？

参考回答：关闭的业务域在解析时会被跳过，新快照中不再包含该域，缓存清理后新请求也不会看到对应委托入口。已经运行中的请求通常不会被强制终止。对于长任务，还要结合任务自身的计划和状态决定是继续、暂停还是人工处理，不能仅根据新配置直接重复或跳过既有步骤。

  1. 业务域配置和用户权限配置为什么采用不同的失败策略？

参考回答：业务域配置非法时不能构造可靠的能力拓扑，因此初始加载选择失败启动，运行时刷新则保留旧快照。用户权限配置解析失败时，当前实现会得到空权限集合，整体上偏向 fail-closed，也就是宁可暂时不可用，也不继续授予无法确认的权限。后者安全性更高，但会影响所有用户可用性，因此需要配套告警和快速回滚。

  1. 如何测试这套配置化机制？

参考回答：需要覆盖四类测试。第一类是解析测试，包括空配置、非法格式、重复域、未知能力、系统能力引用和 Skill 资源缺失；第二类是权限测试，验证无权限能力不会出现在 Tool、Skill、子 Agent 描述和提示词中；第三类是热更新测试，验证成功刷新后缓存失效、失败刷新保留旧快照；第四类是并发测试，验证刷新与请求并发时不会产生混合快照。

当前仓库已有测试覆盖权限过滤、无可见能力时不创建子 Agent、仅 Skill 可见、运行时业务配置缺失以及权限解析等场景，但配置解析器和热更新并发场景还值得补充专项测试。

  1. 这个方案还有哪些不足和改进空间？

参考回答：第一，能力标识目前仍与 Spring Bean 名称有关，可以引入显式、稳定的能力 ID；第二，热更新失败需要增加独立日志、指标和告警；第三，可以把耗时解析移出写锁，只在快照切换时加锁；第四，对高风险 Tool 增加调用时权限复核，支持紧急撤权；第五，可以增加配置灰度、配置版本回滚和变更审计，避免错误配置直接影响全部实例。

4. 负责多格式文档理解链路，支持 XLSX、CSV、DOCX、PDF、PPTX、TXT、JSON 等 7 类文件的异步解析、内容分片、内嵌图片提取、BFS 上传和 Redis 临时存储，使 Agent 能按需读取文档而非一次性注入全文

4.1 具体实现方式

一、需求背景

用户希望直接把运营报表、策划文档、PDF、演示稿等文件交给 Agent 查询和总结。如果直接把原文件或全文放进 Prompt，会产生几个问题：

  • 不同格式的解析方式不同；
  • 大文档容易超过模型上下文；
  • 每次提问都注入全文，Token 成本和响应延迟较高；
  • Excel Sheet、PDF 页码、Word 标题等结构信息会丢失；
  • Office/PDF 中的图片无法通过纯文本解析；
  • 文件解析和 BFS 上传耗时较长，不适合阻塞聊天请求；
  • 不可信文件可能通过 ZIP Bomb、超大图片等方式耗尽资源。

因此，系统没有把文档处理成一个大字符串，而是转换成：

Agent 先查看结构，再根据用户问题读取相关范围，必要时才加载图片。

十三、为什么能避免全文注入

该设计通过四层机制控制上下文：

  1. 聊天消息只携带 fileId、文件名和类型。
  2. document_inspect 只返回结构，不返回全文。
  3. document_read 使用 offset/limit 定向读取逻辑范围。
  4. 图片只按 imageId 单独加载，不自动注入全部图片。

Skill 还明确要求：总结和分析必须由公共域 Agent 基于必要分页结果直接完成，只向主 Agent 返回结论和少量引用，禁止把全文转交主 Agent、写入临时状态或长期记忆。

文档引用会随会话历史保存，使用户后续说“继续看刚才的文档”时可以找回准确 fileId，但历史中仍然只保存轻量引用，不保存文档正文。

ZIP 条目、展开大小、压缩率 防止 ZIP Bomb
禁止宏、加密包和嵌套 ZIP 降低复杂格式风险

禁用 XML DTD 和外部实体 防止 XXE
页数、幻灯片数、Sheet 数和记录数上限 控制 CPU 和内存
图片数量、单图大小、总大小和像素数 防止图片资源耗尽
JSON 深度和标量大小 防止深层递归和超大字符串
分片、Manifest、Redis 总字节数 控制临时存储
解析截止时间 防止后台任务无限执行

文件类型虽然先由扩展名确定，但还会校验真实结构：PDF 检查 %PDF-，OOXML 检查 ZIP 和必要入口，文本类要求合法 UTF-8 且不能包含空字节。

fileId 必须是 UUID v4，并在 Redis Key 中绑定当前用户名。其他用户即使猜到 fileId，也无法通过自己的 owner Key 读取对应内容。

十五、失败和生命周期处理

解析过程中会记录已经写入的 Redis Key。如果任意阶段失败：

  1. 删除已经写入的 Part 和 Manifest；
  2. 将状态更新为 FAILED；
  3. 保存明确的 failureCode；
  4. 清理成功时把失败状态 TTL 缩短为 10 分钟；
  5. 删除本地临时文件；
  6. 释放活动任务配额。

本地临时目录还设置定时清理。activePaths 中正在解析的文件不会被误删；超过保留时间且不再活动的遗留文件会被清理。

状态接口还会检测排队任务和解析任务是否超过截止时间，并通过 Redis 条件更新避免过期状态覆盖并发产生的新 READY 状态。

十六、实现边界

这套能力有几个需要准确说明的边界：

  • 只支持 .xlsx、.csv、.docx、.pdf、.pptx、.txt、.json，不支持旧版 .xls/.doc/.ppt；
  • PDF 使用 PDFBox 提取文本，没有 OCR；
  • 扫描 PDF 正文为空时，只能按需读取页面内嵌图片，不能声称已识别扫描文字；
  • DOCX/PPTX 主要提取文本、表格、标题和图片引用，不还原完整排版；
  • 文档数据受 TTL 管理，不是永久知识库；
  • Redis 中保存的是解析后的结构和压缩分片，原文件与可访问图片保存在 BFS；
  • 文档内容、文件名、图片和替代文本均被视为不可信用户数据，不能作为系统指令执行。

4.2.1 自己想到的问题

1. 介绍一下这个亮点你做了什么工作？

这项工作主要是打通“用户上传文档 → 后端解析和存储 → Agent 按需读取并回答”的完整链路。 让用户可以直接把运营报表、规范文档等材料交给 Agent 分析，同时控制大文档对模型上下文的占用。

具体做了五部分工作。

1. 统一接入七种文件格式

为 XLSX、CSV、DOCX、PDF、PPTX、TXT、JSON 实现对应的解析器，并通过统一接口管理。

不同格式保留各自的内容结构，例如表格按工作表和行组织，PDF 按页组织，PPT 按幻灯片组织。这样，后面的存储和读取流程可以复用，不需要针对每种格式重新实现整条链路。

2. 将耗时解析放到后台异步执行

上传接口完成文件校验和临时落盘后，返回文件编号及解析状态，后台使用独立线程池执行文件上传、正文解析和图片提取。

同时维护解析进度、成功或失败状态，前端可以查询。这样，文件解析不需要一直占用上传请求等待完成。

3. 将正文分片，并建立结构索引

解析结果会按大小限制拆成多个内容片段，同时生成一份结构索引，记录工作表、页数或记录数量、各分片覆盖的范围和图片引用。

存储上分工如下：

  • BFS： 保存原文件和提取出的图片，提供访问地址。
  • Redis： 临时保存文件状态、结构索引和正文分片，并设置过期时间。

后续读取时，可以根据索引定位相关分片，不需要每次重新解析原文件。

4. 提取内嵌图片，支持按需理解

对于 Office 和 PDF 中可提取的内嵌图片，单独上传到 BFS，并记录图片编号、位置及可用的说明信息。

Agent 读取正文时先获得图片引用；只有问题涉及图片内容时，才调用图片读取工具，把必要图片交给多模态模型理解，避免默认加载全部图片。

5. 为 Agent 提供分层读取能力

我接入了三类读取工具：查看文档结构、按范围读取正文、读取指定图片，并通过文档读取 Skill 约束使用顺序。

例如，用户上传一份几十页的 PDF，询问第三页的某项规则。Agent 可以先查看结构，再读取第三页正文；如果解释依赖其中的图片，再补充读取图片。需要分析整份文档时，也可以分批读取，而不是一次性把全文放进上下文。

此外，还补充了文件大小、解压体积、解析时间和存储量限制，以及失败数据和本地临时文件清理，控制这条链路的资源消耗。

相关实现主要在 文档上传与读取服务 和 异步解析服务。

1. 异步解析：上传请求先返回，后台线程负责处理文件

这里使用的是进程内的有界线程池。代码默认配置为一个解析线程、最多十个排队任务，具体可以调整。队列满时返回繁忙响应，避免大量文件无限堆积。

后台还会更新阶段进度，并检查解析期限。失败时记录失败原因、尝试清理已写入的 Redis 数据；处理结束后清理本地临时文件。前端通过状态接口查看解析是否完成，Agent 在文件就绪后读取。

3. 如何避免 Agent 读到解析了一半的数据？

分片会陆续写入，但只有正文和结构索引保存完成后，系统才把文档标记为“可读取”。

写入状态和数据时，使用 Lua 脚本检查：文档是否仍处于解析中、是否超过任务或解析期限，以及是否还有有效存储时间。

读取入口则先检查文档是否就绪。因此，这里通过状态控制对外可读时机；整份文档的所有分片并不是一次事务写完的。

4. “临时”具体体现在哪里？

文档上传时确定过期时间，默认是上传后 24 小时。元信息、结构索引和正文分片写入时，都根据同一个截止时间计算剩余 TTL，后续写入不会重新获得完整的 24 小时。

解析失败时，会尝试删除已经写入的分片和索引。清理成功后，失败状态默认最多再保留十分钟，供前端查询失败原因。

数据过期或必要分片缺失后，读取接口会提示文件数据已过期，需要重新上传。

需要区分的是：Redis 数据过期不等于 BFS 文件同时删除。 当前这条链路没有实现随 Redis TTL 删除 BFS 原文件和图片的联动清理；本地临时文件则在处理结束后清理，并有定时清理兜底。

4.2.2 AI想到的问题

  1. 为什么不直接把文件或者全文交给大模型？

参考回答：不同模型对 Office、PDF 等文件的支持不一致，而且大文件很容易超过上下文窗口。即使模型能够接收文件，一次性注入全文也会增加延迟和 Token 成本，并且不方便定位某个工作表、页面或段落。因此系统先把文档解析成结构化索引和小分片，让 Agent 根据问题按需读取。

  1. 整个文档理解链路是怎样的？

参考回答：用户上传文件后，系统先完成身份、权限、文件类型和大小校验，再把文件保存到实例临时目录，并创建解析中的文档记录。后台线程依次完成安全扫描、原文件上传 BFS、内嵌图片提取、正文解析、Redis 分片写入和结构清单写入。全部成功后才把文档发布为可读状态，随后 Agent 可以通过结构检查、正文读取和图片读取三类能力使用文档。

  1. 为什么采用异步解析？

参考回答：Office 解压、PDF 文本提取、图片转换和 BFS 上传都可能耗时较长，不适合占用上传请求线程。上传接口只返回文件编号、类型、解析状态和过期时间，前端通过状态接口查询进度。聊天请求只有在文件解析完成后才允许携带该文件，避免 Agent 读取半成品。

  1. 异步解析如何做流量控制？

参考回答：解析使用独立的有界线程池和有界队列，队列满时直接拒绝新任务并返回繁忙，而不是无限堆积。上传入口还有单实例并发信号量，Redis 侧也限制单用户同时处于活动状态的文件数量。服务启动时还会校验任务总超时时间能够覆盖预期排队时间，避免任务还没开始就已经过期。

  1. 文档模块的核心组件如何分工？

参考回答：上传服务负责入口校验、临时文件和状态创建；解析服务负责编排后台流程；不同格式的解析器负责把内容转换为统一记录；Redis 存储负责元数据、结构清单和正文分片；BFS 负责保存原文件和图片；Agent Tool 负责向模型提供有限、按需的读取接口。格式差异被限制在解析器内部，其他层只处理统一数据结构。

  1. 7 种文件格式是如何统一接入的？

参考回答：系统定义了统一解析接口，每个解析器声明自己支持的文件类型，并通过回调逐个输出压缩后的正文分片，最后返回文档结构清单。解析服务启动时会校验所有枚举中的文件类型都有对应解析器，并拒绝重复注册。新增格式时主要增加文件类型、解析器、安全校验和必要的图片处理，存储及 Agent 读取流程可以复用。

  1. 不同格式解析后分别保留什么结构？

参考回答：

  • XLSX 按工作表和行保存，保留工作表名称、行数及第一行建议表头。
  • CSV 视为编号为 0 的单工作表，按行保存。
  • DOCX 保存段落、表格行和标题层级路径。
  • PDF 以页面为最小逻辑项，保存页码和页面文本。
  • PPTX 以幻灯片为最小逻辑项，保存标题、正文、表格和备注。
  • TXT 按有界文本块保存，同时保留行号和行内分块编号。
  • JSON 使用流式解析，将叶子值转换为带 JSON Pointer 路径、类型和值的记录。
  1. 为什么 XLSX 使用 EasyExcel？

参考回答：Excel 文件可能包含大量行，如果使用一次性加载整个工作簿的方式，内存占用会随文件大小增长。EasyExcel 可以通过监听器逐行消费数据，解析器只保留当前待写分片的少量记录。每个工作表独立维护分片编号，既降低内存压力，也方便后续按工作表读取。

  1. DOCX 和 PPTX 为什么采用流式 XML 解析？

参考回答：DOCX 和 PPTX 本质上是 OOXML 压缩包，直接构造完整对象模型可能占用较多内存。当前实现读取压缩包中的核心 XML，通过流式事件提取段落、表格、标题、幻灯片正文和备注。同时关闭 DTD 和外部实体能力，减少 XML 外部实体类攻击风险。

  1. PDF 是如何解析的？支持 OCR 吗？

参考回答：PDF 使用 PDFBox，按页面提取文本，每页作为一个逻辑记录，并使用临时文件型缓存减少大文件对堆内存的压力。当前代码不提供 OCR，因此扫描版 PDF 可能提取不到正文。扫描页存在图片时，系统可以按需读取图片让多模态模型理解，但不能宣称已经通过 OCR 得到了页面文字。

  1. JSON 为什么不直接反序列化成一个大对象？

参考回答：大 JSON 整体反序列化可能占用大量内存，也难以对嵌套深度和超长字符串进行细粒度限制。当前实现使用流式 JSON 解析器，逐层遍历对象和数组，把标量值输出为带路径的记录。同时限制嵌套深度、路径长度、字符串和数字长度，避免恶意 JSON 消耗过多资源。

  1. TXT 和 CSV 的编码如何处理？

参考回答：当前实现统一要求 UTF-8，并允许开头存在 BOM。解析器使用严格字符解码，遇到非法字节会失败，而不是静默替换乱码。TXT 还会拒绝空字符等明显二进制内容；CSV 则限制列数、单元格字节数和单行总字节数。

  1. 什么是文档 Manifest，为什么需要它？

参考回答：Manifest 可以理解为文档的结构目录，它描述文件类型、解析器版本、记录数量、工作表、标题、分片范围和图片引用。文件名、下载地址和状态等基础信息单独保存在文档元数据中。Agent 先读取结构目录，就能判断应该读取哪个工作表、哪一段正文以及是否存在相关图片，而不需要盲目扫描全文。

  1. 正文是如何分片的？

参考回答：解析器不断向分片累积器写入统一记录，当估算大小达到目标值时，就把当前记录集合编码为 JSON 并使用 GZIP 压缩，然后写入 Redis。每个分片会记录覆盖的起止行号或顺序项编号。系统同时限制单条记录、单分片、总记录数、总解压数据量和分片数量，防止单个文件占用过多资源。

  1. 为什么按字节大小分片，而不是固定每 100 行一个分片？

参考回答：不同记录大小差异很大，一百行短文本和一百行长文本的存储及模型成本完全不同。按目标字节数分片可以让 Redis value 和单次读取结果更加稳定。行号或顺序项仍然保存在分片索引中，因此读取接口可以继续按业务范围查询。

  1. Agent 按 offset 和 limit 读取时，如何找到对应分片？

参考回答：Manifest 中记录了每个分片覆盖的逻辑范围。读取时先筛选与目标区间相交的分片，再通过 Redis 批量读取并解压，最后按照记录自身的行号或顺序项编号做一次精确过滤。这样不会扫描所有分片，也不会因为分片边界与请求范围不完全一致而返回额外内容。

  1. 如何保证 Agent 不会读到半解析数据？

参考回答：正文分片会先逐个写入 Redis，全部解析成功后再写 Manifest，最后才发布可读状态。发布时会检查文档仍处于解析中、没有超时、Manifest 已存在并且原文件地址有效。读取端只接受可读状态，同时要求元数据、Manifest 和必要分片都存在。

需要准确说明的是，这不是一个覆盖所有分片的多 Key 数据库事务，而是通过写入顺序和最终发布屏障保证正常流程一致性。如果某个分片后来被异常删除或淘汰，读取端会把文档视为不可用，而不会返回不完整结果。

  1. 为什么 Redis 中不把全文放在一个 Key 里？

参考回答：单个大 value 会增加网络传输、序列化和内存峰值，即使只需要一页内容也必须读取全部数据。拆成元数据、Manifest 和正文分片后，可以按范围批量读取，也方便解析失败时删除已经写入的部分。每个 Key 使用同一个绝对过期时间，避免后写入的分片比文档本身多存活很久。

  1. BFS 在这条链路里承担什么职责？

参考回答：BFS 用来保存原文件和提取后的内嵌图片，Redis 只保存临时结构化内容和 URL 引用。原文件上传使用流式请求体，不需要把整个大文件再次读入 JVM 堆。这样二进制文件和高频临时索引分别由适合的存储系统承载。

  1. 为什么要在发布可读状态前完成 BFS 上传？

参考回答：原文件引用和图片引用也是文档完整性的一部分。如果先标记可读，再异步上传 BFS，Agent 可能拿到一个缺少原文件或图片地址的半成品。当前流程只有 BFS 上传、图片提取、正文分片和 Manifest 全部成功后才发布可读状态。

  1. BFS 上传失败如何处理？

参考回答：上传集成会在总截止时间内进行有限次数重试，并为连接、读写和总调用设置超时。如果仍然失败，整个解析任务进入失败状态，不会发布为可读。已经写入的 Redis 分片会被清理，但当前代码没有看到对已上传 BFS 文件的反向删除，因此后续可以增加对象生命周期策略或补偿删除，避免形成孤儿文件。

  1. Office 内嵌图片是如何提取的？

参考回答：系统读取 OOXML 中的文档关系、绘图关系和媒体文件，确定图片属于哪个工作表、行列、段落或幻灯片。支持 PNG、JPEG、GIF 和 WebP，并校验实际文件签名，不能只相信扩展名。同一个媒体资源在文档中出现多次时只上传一次，但可以生成多个位置引用。

  1. PDF 图片是如何提取的？

参考回答：PDFBox 会递归遍历页面资源和表单对象，找到嵌入图片，并记录对应页码。图片转换为 PNG 后检查像素数、单图大小和总大小，再上传 BFS。同一个底层图片对象会复用上传结果，解析失败或超限的个别图片会被跳过，避免图片问题完全阻塞正文读取。

  1. 为什么不给模型一次性加载所有图片？

参考回答：图片的多模态推理成本较高，而且很多用户问题只需要正文。Manifest 和正文读取结果只返回图片编号、位置和替代文本，不代表模型已经理解图片内容。只有用户问题确实涉及图表、截图或图片中的文字时，Agent 才选择相关图片编号调用图片读取接口，并且单次读取数量有上限。

  1. 系统如何识别文件类型？只看后缀吗？

参考回答：入口先根据允许的后缀确定目标解析器，但不会只相信后缀。PDF 会检查文件头，文本类文件会检查 UTF-8 和二进制空字符，OOXML 会检查 ZIP 结构、必要入口文件和内容类型文件。这个方案能过滤常见伪造文件，但还不是完整 MIME 嗅探，后续可以增加更严格的文件魔数检测。

  1. 如何防止 ZIP Bomb？

参考回答：XLSX、DOCX 和 PPTX 本质上都是 ZIP，单纯限制上传文件大小并不够。系统先根据 ZIP 目录检查条目数量、声明解压大小、压缩率、图片数量和图片大小；后台解析前还会真正读取条目，统计实际展开字节，并对核心 XML、共享字符串和样式文件设置单独上限。两次校验可以降低伪造 ZIP 元数据绕过检查的风险。

  1. 除了 ZIP Bomb，还有哪些资源限制？

参考回答：系统限制上传文件大小、单用户活动文件数、解析线程和队列、解析时间、总记录数、正文总字节数、分片数量、Manifest 大小、PDF 页数、PPT 页数、JSON 深度、图片像素和 Redis 单文件写入量。这些限制覆盖磁盘、内存、CPU、Redis 和模型上下文多个资源维度。

  1. 用户之间如何实现文档隔离？

参考回答：上传、状态查询和聊天使用统一的登录身份，并检查文档能力权限。Redis Key 不只是使用文件编号，还会加入用户名的 SHA-256 摘要；即使另一个用户猜到文件 UUID，也会查询到完全不同的 Key 空间。Agent Tool 读取时使用运行上下文中的当前用户身份，不接受模型自行传入用户名。

  1. 如何防止模型伪造 fileId？

参考回答：聊天服务只把已经解析完成的文件转换成轻量引用并注入对话，引用中包含服务端生成的 UUID。文档工作流要求 Agent 原样使用这个 UUID，不能根据文件名、路径或下载地址自行拼接。服务端还会校验 UUID 格式以及当前用户下是否存在对应文档。

  1. 文档内容中的提示词注入如何处理？

参考回答：文件名、正文、图片替代文本和图片内容都被视为不可信用户数据，不能当成系统指令执行。Agent 的文档工作流明确要求这些内容只用于回答当前问题，并且不能把正文写入长期记忆。真正的访问控制仍由服务端 Tool、用户绑定和范围校验保证，而不是依赖文档中的文字。

  1. Redis 数据和本地临时文件如何过期？

参考回答：元数据、Manifest 和分片使用统一的绝对过期时间，默认属于短期临时数据。解析失败时通常只保留较短时间的失败状态，便于前端查看错误。本地临时文件无论解析成功还是失败都会尝试删除，同时定时任务会清理超过保留时间、且不在活动集合中的遗留文件。

  1. 解析超时是如何处理的？

参考回答：文档有整体任务截止时间，后台 Worker 启动后还有更短的单次解析截止时间。解析器在读取文件、处理记录、上传图片和写分片过程中都会检查截止时间。状态查询也会识别长期停留在解析中的任务，通过条件更新将其标记为失败，避免任务无限处于处理中。

  1. 服务重启后，正在解析的文档能自动恢复吗？

参考回答：当前异步任务使用的是进程内线程池，不是持久化消息队列，因此服务重启后不会自动恢复原解析任务。Redis 中的文档会暂时保持解析中，之后在状态查询时根据截止时间转为失败；本地遗留文件由定时任务清理。若要求真正的重启续跑，应使用持久化任务队列，并让解析步骤具备幂等和断点恢复能力。

  1. 为什么要求 Agent 先 inspect 再 read？

参考回答：不同文件的结构差异很大，表格可能有多个 Sheet，Word 可能有标题层级，PDF 和 PPT 则以页为单位。先查看结构，Agent 才能知道有效范围和图片位置，然后选择与问题相关的部分读取。这既减少上下文，也降低读取错误 Sheet 或越界范围的概率。

  1. 为什么 XLSX 和 CSV 必须指定 sheetNo？

参考回答：XLSX 可能包含多个工作表，如果省略工作表编号，服务端无法确定用户希望读取哪一张表。CSV 虽然只有一张逻辑表，也统一使用编号 0，从而让表格类文件共享相同的读取协议。其他文档则按照顺序项读取，不需要工作表编号。

  1. 当前按需读取还有什么不足？

参考回答：读取接口会校验 offset 非负和 limit 大于零，但当前代码没有明显的单次 limit 上限。如果模型传入非常大的范围，仍可能一次读取大量分片并返回较大的工具结果。后续应增加单次最大记录数和最大返回字节数，并让 Agent 自动分页读取。

  1. 为什么文档正文不能写入 Agent 长期记忆？

参考回答：文档属于用户上传的临时、不可信数据，而且 Redis 内容会过期。如果把全文写入长期记忆，不仅占用大量存储，还可能造成敏感信息长期残留，并让过期文档内容继续影响后续对话。因此长期记忆只保留轻量引用或必要结论，需要原文时重新通过受控工具读取。

  1. 如何测试这套文档链路？

参考回答：需要为 7 种格式分别准备正常、空文件、超限和损坏样例，验证结构清单、分片边界和范围读取；为 OOXML 增加 ZIP Bomb、路径穿越、宏、嵌套压缩和超大图片用例；为 Redis 测试发布与超时竞争、缺失分片和 TTL；为 BFS 测试超时、重试和部分成功；最后做跨用户读取和 Agent 按需读取的端到端测试。

从当前仓库能看到完整的生产实现和大量防护逻辑，但没有检索到该文档模块对应的专项测试类，面试时不应夸大已有测试覆盖。更稳妥的表述是说明自己设计或执行过哪些验证，并把缺失的自动化测试作为改进项。

  1. 这个方案还有哪些可以继续优化的地方？

参考回答：第一，引入持久化任务队列，支持服务重启后的解析恢复；第二，为 BFS 文件和图片增加失败补偿及生命周期清理；第三，限制单次正文读取结果大小；第四，补充 OCR 和版面分析，提升扫描 PDF 与复杂表格能力；第五，增加解析耗时、队列等待、失败类型、Redis 写入量和图片提取量等监控；第六，完善 7 种格式和恶意文件的自动化测试。
